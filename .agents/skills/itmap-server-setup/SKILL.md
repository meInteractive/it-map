# Настройка сервера

Этот навык относится к серверу IT-MAP. Адрес, SSH-порт и имя административного
пользователя брать из текущего поручения или доверенной конфигурации среды. Не
публиковать их вместе с ключами и учётными данными в репозитории. Существующая
схема проекта описана в [SERVER.md](../../../docs/user/deployment/SERVER.md),
[RECEIVER.md](../../../docs/user/deployment/RECEIVER.md),
[RELEASES.md](../../../docs/user/deployment/RELEASES.md) и
[ACTIONS.md](../../../docs/user/deployment/ACTIONS.md).

## Какие данные нужны для подключения

Из приватной передачи владельца или доверенной конфигурации установить:

- адрес сервера в Tailnet и SSH-порт;
- имя административного пользователя;
- способ входа: обычный SSH с ключом либо явно настроенный Tailscale SSH;
- путь к существующему приватному ключу в текущей среде и, если доступен, к его
  публичной части; способ разблокировки ключа через безопасный механизм, если нужен;
- тип host key и независимо подтверждённый SHA256-отпечаток либо доверенный
  `known_hosts` для исходного сервера;
- разрешённую операцию и её границы, включая уже выданные разрешения.

Значения этих данных не сохранять в skill, публичный handoff, Git, PR или issue.
При следующей передаче дел повторить их **только отдельным внутренним текстом
в пользовательском чате**, вместе с результатами проверки и оставшимися шагами.
Содержимое приватного ключа, токены и пароли не переносить даже в этот текст.
Сохранённый путь к ключу не доказывает, что файл пережил смену среды.

Не объявлять доступ заблокированным до проверки путей из передачи. Отсутствие
`~/.ssh`, SSH-агента и secret bindings в статусе среды не исключает ключ в
допустимом каталоге workspace. Проверять наличие и права файла без вывода его
содержимого. Не создавать замену, пока не проверен указанный существующий ключ.
Недостающие параметры запрашивать по отдельности, не просить повторного
разрешения на уже порученную операцию.

## Сначала установить фактический доступ

1. Прочитать доступный в текущей сессии skill
   `cloud-environment:cloud-environment-runtime`, включая разделы о сети и
   Tailscale. Вызвать `cloud_environment.environment_status` и прочитать
   `/etc/codex/network-policy.json`. Состояние среды и снимок политики могут
   различаться; `vpn_configured` подтверждает конфигурацию, а не исправность VPN.
   Если нужно живое состояние, выполнить разрешённый runtime skill запрос к
   `http://proxy:8099/status` из внешнего executor и вывести только нужные поля
   Tailscale: `configured`, `state`, `routing_ready`. Не печатать весь сетевой
   статус. Старое наблюдение `disabled` не переносить на новый экземпляр.
2. Tailscale работает в сетевом сервисе среды. Отсутствие `tailscale`, интерфейса
   `tailscale0` или прямого маршрута в рабочем контейнере не означает отказ VPN.
   По [документации Codex Cloud](https://learn.chatgpt.com/docs/environments/cloud-environments#private-networking-vpn)
   адресам через Tailscale **не нужен отдельный список разрешённых IP или доменов
   Codex**, в том числе для SSH. Пустой `tcp_network_access` сам по себе не
   блокирует такой адрес; не требовать добавления IP `/32` без наблюдаемого
   отказа. Проверять маршруты и правила Tailscale и реальный ответ прокси.
3. Для SSH нужен raw TCP через HTTP CONNECT `proxy:8088`, обычно с локальным
   forward на `127.0.0.1`. Следовать команде и способу установки `socat` из
   skill текущей среды. Путь: SSH-клиент → локальный forward → CONNECT-прокси →
   адрес сервера через Tailscale. Локальный слушающий порт ещё не доказывает
   доступ к серверу: сделать реальное подключение клиента. Не устанавливать
   Tailscale в контейнер и не менять маршруты или настройки прокси.
   Сначала ограниченным по времени CONNECT к известному SSH-порту проверить
   ответ `200` и SSH banner без аутентификации. Это подтверждает транспорт,
   но не host key и не вход. Адрес брать из передачи, не сканировать Tailnet.
   Если `socat` отсутствует, допустим небольшой Python 3 stdlib relay как
   `ProxyCommand`: соединиться с CONNECT-прокси, передать исходный адрес/порт,
   полностью прочитать заголовки, принять только `200` и двунаправленно
   пересылать stdin/stdout. Протокольные байты идут только в stdout, ошибки —
   в stderr; нужны timeout на установление и обработка EOF. Не подменять
   SSH-аутентификацию и проверку host key. Команду, обращающуюся к sidecar,
   выполнять через штатное разрешение внешнего executor. При локальном forward
   клиент и listener должны быть в одном сетевом namespace.
4. Если прокси или sandbox отвергает запрос, использовать штатную процедуру
   разрешения среды и повторить тот же ограниченный запрос. Явный отказ
   политики, ошибка VPN, недоступный SSH-порт и отказ SSH-аутентификации — разные
   причины; сообщать этап и наблюдаемую ошибку. Не объявлять VPN неисправным по
   одному признаку внутри контейнера.

## Проверить SSH без изменений сервера

5. Найти доступный в этой среде административный приватный SSH-ключ, не выводя
   его содержимое. Ключ другой сессии нельзя считать доступным по памяти. Если
   его нет, создать **отдельную административную пару** в постоянном допустимом
   месте среды и показать владельцу только полный публичный ключ для добавления
   на сервер через доверенный канал. Отпечаток публичного ключа не заменяет сам
   ключ. Не считать новый ключ уже установленным.
6. Проверить SSH host key независимо через ранее доверенное подключение к
   серверу. Если владелец уже передал независимо подтверждённый отпечаток,
   получить соответствующий тип ключа через тот же CONNECT-маршрут, вычислить
   `ssh-keygen -lf` и сравнить точное значение SHA256. `ssh-keyscan` только
   получает ключ, но не подтверждает доверие. При совпадении сохранить ключ
   в отдельный `known_hosts` для исходного адреса; повторное подтверждение
   владельца не нужно. При несовпадении остановить вход, не перезаписывать
   доверенный ключ. Если доверенного отпечатка нет, показать наблюдаемый и
   остановить SSH-вход. При forward сохранять идентичность исходного сервера,
   например `HostKeyAlias` и проверенным `known_hosts`. Не отключать
   `StrictHostKeyChecking`; не путать ключ сервера с ключом пользователя.
   Для обычного SSH явно задать `-i`, `IdentitiesOnly=yes`, `BatchMode=yes`,
   `StrictHostKeyChecking=yes`, `UserKnownHostsFile` и `ConnectTimeout`.
   С ProxyCommand использовать исходный адрес, с loopback-forward — также
   `HostKeyAlias` исходного сервера. Членство в Tailnet не включает Tailscale
   SSH автоматически и не заменяет административный SSH-ключ.
7. После успешной аутентификации выполнить только чтение: `hostname`, `id`,
   версию ОС, архитектуру и состояние относящихся к IT-MAP служб. Сообщить
   отдельно, подтверждены ли CONNECT, host key, SSH-аутентификация и вход.
   Пока пользователь не поручил конкретное изменение, не трогать файлы,
   службы, базу данных или конфигурацию сервера.

## Если поручено снять календарный срок scheduler

Это не общее разрешение на изменение production. Использовать только уже
порученный владельцем объём работ.

1. Найти фактические units через `systemctl list-timers --all` и список служб,
   затем прочитать нужные unit-файлы. Имя установленного скрипта может отличаться
   от имени service/timer; не угадывать unit по имени файла. Если на сервере нет
   `rg`, использовать `grep`. Изучить установленный скрипт, не считать его
   идентичным репозиторию или обновлённым публикацией бинарника.
2. Из EnvironmentFile выводить только конкретное поле срока, без токена и
   остальных значений. Зафиксировать срок в UTC и часовом поясе владельца,
   состояние timer, следующее срабатывание, MainPID/активность service и
   безопасный итог последнего запуска. Ошибку `partial` не приписывать сроку.
   Отсутствие процесса tick не доказывает отсутствие работы backend/worker.
3. Перед изменением сохранить локальную на сервере резервную копию и hash.
   Точечно удалить календарную блокировку, сохранив токен, тело запроса,
   расписание, таймауты, защиту от redirect и существующие бюджетные ограничения.
   Не устанавливать целиком новую версию с несвязанными изменениями.
4. Проверить синтаксис и синтетические сценарии с подставным opener без сети:
   истёкший/отсутствующий срок больше не блокирует запрос, невалидный токен
   отвергается, параметры запроса прежние. Проверить точный diff, права файла
   и состояние timer после записи. Не запускать service вручную для проверки:
   обычный tick может инициировать платную работу. Диагностический HTTP-запрос
   также не считать автоматически разрешённым или свободным от записей в БД.
5. Проверить ближайшее естественное срабатывание, если оно наблюдалось; иначе
   явно указать, что результат ещё не проверен. Не сбрасывать состояние failed
   ради красивого отчёта. БД, backfill, платные Actor, merge и deploy требуют
   своего разрешения, если не входят в текущее поручение.

## Подготовка ограниченного доступа для релизов

8. Когда пользователь поручит настроить релизы, использовать подтверждённый
   административный вход только для установки: создать отдельного пользователя
   `itmap-deploy-main` с заблокированным паролем, установить root-owned приёмник
   релизов и настроить для его ключа `restrict` + forced command и точное правило
   `sudo`, как в [RECEIVER.md](../../../docs/user/deployment/RECEIVER.md).
   Проверить путь Python для ОС сервера и обе совпадающие команды в
   `authorized_keys` и `sudoers`; проверять `sudoers` через `visudo -cf`.
   Релизный ключ не должен давать интерактивный shell или общий root-доступ.
9. Установить происхождение **пары для релизов**. Публичный ключ должен быть в
   `authorized_keys` релизного пользователя на сервере. Для существующего
   GitHub workflow соответствующий приватный ключ требуется в секрете GitHub
   Environment `itmap-main` как `DEPLOY_SSH_KEY`, а подтверждённый host key —
   как `DEPLOY_KNOWN_HOSTS`. Сохранённый в GitHub *публичный* ключ или GitHub
   Deploy Key сам по себе не позволяет Actions войти на сервер. Не копировать
   административный приватный ключ в GitHub. Если релизы запускаются также из
   Codex, использовать отдельный ограниченный ключ Codex для того же приёмника.
10. Проверить ограниченный вход запросом `status`, отказ интерактивной команды
    и отказ использования неправильного слота. Проверка подключения не является
    публикацией. Реальный релиз выполнять только по отдельному прямому поручению:
    сверить точный SHA, целевой сервер, архитектуру, обязательные проверки и
    состояние работающего релиза, затем проверить результат и доступность сайта.
    Откат кода не откатывает базу данных.

## GitHub Actions — отдельный этап

11. Tailscale этой среды Codex не даёт GitHub-hosted runner маршрута в Tailnet.
    Для текущего временного сервера runner использует публичный SSH-адрес из
    `DEPLOY_HOST`; VPN ему не нужен. Проверять доступность порта 22 и host key
    именно из Actions. Для будущего сервера без публичного SSH понадобится
    отдельный маршрут runner. Выполнить пункты из
    [ACTIONS.md](../../../docs/user/deployment/ACTIONS.md), включая GitHub
    Environment, секреты, архитектуру сервера и проверку точного SHA. Не включать
    `ITMAP_DEPLOY_ENABLED` и не запускать публикацию только на основании
    успешного SSH из Codex.
12. При `ssh_private_key_invalid` проверить, что `DEPLOY_SSH_KEY` содержит полный
    многострочный приватный ключ OpenSSH, а не `.pub` или его отпечаток. Если
    владелец должен сам заполнить GitHub secret, генерировать релизную пару на
    его доверенном устройстве и передавать Codex только публичную часть.
    При `missing_or_invalid_ssh_settings` проверить `DEPLOY_HOST`: только IP или
    имя без схемы, пользователя, порта и пробелов. Значение `DEPLOY_KNOWN_HOSTS`
    составлять для того же адреса из независимо проверенного host key. Если
    интеграция GitHub возвращает 403 для секретов, владелец добавляет их через
    интерфейс GitHub; не просить присылать приватный ключ в чат.
13. После слияния PR найти запуск `Publish native main` с событием `push` и SHA
    merge-коммита. Убедиться, что `register`, обязательный CI, `package` с
    архитектурой сервера и `publish` завершились успешно, а не были пропущены.
    Проверить терминальный `success` приёмника, ссылку `current` на тот же SHA,
    активную службу и внешний HTTPS. Пока бизнес-API не перенесён, для текущего
    staging ожидаются live200, SPA200 и ready503 с
    `business_api_not_migrated`. Успешный ручной `workflow_dispatch` не
    доказывает автоматический запуск по push.

Не печатать приватные ключи, содержимое `.env`, токены, пароли или пользовательские
данные. Не включать автодеплой, не менять DNS и не выполнять миграции, импорт или
удаление данных без отдельного поручения владельца.
