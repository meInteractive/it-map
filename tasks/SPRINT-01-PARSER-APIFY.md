# Спринт 1.1: сквозной Go-парсер HH через Apify

**Актуальный маршрут с 31.10.2026.** Это приоритетная очередь внутри [спринта 1.1](SPRINT-01.md) до первой работающей цепочки `HH-источник → Apify → кандидаты → классификация → полный текст → извлечение → конечные роли → импорт → MariaDB/API`. Выполнять пункты по порядку, не переключаясь на UI, письма, другие источники, общую доводку CRM или production cutover. Исключение — исправление дефекта, без которого текущий пункт нельзя безопасно принять.

Пункты ниже **не закрывают автоматически** родительские GO-021…027, GO-039/044/046 и ранее выделенные GO-368…372/392/393. Уже написанный код проверять и использовать, а не переносить заново. `[x]` ставить только при выполнении критерия конкретного пункта, положительном обязательном CI и ссылке на коммит/PR в этом файле. У каждого пункта — один проверяемый результат и отдельный PR; зависимые PR можно складывать в стек по правилам [AGENTS.md](../AGENTS.md). Если обязательный тест упал или этап небезопасен, зафиксировать причину здесь и не переходить к зависимому пункту. Следующий чат начинает с первого незавершённого доступного пункта, сверив фактическую `main`, статус PR и CI.

**Граница готовности.** На отдельной MariaDB 10.11+ настроенный HH-источник запускается вручную и по расписанию, Apify возвращает страницы, кандидаты переживают рестарт, релевантные вакансии проходят все стадии и читаются из основной таблицы через Go API. Повторный цикл не создаёт дублей, неизвестный результат платного вызова не вызывает слепого повтора, отказ/смена настроек/поколения оставляет данные и бюджет согласованными. Сначала это доказывается на одноразовой БД и mock-провайдерах, затем ограниченным запуском на изолированном staging с настоящим Apify. Результат staging не означает разрешение включить parser в GPT Sites, импортировать реальные данные или открыть production.

**Уже есть:** Apify HTTP-клиент без runtime-подключения (`internal/integrations/apify`); durable leases, attempts и отдельные SQL/AI-стадии (`internal/parser`); подготовленное планирование следующей стадии и проверка содержимого текста. В `cmd/itmap` нет worker, а Go-исполнителей `scan_source`, `fetch_full_text` и `import_vacancy` нет. Временный staging сейчас отвечает `ready503` (`business_api_not_migrated`); MariaDB 10.3.32 не поддерживает текущую схему, проверен минимум 10.11. Эти факты повторно сверять с кодом перед исполнением, не считать исторический статус `[ ]` доказательством отсутствия реализации.

## Строгая очередь

### [x] GO-396. Замкнуть SQL-планирование кандидата

- **Зависимости:** существующие GO-368…372 и GO-392/393; их фактический код и CI проверить первым делом.
- **Результат:** одна owned-транзакция после сохранения результата стадии повторно читает актуальные owner/source/title/raw/extraction/roles, выбирает ровно следующую стадию и атомарно ставит задание. Проверить переходы `classify_title → fetch_full_text → extract_vacancy → assign_roles → import_vacancy`, отсутствие задания при reject/пустых ролях, отказ на stale generation/config и imported-кандидате. Не доверять `job.payload` для scope.
- **Приёмка:** source parity для ключей и решений плюс обязательная одноразовая MariaDB с cache/replay/concurrency/rollback; положительный CI без skips. Если всё уже подтверждено, зафиксировать доказательства без повторной реализации. Runtime и внешняя сеть остаются выключены.
- **Проверено:** PR [#200](https://github.com/meInteractive/it-map/pull/200), код `47bd7aaecd50a427127ec03f1bc41363ac1ae45d`: все обязательные CI успешны. Disposable MariaDB проверила реальный SQL-планировщик и handoff после классификации, extraction и выбора ролей, отсутствие задания при reject/пустых ролях, повтор, конкуренцию, поздний rollback, смену правил и поколения, ограничения source и подменённый payload. Source-oracle сравнивает решения и ключи со старым JavaScript. Импортированный кандидат блокируется до выбора стадии. Локально прошли `go test -race ./...`, `go vet ./...`, сборка Go и `TestUnchangedCandidateStageSource`. Исполнители `fetch_full_text` и `import_vacancy` относятся к GO-400/401; runtime здесь не включён.

### [x] GO-397. Настройки, ключ и права Apify

- **Проверено:** PR [#201](https://github.com/meInteractive/it-map/pull/201), код `2714e2b2d3accbd17ffac87954e254437f81739f`: все три обязательных CI успешны, включая disposable MariaDB без skips. Подтверждены шифрование/ротация ключа, revision CAS, generation, недоступный старый ключ, права административного HTTP, серверные версии операции, актуальный owner/source URL и disabled. HH компаний доступен через отдельный список с областью избранного и форму во вкладке Apify; legacy PUT компании/hh подключён. Source-тест сверяет конфигурацию с неизменённым JS. Исправлены зависимости кэша и проверена совместимость с сессией после merge #193. Общий смешанный список Firecrawl и агентства остаются вне отдельного HH-пути; запуск Actor и денежный журнал — GO-398.

- **Зависимости:** GO-396; существующие GO-021/040 и схема `apify_settings`.
- **Результат:** Go читает и меняет только разрешённые настройки Apify и HH-источника через защищённый административный путь; токен хранится зашифрованным, не попадает в GET/логи/PR. Смена ключа, revision, generation, owner/source URL или отключение источника запрещает использование старой операции. При недоступном старом ключе допустим отдельный повторный ввод без раскрытия ciphertext.
- **Приёмка:** source/SQL/HTTP тесты прав, CAS, redaction, ротации и восстановления; без реального токена и вызовов Apify.
- **Порядок реализации:** (1) `internal/apifysettings` — проверка профилей/JSON, revision и безопасное публичное представление с тестами контракта; (2) SQL singleton и `legacycrypto.Apify` — generation fence, CAS, шифрование и ротация в одной транзакции, тесты на disposable MariaDB; (3) admin-only `/api/apify/settings` и `/api/apify/key` с same-origin и ограничением body, HTTP-тесты прав и ошибок; (4) защищённое чтение/изменение HH-источника через существующий контракт, проверка owner, URL, revision и disabled в SQL; (5) source/SQL/HTTP и CI на точном SHA. Actor, расход и внешние вызовы остаются в GO-398/399.

### [ ] GO-398. Устойчивый запуск Apify с бюджетом

- **Зависимости:** GO-397; изолированный Go-клиент GO-081/039 и существующий денежный ledger.
- **Результат:** серверная операция резервирует допустимый лимит до Actor POST, записывает operation/run/dataset IDs, опрашивает статус и стоимость, различает `running`, `failed`, `succeeded`, `uncertain`. После таймаута или неизвестного ответа POST не повторяется вслепую; восстановление сверяет известный run и освобождает резерв только при доказанном отсутствии расхода. Free/paid policy и предел одного HH-запуска соблюдаются.
- **Приёмка:** mock HTTP + одноразовая MariaDB: конкурентный запуск, crash до/после POST, неизвестный ответ, повтор, ротация ключа, исчерпание бюджета и отсутствие двойного списания. Платных запросов нет.

### [ ] GO-399. HH-листинг и сохранение кандидатов

- **Зависимости:** GO-398; HH URL/input из Apify-клиента и старый `apify-discovery` как контракт.
- **Результат:** `scan_source` строит title-фильтр из актуальных корневых ролей, запускает разрешённый Actor, постранично читает dataset, валидирует/карантинирует записи и сохраняет новых или обновлённых `vacancy_candidates` с source/owner/provenance. Cursor, page/offset и run ID переживают рестарт; повтор страницы не создаёт дублей и не теряет обновление заголовка. После записи атомарно ставится классификация.
- **Приёмка:** source fixtures + mock Apify + одноразовая MariaDB: минимум две страницы, ошибочная запись, пустой/изменённый dataset, restart/resume, concurrent scan, duplicate URL и смена source revision. Первый рубеж: **кандидаты реально видны в БД**, без AI и импорта.

### [ ] GO-400. Полный текст HH и проверенный снимок

- **Зависимости:** GO-399 и существующая проверка GO-395.
- **Результат:** `fetch_full_text` для принятого HH-кандидата использует сохранённый снимок либо безопасное получение detail (включая предусмотренный старым контрактом бесплатный HH-путь и Apify fallback), проверяет URL/статус/содержимое, пишет hash, provenance, диагностику и историю fetch. Не передавать модели неполный/повреждённый текст, не тратить бюджет при cache hit; после успеха планировать извлечение.
- **Приёмка:** recorded detail fixtures, mock transport, SQL rollback/retry/stale source tests и чтение полного текста из MariaDB, в том числе составного снимка. Другие источники и Firecrawl не блокируют маршрут HH.

### [ ] GO-401. Атомарный импорт вакансии

- **Зависимости:** GO-396 и GO-400; подготовленные extraction/leaf SQL-стадии GO-364/366.
- **Результат:** `import_vacancy` повторно проверяет кандидата, extraction, непустые конечные роли и owner/source, создаёт либо обновляет основную вакансию и связывает `main_vacancy_id`, источник и историю в одной транзакции. Повтор job/конкурентный импорт не создаёт дублей и не перезаписывает ручные изменения; старый receipt позволяет безопасный replay.
- **Приёмка:** одноразовая MariaDB: create/update/no-op, 2 конкурирующих worker, late failure/rollback, restart/replay, deleted/changed source и чтение созданной вакансии через существующий Go API.

### [ ] GO-402. Релевантность после импорта

- **Зависимости:** GO-401; типизированное JEV-решение GO-357 и бюджет/attempts.
- **Результат:** для импортированной HH-вакансии вычислять и сохранять релевантность только по актуальным полям/ролям и для нужного пользователя; повтор использует совместимый cache/receipt. Ошибка оценки не удаляет импортированную вакансию и не вызывает второй оплачиваемый POST без подтверждения исхода.
- **Приёмка:** source/mocks + MariaDB: score, cache, stale model/prompt, budget refusal, неизвестный платный исход и изоляция пользователей. Это завершает целевую цепочку обработки, но не добавляет генерацию писем.

### [ ] GO-403. Исполнение одного полного цикла worker

- **Зависимости:** GO-399…402, GO-394 и принятый durable-core GO-045.
- **Результат:** серверный worker получает due jobs под lease и направляет `scan_source`, `classify_title`, `fetch_full_text`, `extract_vacancy`, `assign_roles`, `import_vacancy`, `score_relevance` в конкретные исполнители, связывая подготовленные `RouterService`/`Generator` с AI-диспетчером; завершает attempt/job и передаёт следующую стадию. Ключи, модель и владелец берутся из серверной конфигурации, не из payload. Ручной bounded cycle завершается, отменяется и восстанавливается после crash без второго оплачиваемого вызова.
- **Приёмка:** полный mock-provider/MariaDB цикл от источника до API readback, а также SIGKILL/restart, lease expiry, generation rotation, ошибки каждой стадии и отказ неподдерживаемому типу. Пока без таймера и live Apify.

### [ ] GO-404. Ручной запуск, расписание и остановка

- **Зависимости:** GO-403 и GO-021/027/046.
- **Результат:** защищённая команда ручного запуска и один серверный scheduled tick используют тот же worker; disabled/budget/dry-run/favorites/source scope соблюдаются. Не допускать двух параллельных циклов, обеспечить остановку, понятные run/job/expense diagnostics и возобновление после рестарта. На изолированном Go staging не запускать старую Site Automation против того же набора данных.
- **Приёмка:** SQL/HTTP тесты прав, расписания, паузы, двух экземпляров, restart и диагностик; тест доказывает отсутствие задания при disabled. Live provider ещё выключен.

### [ ] GO-405. Обязательная сквозная приёмка на синтетической БД

- **Зависимости:** GO-404.
- **Результат:** required CI запускает Go HTTP + worker + одноразовую MariaDB 10.11 с mock Apify/JEV/LLM. Одна HH-страница с несколькими записями даёт импортированную вакансию, отклонённый title не импортируется, повтор и рестарт сохраняют ровно один результат и корректные расходы. Вакансия читается из Go API с ролями/источником/описанием; ручной и scheduled запуск проверены отдельно.
- **Приёмка:** тест проходит на точном SHA без skips и без внешних денег/секретов; web/build/security и профильные source-oracle gates зелёные. Провал любого звена не заменять unit-тестом соседнего звена.

### [ ] GO-406. Изолированный staging для парсера

- **Зависимости:** GO-405; отдельное поручение на изменение сервера/БД/секретов.
- **Результат:** проверить версию и состояние целевой БД без изменений; подготовить отдельную MariaDB 10.11+ со схемой, пользователем и синтетическим HH-источником, настроить защищённые интеграционные ключи и лимит без публикации секретов. Подтвердить `health/ready`, ручной цикл с mock-провайдерами, SQL/API readback и откат конфигурации. Не переносить реальные D1-данные и не обновлять 10.3 поверх существующих данных автоматически.
- **Приёмка:** зафиксированы версия, схема, SHA, run ID, редактируемая конфигурация, результаты API/SQL и способ выключить parser. Если доступ/разрешение ещё отсутствуют, пометить этот пункт заблокированным, сохранив пройденные CI-доказательства.

### [ ] GO-407. Ограниченная проверка с настоящим Apify

- **Зависимости:** GO-406; отдельное разрешение владельца на платный вызов и расходный лимит.
- **Результат:** на изолированном staging один разрешённый HH-источник проходит Actor → dataset → кандидат → detail → реальные AI-стадии → импорт → API/БД. Зафиксировать стоимость, ошибки, run IDs и итоговую вакансию без пользовательских данных в отчёте. Повторный запуск не создаёт дубль и не запускает второй Actor без необходимости; после проверки автоматический режим остаётся только в согласованных границах.
- **Приёмка:** проверены фактический внешний Apify и нужные AI-провайдеры, полный run и readback основной вакансии, восстановление после остановки и бюджет. Для каждого платного провайдера требуется отдельно подтверждённый лимит; без него пункт остаётся заблокированным, а не отмечается выполненным по mock-результату. До этого пункта не объявлять parser рабочим с Apify.
