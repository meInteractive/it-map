# GO-431: контракт paid execution для bound worker

Этот документ описывает незавершённую реализацию. `BoundAttempt.Reserve`
фиксирует резерв, но не отправляет запрос и не подтверждает стоимость. Сеть,
settlement и подключение к runtime остаются закрыты до выполнения критериев.
См. [consumer fence](GO-431-CONSUMER-FENCE.md) и
[проект версионированной схемы](GO-431-CONTROL-SCHEMA-DESIGN.md).

## Инварианты границы платной операции

1. Текущий generation, consumer, run и job проверяются под согласованными
   блокировками до каждой записи; сроки повторно проверяются перед commit.
   Данные запроса клиента не подтверждают владение. Одноразовый в памяти
   `BoundRun` не восстанавливается после потери процесса.
2. До сети должен быть подтверждён durable reserve с проверкой общего бюджета,
   неизвестных расходов и provider-specific operation identity. Ошибка или
   неизвестный исход commit не разрешают автоматически повторить запись или
   вызвать провайдера; сначала перечитать состояние под проверенным fence.
3. Перед единственным платным POST нужен durable переход в состояние
   неопределённого исхода. Ответ или ошибка транспорта не доказывают, что
   провайдер не исполнил запрос. Нельзя повторно отправлять POST только из-за
   timeout, отмены, падения процесса или потери ACK. Для Apify сохраняется
   существующий `apify_runs.claimStart` и связь operation identity с run ID;
   второй параллельный ledger или обход этого механизма не допускаются.
4. После потери consumer fence новая работа запрещена. Внешний запрос мог уже
   уйти; его нельзя отменить SQL-блокировкой. Сохранить резерв и unknown-paid,
   не объявлять отсутствие ответа бесплатным и не освобождать его наугад.
5. Settlement не должен доверять произвольному JSON только потому, что он имеет
   поле стоимости. Нужна доказуемая связь ответа с конкретной оплаченной
   операцией и корректным провайдером; идентичность, outcome и политика данных
   должны быть определены для каждого адаптера. Стоимость сверх резерва нельзя
   молча обрезать. Неизвестная стоимость остаётся зарезервированной.
6. Завершение attempt и job, денежный receipt и запись результата должны иметь
   явную атомарную границу. При неизвестном commit повторное выполнение функции
   и повторный вызов провайдера запрещены до чтения зафиксированного исхода.
   При draining новые reserve/POST запрещены; завершать ранее начатое можно
   только при сохранённом fence и с учётом полной paid evidence.

## Вопросы реализации, которые нельзя закрыть предположением

- Как долговечно связать request identity, reservation, marker отправки и
  подтверждённый ответ, не сохраняя токены, payload и персональные данные?
- Как проверяется подлинность результата и цена у каждого провайдера, если
  callback в памяти не переживает процесс? Какие источники reconciliation
  позволяют однозначно установить исход, а какие оставляют его неизвестным?
- Где хранить маркер вне v39 без потери backup/restore совместимости, как
  менять generation и не возрождать старого владельца после restore?
- Как ограничивать запуск внешней работы после подтверждения consumer без
  ложного обещания атомарности между SQL и сетью? Какая гарантия даётся старым
  бинарником, не знающим fence, и как подтверждается его остановка?

## Обязательные доказательства

Только синтетические провайдеры и disposable MariaDB: конкурентные reserve и
interrupt; обрыв до/после commit reservation и marker; lost ACK provider POST;
ошибка после успешного commit settlement; истечение owner/run/job в каждой
точке; draining во время запроса; SIGKILL, рестарт и rotation generation;
сохранение неизвестного резерва и отсутствие второго POST. Для известного
ответа проверить корректную цену, превышение резерва и ошибочный provider;
для неизвестного — невозможность фиксации нулевой стоимости или повторного
платного вызова. Выполнить существующие billing/source и Apify idempotency
проверки без skip в CI на точном SHA. Production SQL и платные вызовы в эту
проверку не входят.

## Кандидат identity и диагностики HH

`apifyruns.HHJobKey` строит непрозрачный стабильный ключ generation/job/step,
не включая меняющиеся run, lease owner и attempt. Его можно использовать как
аргумент существующей HH operation identity, которая также привязывает source и
конкретный input. Никакие URL, payload и credential в этом ключе не хранятся.
Изменение generation после restore создаёт другую identity: до нового старта
обязательна отдельная проверка старых paid evidence и draining.

`ClassifyRecoveryEvidence` различает неизвестный исход без run ID, необходимость
reconcile известного run и терминальную запись со стоимостью. Это описание
строки, не доказательство её связи с attempt, подлинности ответа или разрешение
POST/settlement. Durable связь с конкретным attempt, consumer fence, atomic
reserve/marker и восстановление после crash остаются необходимыми; данные
функции сами по себе не подключаются к worker runtime.
