## 1. Проверенный кодом пробел

- `internal/parser/attempts.go`: `reserveAttemptLocked` запрещает повтор при неопределённости у **того же job_id** и у **того же candidate_id + типа AI-этапа**. Для `score_relevance` есть дополнительная корреляция по основной вакансии.
- Для старых/осиротевших попыток проверяется отдельное поколение и некоторые признаки незавершённого расхода. `/recoveryz` содержит дополнительные **read-only** счётчики, в том числе `reserved_usd=0,cost_usd=NULL` с провайдером. Счётчики не являются доказательством неоплаты.
- При разных `candidate_id`, но **фактически одинаковом полном AI-входе**, текущие guards не имеют межкандидатного долговечного ключа. При отсутствии `scheduler_jobs` у orphan попытки нельзя безопасно восстановить кандидатскую привязку. Это **остаточный риск**, а не доказательство совершённого повторного POST.
- `Attempt.Run` выполняет сетевую работу после резерва, помечает исход неизвестным до известного settlement и не делает retry сам. Однако уникальность `job_id` или наличие успешного COMMIT локального резерва **не доказывают**, что другой job не отправит эквивалентный запрос.

## 2. Предлагаемый контракт (требует отдельного утверждения)

1. **Стабильный semantic fingerprint.** До платного вызова сервер строит версионированный отпечаток **полного эффективного входа**: тип AI-этапа, tenant/область прав, нормализованный запрос, модель и provider policy, версии/снимки prompt и схемы, настройки генерации, назначенные роли, контекст вакансии/резюме и другие влияющие на результат атрибуты. Не включать `job_id`, `candidate_id` или `run_id` как обязательный компонент для межкандидатного сравнения; при этом не отождествлять похожие названия, если различаются настройки или содержимое. Не использовать только title/URL/вакансию как ключ.
2. **Канонизация и защита.** Одинаковый смысл должен давать одинаковые байты и digest при перестановке ключей JSON; разные prompt/model/scope/входы — разные digest. Избежать недетерминированного JSON/порядка полей, Unicode-расхождений, неоднозначности `null` и пустых значений. Отпечаток и версия алгоритма хранятся без raw prompt, full text или PII в логах. Решение о HMAC/хранении ключа, защите от offline-угадывания и ротации отдельно пройти security review.
3. **Durable ledger до POST.** Для каждого `fingerprint` требуются атомарные unique/admission, идентификатор операции, owner/generation/lease, provider/model, фаза вызова, временные метки, резерв и статус списания. Факты относятся к операции и **не исчезают** при удалении job/кандидата или смене поколения. Нужен внешний ключ/связь «много jobs → одна paid operation»; не подменять `scheduler_attempts` результатом одного job.
4. **Однократное право dispatch.** Под ownership/lease и бюджетным guard выполнить COMMIT перехода в состояние «вызов мог быть отправлен» **до** сетевого I/O. Если COMMIT неоднозначен — не отправлять и не выдавать автоматическое право повторить. Между COMMIT и фактической отправкой возможна консервативная блокировка операции, которая не состоялась: доступность здесь сознательно ниже денежной безопасности.
5. **Reconciliation вместо слепого replay.** Зафиксировать запросный idempotency key и provider operation/receipt ID только там, где провайдер гарантирует соответствующую семантику. При потерянном ACK, SIGKILL, отмене, неизвестной стоимости или неопределённом COMMIT новая операция на тот же fingerprint должна оставаться заблокированной до независимого доказательства. Провайдерский request ID, если он не поддерживает идемпотентность, сам по себе **не** разрешает повторный POST.
6. **Settlement и потребители.** Подтверждённые provider usage/cost — отдельно от reserve. `cost_usd=NULL` не превращать в 0 даже при `reserved_usd=0`. Известный результат для полностью идентичного входа можно переиспользовать для другого job **только после** проверки полномочий, generation, версии output schema и актуальности контекста. Reuse не должен объявлять результатом неотправленный или незавершённый вызов.
7. **Историческая неопределённость.** Не «заполнять задним числом» fingerprint из приблизительных candidate/title/URL для старых orphan/unknown записей. Для их разблокировки нужен отдельный read-only reconciliation по достоверным receipts и разрешённый операторский протокол. Нельзя глобально останавливать независимые AI jobs только по наличию одного неатрибутируемого orphan без решения владельца.

Предлагаемые условные фазы: `prepared` → `dispatch_uncertain` → `provider_confirmed` → `settled` либо `needs_reconciliation`; переход `known_not_sent` допустим только при доказательстве, позволяющем безопасно вернуть право отправки. Это **не утверждённая** SQL-схема; переходы и инварианты требуется отдельно описать до реализации.

## 3. Прежде чем писать миграцию

- Найти все места построения фактического `GenerationRequest`, модели, роли и prompt/config в `internal/parser`, `internal/aiproviders`, `internal/profiles`; сформировать матрицу влияющих полей отдельно для `classify_title`, `extract_vacancy`, `assign_roles`, `score_relevance`.
- Проверить provider idempotency/reconciliation contract **на конкретных адаптерах**, не предполагать поддержку по названию провайдера. Установить точное место правообразующего COMMIT относительно HTTP-запроса и `Attempt.Run`.
- Спроектировать append-only evidence/связи с `scheduler_attempts`, `scheduler_jobs`, бюджетами, generation и существующими AI-кэшами. Рассмотреть уникальный ключ и конкурентный claim без блокировки сетевого I/O в SQL.
- Сформулировать миграцию/rollback, dry-run на disposable MariaDB, проверку индексов, restore из свежей тестовой копии. **Production backup/restore, DDL и запуск paid providers не разрешены этим документом.**

## 4. Обязательные синтетические проверки

| ID | Сценарий | Инвариант |
| --- | --- | --- |
| AI-ID-01 | Два конкурентных job разных кандидатов с полным одинаковым входом | Не более одного права на платный dispatch |
| AI-ID-02 | Разные prompt, модель, настройки, роли, tenant или полный текст | Не ошибочно объединять разные входы |
| AI-ID-03 | Тот же job и новый job того же кандидата | Existing same-job/same-candidate guard не ослаблен |
| AI-ID-04 | COMMIT неизвестен перед отправкой | Ноль дополнительных POST до reconciliation |
| AI-ID-05 | Прерывание между COMMIT и сетью | Консервативный unknown; отсутствие второго POST |
| AI-ID-06 | Потеря ACK после отправки, таймаут, SIGTERM/SIGKILL | Unknown сохраняется после restart/generation change |
| AI-ID-07 | `reserved_usd=0, cost_usd=NULL` с выбранным провайдером | Не считать вызов бесплатным и не разрешать replay |
| AI-ID-08 | Orphan attempt без job/candidate lineage | Не реконструировать случайный fingerprint; ручная блокировка только по доказательству |
| AI-ID-09 | Provider idempotency отсутствует или operation ID неизвестен | Автоматического POST retry нет |
| AI-ID-10 | Достоверный receipt, успешный settlement, повторное использование результата | Reuse только при точном входе, scope и валидной схеме |
| AI-ID-11 | Падение фиксации settlement и поздний ответ прошлого owner | Ledger, lease и стоимость не перезаписываются устаревшим владельцем |
| AI-ID-12 | Независимые задания и exhausted budget | Нет лишней глобальной остановки; сохранены дневные/месячные ограничения |

**Приёмка реализации:** unit/source-oracle тесты для канонизации и полного состава входа; concurrency/crash/replay/rollback на **одноразовой MariaDB**; mock provider с подсчётом реально отправленных POST; проверка реального исполнения тестов в required CI на последнем SHA без `SKIP`. Отдельный PR для контракта/миграции, отдельный PR для runtime и отдельная operator acceptance с разрешения владельца. До этого задача не считается выполненной.
