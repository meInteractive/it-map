# GO-431: проект схемы consumer control и восстановления

Этот документ задаёт критерии реализации. Он не является миграцией, не разрешает
DDL в production и не подключает worker. Контракт переходов и ограничения runtime:
[GO-431-CONSUMER-FENCE.md](GO-431-CONSUMER-FENCE.md).

## Причина и границы

Добавление таблицы к текущей базе без обновления политики несовместимо с backup:
`backup.validateInventory` отклоняет неизвестные таблицы, а `dbschema.Preflight`
сравнивает метаданные с доверенной baseline. Успех `ValidateBaseline` не
подтверждает работоспособность backup. `schema-init` рассчитан на пустую базу;
его нельзя использовать как мигратор заполненной базы. Исходные v39 fixture и
исторические таблицы миграций не изменяются ради добавления control state.

## Предлагаемая структура

Одна таблица `go_consumer_control`, InnoDB, с единственной строкой `id=1`:

| Поле | Контракт |
| --- | --- |
| `id` | BIGINT, PK; только 1. |
| `generation` | VARCHAR(36), NOT NULL; в точности generation из `app_runtime_generation`. |
| `revision` | BIGINT, NOT NULL; положительный, начинается с 1, при смене режима увеличивается; overflow — отказ. |
| `mode` | VARCHAR(16), NOT NULL; только `legacy`, `draining`, `worker`. |
| `owner_digest` | VARBINARY(32), nullable; NULL без владельца, ровно 32 ненулевых байта при владельце. Credential не сохраняется. |
| `lease_until` | BIGINT, NOT NULL; Unix milliseconds по часам БД; 0 без владельца. |

Legacy: NULL и 0. Worker: digest и положительный lease. Draining может
сохранять прежний digest и lease, чтобы безопасно завершить начатую работу;
либо оба поля пусты, если владельца не было. Проверки приложения обязательны,
даже если CHECK поддерживается СУБД. Фактические DDL, collation, ограничения,
metadata и совместимость версий MariaDB должны быть зафиксированы и проверены
в отдельном implementation PR; табличное описание не доказывает их наличие.

## Версия и миграция

Нужна новая явно версионированная доверенная спецификация, отдельно от v39:
точные таблицы, колонки, типы, nullable, PK, индексы, проверки и InnoDB. Старый
v39 и новый вариант распознаются явно; неизвестная, неполная, смешанная или
изменённая структура — отказ. Наличие только имени таблицы не является
доказательством доверенной схемы. Версия должна указывать на проверенную
структуру, а не заменять её проверку.

До добавления таблицы проверить совместимость опубликованного backup/restore,
остановку старых потребителей и согласованные границы работ. Начальный singleton
создаётся в `legacy`, revision 1, без владельца, с generation, прочитанной под
блокировкой. Ошибка либо отсутствие generation — отказ. Повторный запуск
разрешён только при подтверждённой полной структуре и корректном singleton;
не переписывать существующее worker/draining-состояние как legacy.

DDL MariaDB может неявно завершать транзакции. Мигратор должен явно распознавать
промежуточные состояния после обрыва: только таблица без строки, строка без
подтверждённой версии, неожиданная структура и несоответствие generation.
Не объявлять весь процесс атомарным и не удалять или переинициализировать
неизвестное состояние автоматически. Для каждого допустимого промежуточного
состояния нужны проверенные idempotent действия либо безопасный отказ с
операторской процедурой. При неизвестном исходе commit сначала перечитать
фактическое состояние под lock.

## Backup и restore

Операционное состояние владельца не экспортируется как пользовательские данные:
credential и digest, lease и режим worker нельзя переносить в архив как право
возобновить работу. При этом экспорт обязан проверить точную доверенную схему
и не скрывать неизвестные таблицы или столбцы. Поддержка таблицы с binary digest
должна быть реализована отдельной политикой operational state, а не слепым
добавлением в v39 экспортируемые секции. Старые архивы остаются читаемыми.

При restore новой схемы сначала захватить generation lock, затем control row;
в одной транзакции с применением данных и сменой generation установить новую
случайную generation в обоих местах и сбросить режим в **draining**, revision 1,
owner NULL, lease 0. Draining сохраняет запрет запуска до подтверждённой
проверки активной работы и paid evidence; автоматическое включение legacy после
restore не допускается. Никакой импортированный digest не возрождается. Старая
схема остаётся поддерживаемой по прежнему контракту. Порядок блокировок и
отсутствие совместимых старых бинарников проверяются отдельно: старый код не
знает про draining. При rollback restore старые generation и состояние должны
остаться целыми; commit с неизвестным исходом требует повторного чтения.

## Обязательные доказательства до готовности

- Disposable MariaDB: чистая v39, корректное обновление, повторное выполнение,
  все промежуточные состояния после аварии, неожиданные таблицы/колонки/PK,
  неподдерживаемая engine/collation и неправильные значения singleton.
- Старый backup → новая схема и новая схема → backup → restore; исключение
  digest и token из архива, новая generation, draining и отказ старого token.
  Ошибка на неизвестной metadata остаётся fail-closed.
- Параллельный restore и Begin/claim/renew/drain: общий порядок блокировок,
  rollback, истечение lease и отсутствие stale write. Отдельно lost ACK и
  unknown-paid без повторного платного POST на синтетических данных.
- Версионная совместимость с v39 preflight, runtime и операторской процедурой;
  тест на повреждённую и частично применённую миграцию без удаления данных.
- Реальный cutover, DDL на production, старые процессы и paid ledger требуют
  отдельного операторского плана и разрешений. При неготовой схеме worker не
  запускается; экспериментальные модели в коде не гарантируют эксклюзивность.

## Кандидат marker v1

Для проверки промежуточных состояний предложена отдельная таблица
`go_consumer_schema_version`: `id BIGINT PRIMARY KEY`, `version BIGINT NOT NULL`,
`status VARCHAR(16) NOT NULL`, InnoDB, `utf8mb4_bin`. Доверенная metadata снята
с синтетической MariaDB 10.11 и хранится отдельно от v39. Допускается ровно
одна строка `id=1, version=1, status='complete'`; отсутствие, лишние строки,
неизвестная версия и любой другой статус — отказ. Marker не содержит owner,
lease или данные пользователя и не заменяет проверку всей metadata и singleton.

При будущей миграции marker должен записываться в одной транзакции с начальным
singleton после DDL; создание таблиц отдельно и может прерваться. Пустая таблица,
несовместимая metadata или несогласованная generation не исправляются наугад.
Порядок блокировок: generation → consumer → marker. Текущие диагностические
функции не создают marker и не проверяют совместимость backup/restore. До их
полной реализации старый экспорт и restore продолжают отклонять новые таблицы.
