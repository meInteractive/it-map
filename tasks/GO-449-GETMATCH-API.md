# GO-449 — Интеграция Getmatch через прямой JSON API

**Спринт:** 1.2 ([SPRINT-02.md](SPRINT-02.md))  
**Приоритет:** средний.  
**Статус:** [ ] — запланировано, не выполнено.  
**Дата постановки:** 24.11.2026.

## Цель

Добавить Getmatch как источник вакансий через нативный Go HTTP-адаптер с использованием существующего Worker и MariaDB-очереди. При подтверждённом допустимом прямом доступе не использовать Firecrawl, Apify или браузерную автоматизацию для этого источника. Стоимость прямых HTTP-запросов у посредников — нулевая; это не означает отсутствия затрат на сервер или штатный AI-конвейер.

## 1. Preflight: контракт и разрешённость

Обнаруженный сторонний адаптер: [sasaki-agent / getmatch.mjs](https://github.com/peachcardinal/sasaki-agent/blob/main/src/sources/getmatch.mjs). Это исследовательская зацепка, не официальная спецификация и не подтверждение доступности API на текущую дату. Не копировать сторонний код без проверки лицензии.

Предполагаемые запросы:

```http
GET https://getmatch.ru/api/offers?limit=2&offset=0
GET https://getmatch.ru/api/offers/31814
GET https://getmatch.ru/api/offers?limit=100&offset=0&sp=product_design
```

- Проверить условия использования, ограничения автоматизированного доступа и допустимость сбора. Официальный Public API ориентирован на ATS; возможность получения сторонних вакансий через него не подтверждена. При необходимости обратиться в поддержку Getmatch.
- После согласования внешней read-only проверки выполнить небольшое число HTTP GET из допустимого окружения, без записи в БД, без авторизации чужими данными и без обхода защит. Зафиксировать статус, Content-Type, схему, требуемые заголовки, пагинацию, порядок выдачи, фильтры, ограничения и обработку удалённых карточек.
- Проверить `limit`, `offset`, `sp`, `meta.total`, ID, даты, зарплаты, города, формат работы, наличие полного описания и грейда. Не считать поля или параметры гарантированными до проверки.
- Если API недоступен, требует неподтверждённого доступа, запрещает сбор или не обеспечивает надёжное получение данных, зафиксировать блокировку. Рассмотреть согласованный партнёрский API или разрешённый альтернативный источник отдельным решением.

## 2. Реализация после успешного preflight

- Изучить актуальные контракты адаптеров, источников, планировщика, GO-431 и pipeline. Использовать стандартный Go HTTP client с context, timeout, ограничением размера ответа, контролем частоты, ограниченной пагинацией и backoff с учётом Retry-After; не обходить 403/429/CAPTCHA. Не создавать параллельный планировщик.
- Добавить Getmatch в существующий каталог/настройки источников и ручной/регулярный запуск через действующий Worker. Предварительный интервал 30–60 минут и размер страницы до 100 — настраиваемые гипотезы, только в пределах подтверждённых лимитов. По умолчанию не активировать production-сбор.
- Получать страницы листинга, сохранять корректный checkpoint/курсор согласно действующим контрактам, использовать фильтры специализаций и географии при подтверждённой поддержке. При отсутствии устойчивой сортировки обеспечить ограниченное безопасное сканирование, не теряющее новые записи.
- Нормализовать ID, должность, работодателя, URL, зарплату и валюту, локацию/удалённость, дату публикации, полное описание и seniority по подтверждённой схеме. Возможные поля: `id`, `position`, `company.name`, `url`, `salary_display_from`, `salary_display_to`, `salary_currency`, `location_items`, `published_at`, `seniority`. Не выдумывать отсутствующие данные; URL формировать только по подтверждённому контракту.
- Дедупликация по паре источник/Getmatch ID с использованием существующих правил межисточниковой дедупликации. Детали получать для новых и при обоснованном обновлении изменившихся вакансий; повторные запуски не дублируют очередь, записи или платные AI-запросы. Использовать действующие leases, retry, generation/CAS и бюджетные fences.
- Направлять нормализованных кандидатов в существующие стадии отбора, классификации, извлечения и релевантности, включая действующие настройки JEV/AI; не менять правила для других источников. Не запускать платные AI-вызовы на этапе проверки.
- Интегрировать стандартную диагностику: число страниц/полученных кандидатов/новых/дублей/ошибок, время проверки, последний успешный запуск, причина отказа, следующий запуск; без чувствительных данных и фиктивных метрик. Ошибки схемы, пустой ответ и отказ сервера не выдавать за успешное завершение.

## 3. Приёмка

- [ ] Подтверждены доступность и разрешённость API, описаны схема, ограничения, доказательства и выбранный метод.
- [ ] Mock HTTP/синтетические fixtures: пагинация, повтор страницы, пустой список, отсутствующие поля, неверный JSON, timeout, 403/404/429/5xx, лимит запросов, отмена context и изменение вакансии.
- [ ] Повторный запуск, retry, конкуренция и рестарт Worker не порождают дублей и не теряют вакансии/курсор; новые и изменённые записи корректно проходят штатный pipeline.
- [ ] Источник и настройки совместимы с текущим UI/API и диагностикой; другие адаптеры, лимиты и бюджетные ограничения не ухудшены.
- [ ] Применимые gofmt, go vet, go test -race, сборка, MariaDB на изолированной БД и штатный PR CI пройдены; при изменении UI — применимые frontend/browser проверки.
- [ ] Независимая проверка Codex; production-включение, деплой Worker, реальные записи и платные вызовы только после отдельного явного разрешения владельца.
