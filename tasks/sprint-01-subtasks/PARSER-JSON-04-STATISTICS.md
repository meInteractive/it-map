# S11-DIAG-04 — JSON-кнопки в статистике P1/P2 и воронке вакансий

**Статус:** [ ] Часть A слита в PR #267: JSON-кнопки графика P1/P2 и воронки, полный ряд 30 дней и безопасные проекции. Часть B готовится в отдельной ветке: детализация текущих активных P2 без переписывания истории. Визуальная эксплуатационная приёмка ещё требуется. **Приоритет:** высокий, связано с GO-107/108. Серверные read-only Go endpoints уже существуют. Не путать с отдельной GO-436 об аномалии числа 61 за 07.11.2026: эта задача добавляет возможность диагностировать расхождение, но не объясняет и не исправляет расчёт автоматически.

У `ParserIssues.tsx` («Известные проблемы и задачи») разрешается отдельная кнопка для текущих проблем, но не дублирующая все 30 точек графика. - [ ] **S11-DIAG-04-05.** После реализации GO-107 сверить JSON с реальным Go/MariaDB reader и UI на одноразовых данных, в том числе восстановление истории, пустой период, одинаковые timestamps, 401/403, смена владельца, отсутствие замеров. Кнопка не должна сама создавать дневную запись; если GET имеет side effect, рассмотреть отдельный read-only snapshot.


### Разъяснение наблюдаемой аномалии и граница исторических данных

- **Входной пример для приёмки:** есть 2 наблюдаемых дня из 30; `p2Peak` двух дней равен 100 и 101. JSON и UI показывают `average.p2 = 100.5`, `observedDays = 2`, 28 пропущенных дней с `null`, а при отсутствии измерения текущего дня `todayPeak.p2 = null`. Это **среднее из двух дневных максимумов количества проблемных заданий**, **не число новых ошибок за день** и не оценка ежедневных 100 новых ошибок.
- **Проверить методику активных P2:** исходный JS `server/services/parser-issues.js` считает записи `scheduler_jobs` в статусах `failed/pending` в разрешённой области, исключая ожидаемые причины ожидания и более новые superseding jobs; блоки `verification/planned` и общая история `failed` не равны активной очереди. Для нового Go reader обязательно сверить семантику с реальной SQL-схемой и правилами GO-430.
- **Нельзя восстановить причины старых пиков из одной таблицы `parser_error_daily`:** она хранит `owner_name`, `day`, `p1_peak`, `p2_peak`, `first_sample_at`, `last_sample_at`, **не содержит breakdown по status/type/reason**. Для исторического breakdown вернуть `available:false`; при необходимости будущей детализации отдельно согласовать новый сбор и хранение с миграцией на disposable DB. Не выдавать текущий breakdown за причину исторической аномалии.
- Отдельное поле `sampleCount` не выводить, пока не реализован источник: наличие `first_sample_at`/`last_sample_at` **не доказывает число замеров за день**. Время последнего образца брать из `observedAt` соответствующего дня, не из момента нажатия кнопки.
- Нажатие на JSON-кнопку должно быть **read-only**. В старом JS `parserIssues()` выполнял `recordParserErrorSnapshot()`, поэтому не переиспользовать такой маршрут для экспорта без разделения чтения и записи. В новых Go API сначала обеспечить защищённый отдельный reader.

**Актуализация после PR #255/#257:** admin-only read-only маршруты `GET /api/scheduler/issues` и `GET /api/scheduler/funnel` реализованы в Go. Историческая детализация недоступна: в parser_error_daily сохраняются только дневные пики. ### Отчёт части B (до приёмки)

- **Ветка:** `codex/S11-DIAG-04-p2-breakdown`. PR и последний SHA уточнить после CI.
- **Источник данных:** существующий `IssuesRepository.collect` в Go, read-only RepeatableRead. При расчёте текущего P2 учитываются все подходящие задания, даже после ограничения списка 120 записями. Ожидаемое `pending`, восстановленные `scan_source`, более новые superseding jobs и `verification/planned` не входят в число активных P2.
- **Экспорт:** полный `totalActiveP2`; разбивка по `status/type/sourceId/reasonCode` (максимум 30 категорий каждого измерения + сумма `remaining` при переполнении), последние 10 заданий по серверной сортировке, псевдонимизированные `jobId`; `truncated/sampleLimited/groupTruncated` и флаги недоступности исторической разбивки. Секреты, сообщения, payload, имена организаций/вакансий в экспорт не включаются.
- **Тесты:** Go unit на >120 активных заданий, 10 последних, причины/статусы, приватность и переполнение категорий; Node/schema на разрешённые поля и лимиты, старые HTTP/React/MariaDB CI должны пройти. Live-стенд и фактические цифры пока не проверены.
- **Ограничения:** это текущий срез, не историческая расшифровка пиков; метрики GO-436 и реальные исправления парсера вне PR. Не отмечать чекбоксы закрытыми до эксплуатационной сверки.
