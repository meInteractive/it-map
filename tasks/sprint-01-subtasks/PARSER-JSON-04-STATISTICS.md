**Статус:** [ ] Запланировано. **Приоритет:** высокий, привязано к **GO-107 и GO-108 спринта 1.1**. Не создавать новый backend раньше обязательных Go endpoints; кнопки можно реализовать в соответствующих PR после готовности безопасных DTO.

## GO-107 — «Ошибки за 30 дней»

- [ ] **S11-DIAG-04-01.** В `frontend/features/settings/ParserIssues.tsx` / `ParserErrorHistory.tsx` добавить одну кнопку «Копировать JSON» для **всей секции диагностики** и при необходимости отдельную для только дневной истории, не дублируя одну и ту же информацию.
- [ ] **S11-DIAG-04-02.** `checkedAt`, текущие `activeCounts.p1/p2`, `historicalFailed` (строго обозначить как исторический count), `sampleLimited`, `limit`, сгруппированные текущие P1/P2/P3 проблемы: `id`, `priority`, `status`, `target`, `observedAt`; **без сырого текста ошибки** и потенциально приватных полей `jobs[].message`.
- [ ] **S11-DIAG-04-03.** `history`: все **30 дневных агрегатов** `day`, `p1Peak`, `p2Peak`, `lastSampleAt`, `observedDays`, `averages`, `timezone`. Отсутствие снимка — `null`, не `0`; текущий день может быть неполным. Если `GET /api/scheduler/issues` не готов/ошибка БД — `available:false`, а не `p1=0`.
- [ ] **S11-DIAG-04-04.** Если требуется список затронутых заданий, **10 самых свежих** по времени, с безопасным `jobId`, `status`, `reasonCode` и без `message`, имени/названия вакансии по умолчанию. Не выводить список задач проверки как фактически наблюдавшиеся ошибки.
- [ ] **S11-DIAG-04-05.** После реализации GO-107 сверить JSON с реальным Go/MariaDB reader и UI на одноразовых данных, в том числе восстановление истории, пустой период, одинаковые timestamps, 401/403, смена владельца, отсутствие замеров. Кнопка не должна сама создавать дневную запись; если GET имеет side effect, рассмотреть отдельный read-only snapshot.
