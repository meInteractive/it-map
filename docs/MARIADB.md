# Целевая MariaDB it-map: схема, миграция и эксплуатация

**Новый отдельный документ.** Исторический `docs/DATABASE.md` описывает исходную SQLite/D1 и **не изменён**. Эта страница описывает *предназначенную для Go* MariaDB и то, что можно проверить по приватному прямому D1-дампу от 23.10.2026 (в публичном Git дампа нет).

## 1. Текущее и целевое состояние

- GPT Sites сейчас использует Cloudflare D1 (SQLite). Старый сервис пишет туда независимо от Go; схема/описания: [DATABASE.md](DATABASE.md), `db/schema.ts`, `server/generated/backup-schema.json`.
- План для Go: MariaDB **10.11+ на том же сервере**, локальное соединение `127.0.0.1:3306`, разные базы и пользователи для staging и production.
- В Go уже есть `internal/storage/store.go` (`database/sql`, DSN, pool, транзакции), `baseline.go`/`baseline.json` (ожидаемая схема) и `mysql_driver.go` за build tag `mariadb`. Наличие кода **не равно** успешному тесту на MariaDB: серверные интеграционные проверки ещё не подтверждены. Статус `go.sum` см. в разделе 11.

## 2. Проверенная исходная структура

Приватный архив `it-map-mariadb-2026-10-23(1).zip` содержал `it-map-mariadb.sql`, `validation.json`, `schema-changes.json`, конвертер и README. Согласно отчёту его создателя, согласованный снимок D1 сделан **23.10.2026 12:36:05 МСК** и пробный импорт успешно проверен на MariaDB **10.11.14**: **72 таблицы, 32 183 строки, 604 исходных столбца**, все значения исходных строк совпали; **50 внешних ключей и 22 триггера** в целевой схеме. Два невидимых вычисляемых служебных столбца добавлены для семантики ограничений SQLite. В `internal/storage/baseline.json` ожидается **606 столбцов** суммарно. Это результаты проверки *дампа*, а не подтверждение работы Go с живой БД.

## 3. Отличия от D1/SQLite

- SQLite `INTEGER` → MariaDB `BIGINT`, `REAL` → `DOUBLE`; основное `TEXT` → `LONGTEXT` с `utf8mb4_nopad_bin` для сохранения регистра, Unicode и значимых пробелов.
- Текстовые индексируемые идентификаторы получили `VARCHAR(255)`; для префиксных/хеш-индексов и уникальности учтены ограничения MariaDB.
- 2 виртуальных невидимых столбца (`scheduler_jobs._d1_active_scan`, `vacancy_roles._d1_ascii_nocase_name`), ограничения CHECK/триггеры/индексы эмулируют специфичное SQLite-поведение.
- Перевод бизнес-SQL требует явной замены `INSERT OR IGNORE`, `ON CONFLICT`, `RETURNING`, `PRAGMA`, JSON-функций, D1 `batch()` и подхода к транзакциям/блокировкам. Не переносить SQL механически.
- Существующая MariaDB-схема **не во всех местах** гарантирует уникальность `company_vacancies.url`, `company_identity` и состояний пользователя так же, как предполагал старый код. До согласованной миграции Go-операции должны выявлять дубликаты/неоднозначности и безопасно отказывать. Данные не «исправлять» автоматически.

## 4. Импорт в изолированный staging

Использовать приватно хранимый полный SQL, **не** приложение JSON backup v39. Создать пустую staging-БД и отдельного пользователя с минимальными правами; не загружать архив в публичный Git или обычные журналы CI. Импорт SQL через `mariadb --default-character-set=utf8mb4 --max-allowed-packet=128M ... < private.sql` выполнить **только после утверждения**, без `--force` и без перезаписи существующей базы. После импорта: версии сервера, количество таблиц/строк, nullable/type/FK/index/trigger, генераторы идентификаторов, контрольные суммы значений, SQL read-only preflight в `db/`.

Для Go: заполнить **локально** `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_ENABLED=true` и собрать `go build -tags mariadb ./cmd/itmap`. До реальной проверки драйвера и DSN не утверждать, что Go-маршруты работают с MariaDB.

## 5. Миграции и правила изменений

- Исходный SQL и `docs/DATABASE.md` неизменны. Новые схемные изменения на MariaDB — отдельные **последовательно пронумерованные миграции**, с описанием причины/совместимости/проверки; место и инструмент запуска ещё требуют решения (не добавлять самовольно новый миграционный фреймворк).
- Действующие данные не удалять, не менять массово и не накатывать DDL в production без согласования. Требуется бэкап до миграции, dry-run на staging, тест отката/совместимости, отдельный PR.
- Тестировать повторный запуск миграций, конкурентные транзакции, `SELECT ... FOR UPDATE`, idempotency, соответствие FK и семантику времени/`NULL`. Минимизировать блокировки; запретить сетевые вызовы под SQL-транзакциями.
- Миграции не запускаются автоматически при обычном старте сервиса и не должны влиять на действующую D1.

## 6. Бэкап, восстановление и cutover

- SQL-снимок MariaDB и JSON-бэкап приложения — **разные продукты**. Формат JSON v39 задокументирован в `docs/BACKUP_FORMAT.md`; его нельзя считать полной заменой прямого снимка системных таблиц/очередей/платёжных журналов.
- Определить частоту, шифрование, доступ, удержание и отдельное место хранения SQL-бэкапов. Перед выпуском выполнить восстановление в **новую пустую** базу, сверить таблицы/данные/FK и проверить логин, CRUD, криптографию интеграций, парсер и очередь.
- Последний D1-снимок уже устаревает, поскольку GPT Sites продолжает запись. При cutover нужен новый прямой снимок D1 после остановки записи/старых automation, полное сопоставление и только потом переключение домена/Go-диспетчера.
- После первых Go-записей простой откат DNS на прежнюю D1 небезопасен без обратной синхронизации. Основной безопасный откат — предыдущая совместимая Go-версия с той же MariaDB; подробности в `PLANS.md`.

## 7. Непроверенное и открытые вопросы

MariaDB-driver pinned в `go.mod`, но `go.sum` ещё не проверен; реальные интеграционные тесты и проверка `SHOW CREATE TABLE` не запускались в этом аудите. Не утверждены миграционный инструмент/права/бэкап-политика, финальная D1→MariaDB синхронизация и RPO/RTO. Эти условия — обязательные gates спринта 1.1.

## 8. Усиленная проверка GO-005/GO-007 (24.10.2026)

В рабочей ветке `codex/GO-005-staging-hardening` добавлены две отдельные проверки для **одноразовой** MariaDB 10.11 в GitHub Actions:

- read-only `ValidateBaseline` со строгим запретом тихо пропускать тест при `ITMAP_REQUIRE_MARIADB_INTEGRATION=1`;
- синтетическая запись в транзакции с `ROLLBACK`, проверка возврата `RowsAffected=1` на неизменившийся `UPDATE` (`clientFoundRows=true`) и откат после ошибки. Write-тест **отказывается** работать вне БД с точным именем `itmap_ci` или при наличии исходных строк в используемой тестовой таблице.

CI также сверяет **на самой базе** 50 внешних ключей и 22 триггера, затем запускает Go-процесс с подключением к read-only CI-пользователю и выполняет HTTP-smoke. `go.sum` публикуется в CI как проверяемый краткоживущий артефакт; его ещё надо включить в Git отдельным PR. Эту подготовку нельзя считать доказательством успешного исполнения CI, реального staging или миграции пользовательских данных.

## 9. Проверка доступности API с авторизацией (v15)

На синтетической MariaDB в GitHub CI теперь дополнительно включён `AUTH_ENABLED=true` с одноразовыми **непроизводственными** значениями и проверяется цепочка `401 → POST /auth (303) → GET /api/session (200)` с cookie. Внешние staging URL в этом режиме запрещены: проверка выполняется только на `127.0.0.1`/`localhost`. Это тест backend-сессии, **не** браузерная проверка `Secure` cookie и HTTPS-прокси.

CI обязан получить зависимости по сети и проверить, что `go.sum` уже отслеживается Git и не изменился после `go mod tidy`. Пока файл отсутствует, приемка GO-005/007 запрещена, даже если остальные тесты проходят. Первый сетевой запуск может сформировать `go.sum` как artifact; его нужно проверить и включить отдельным PR. Тест с реальной MariaDB и тестовый домен ещё не выполнялись в этой рабочей среде.

## 10. Совместимость кодировки соединения и MariaDB-столбцов (v16)

В процессе проверки GO-005 выявлена несовместимость **параметра соединения**, не схемы: `go-sql-driver/mysql` версии `v1.9.3` не содержит `utf8mb4_nopad_bin` среди поддерживаемых collation ID начального handshake (см. `collations.go` этой версии драйвера). Использование `collation=utf8mb4_nopad_bin` в DSN препятствовало бы подключению.

В `internal/storage/store.go` и CI DSN теперь указано `charset=utf8mb4`, `collation=utf8mb4_bin` (известное драйверу значение). **Сортировка существующих столбцов и таблиц `utf8mb4_nopad_bin` сохранена без DDL**: именно определение столбца управляет большинством сравнений с ним. Любые SQL-выражения, зависящие от collation строкового литерала или соединения, требуют отдельной проверки на реальной MariaDB.

В `TestMariaDBSchemaBaselineIntegration` добавлена read-only проверка `@@collation_connection = utf8mb4_bin` и `information_schema.COLUMNS` (`agency_identity.agency_name = utf8mb4_nopad_bin`). CI проверяет обе настройки после запуска настоящего драйвера. **Проверка пока не запускалась на MariaDB 10.11**: в текущем окружении не получен `go.sum`, нет MariaDB. GO-005/GO-007 остаются открытыми.

## 11. Зафиксированные суммы зависимостей и сетевой gate (v17)

`go.sum` добавлен в ветке `codex/GO-005-locked-dependencies-v17` для уже закреплённых в `go.mod` версий `github.com/go-sql-driver/mysql v1.9.3` и `filippo.io/edwards25519 v1.1.0`. Четыре значения `h1:` (модули и файлы `go.mod`) сверены между публичными Go-проектами (например, `github.com/digicert/ca-extension-mtc-playground` и `github.com/chenjia404/meshserver`). Это независимое сопоставление **опубликованных сумм**, а не локальная проверка скачанного содержимого.

CI теперь использует `go mod download`, `go mod verify`, `go mod tidy -diff` и `git diff --exit-code -- go.mod go.sum`, вместо `go mod tidy`, меняющего файл в процессе сборки. Любое несовпадение зависимостей приводит к ошибке. На изолированном runner с сетью Go проверяет соответствие загруженных архивов значениям `go.sum` и своей базе контрольных сумм. **Здесь сеть Go Modules недоступна, поэтому эта проверка и тесты `-tags mariadb` пока НЕ выполнялись.**

Ранее описанный в разделах 8–10 этап временного получения `go.sum` как CI-артефакта заменён отслеживаемым в Git файлом. По-прежнему требуются успешные результаты сетевого CI на disposable MariaDB 10.11, затем внешний staging-домен и проверка контрактов React. Ни GO-005, ни GO-007 ещё не закрыты.

## 12. Проверка идентичности ограничений в CI (GO-005, v18)

Проверки одних чисел `50 FOREIGN KEY` и `22 TRIGGER` недостаточно: ошибки импорта могут заменить один объект другим при сохранении общего количества. Для одноразовой схемы `itmap_ci` добавлен **публичный schema-only эталон** `internal/storage/schema-objects.json`: названия и таблицы 50 внешних ключей, названия/события/момент выполнения 22 триггеров. В нём нет строк БД и секретов.

`python3 scripts/check-ci-schema.py` сверяет этот эталон с `db/testdata/empty-schema.sql` без подключения к серверу. `TestMariaDBSchemaObjectsIntegration` при запуске с тегом `mariadb` сравнивает импортированные метаданные `information_schema` с эталоном и проверяет, что все 72 таблицы используют InnoDB. Тест выполняет **только SELECT**, но использует **синтетического CI-пользователя с правами тестовой записи**, поскольку просмотр метаданных триггеров может требовать дополнительных привилегий. Учетной записи Go-приложения права `TRIGGER` не выдаются. Тест отвергает подключение к базе, отличной от `itmap_ci`.

Это **усиление ещё не запущенного интеграционного gate**, а не подтверждение, что схема успешно импортировалась в MariaDB 10.11. В этой среде по-прежнему отсутствуют загруженные Go-модули и сервер MariaDB. GO-005/GO-007 открыты. Публичный эталон не является источником миграции: при утверждённой эволюции схемы его нужно обновлять осознанно вместе с миграцией и проверками.

## 13. Авторизованный Go → MariaDB smoke на синтетическом каталоге (v19)

После read-only проверки baseline, метаданных FK/trigger и транзакционного теста CI загружает **не приватный дамп**, а `db/testdata/smoke-catalog.sql` в одноразовую `itmap_ci`. Фикстура состоит только из записи `company_crm`, `company_identity` и `app_catalog` для вымышленного `CI Synthetic Employer` (ID=1). Защитный скрипт `scripts/check-ci-smoke-seed.py` проверяет допустимые SQL-команды и JSON, чтобы тест случайно не пополнился реальными данными.

Сервер запускается с синтетической учётной записью и **read-only** доступом к CI-базе. `scripts/staging-smoke.sh` проверяет анонимный 401, вход 303, сессию 200 и авторизованный `GET /api/companies/list`, ожидая HTTP 200, ровно одну компанию с именем и ID из фикстуры. Неуспешный SQL/API-запрос (в частности, 503) должен провалить gate: это проверено локальным тестовым HTTP-сервером в `scripts/test-staging-smoke.py`.

**Ограничения:** локальный тест не использует настоящий MariaDB; Go-драйвер и MariaDB на CI по-прежнему должны быть проверены отдельно. Фикстура импортируется **только после** тестов, требующих полностью пустой базы. Полный пользовательский дамп, внешний staging-домен и production не затрагивались.

## 14. Защита транзакционных тестов от подключения к чужой базе (v20)

Тест записи `TestMariaDBDisposableTransactionIntegration` **не должен подключаться** к произвольной MariaDB только на основании названия базы. Добавлена предварительная проверка разобранного DSN: `tcp(127.0.0.1:3306)`, база `itmap_ci`, пользователь `itmap_ci`. Перед запуском тестов GitHub Actions генерирует уникальный UUID поколения и сохраняет его в `app_runtime_generation` **только одноразовой CI-базы**. Для операций записи тест должен прочитать такое же значение из `ITMAP_TEST_DISPOSABLE_GENERATION`. Несовпадение, пустой или устаревший маркер блокируют тест до первой `INSERT`/`UPDATE`.

Маркер предназначен исключительно для CI и **не является** реализацией генерации/восстановления рабочих данных. Историческая схема, дамп и production не изменяются. Условие наличия именно одноразового окружения GitHub Actions остаётся обязательным: само имя базы или маркер не дают разрешения писать в рабочие данные. Проверка на реальном MariaDB-сервере пока не выполнена; GO-005 и GO-007 остаются открытыми.

## 16. Конкурентная блокировка поколения в disposable CI

PR #1 объединён в main: [run 40128620919](https://github.com/meInteractive/it-map/actions/runs/40128620919) для `75ec2df` реально подтвердил MariaDB 10.11 schema/rollback, бизнес-чтения после синтетического seed и авторизованный Go → MariaDB → API smoke. Старые ограничения сети/отсутствия живого CI в разделах выше относятся к прежним проверкам. Это всё ещё не тест согласованного пользовательского снимка и не внешний staging.

Следующая часть GO-005 — `TestMariaDBDisposableLockingIntegration`. Два заранее зарезервированных соединения с разными `CONNECTION_ID()` используют `REPEATABLE READ`. Первая транзакция блокирует существующую строку `app_runtime_generation(id=1)`, вторая пытается получить ту же блокировку. Проверяется именно MariaDB error 1205 (`innodb_lock_wait_timeout=1` только в сессии второго соединения), а не задержка получения соединения из Go pool или отмена общего context. После rollback обеих транзакций то же второе соединение снова получает блокировку; UUID поколения остаётся прежним.

Тест не выполняет INSERT/UPDATE/DELETE/DDL и не фиксирует изменение данных. Он ограничен одноразовой CI-базой: общий test-only helper проверяет разобранный DSN/loopback/user/schema до соединения и UUID текущего запуска до блокировки. Тот же helper используется прежним rollback-тестом, без ослабления guard. Тесты не запускаются параллельно и выполняются существующим полным storage-шагом до бизнес-фикстур. В обязательном CI-режиме отсутствие DSN/маркера — ошибка, в обычной локальной проверке без БД — явно обозначенный пропуск.

Проверки этой порции: vet (обычный и mariadb), race-тесты, tagged-сборка, статические source/schema/seed gates, smoke-script unit-test; затем обязательный live CI на SHA нового PR. Отрицательная локальная проверка требует, чтобы оба disposable-теста отвергали отсутствие DSN, неверный DSN/target или отсутствие UUID до обращения к БД, без пропусков. Полная GO-005 остаётся открытой: проверки миграции согласованного снимка и всех CRUD/конкурентных сценариев этим тестом не заменяются.
