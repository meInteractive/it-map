# GO-293 — ретроспективные пробелы HH: календарная модель и план проверки

**Статус:** модель проверяется синтетическими Go-тестами; реальный исторический охват не проверен. Текст — read-only методика, **не** разрешение на обращение к платному Actor, backfill, manual scan, retry, изменение расписания, SQL writes, restore или production SSH.

Связанные задачи: [Issue #293](https://github.com/meInteractive/it-map/issues/293), [#303](https://github.com/meInteractive/it-map/issues/303), [#323 GO-446](https://github.com/meInteractive/it-map/issues/323). Публичный [playbook](PARSER_DIAGNOSTICS_PLAYBOOK.md) содержит исходные определения. Перед любым реальным измерением нужны актуальные права и отдельное разрешение владельца на операторский read-only доступ.

## 1. Что доказано кодом, а что нет

- `hhDateWindow(now, 3)` задаёт **три предыдущих полных календарных дня по Москве**. День запуска не входит в окно. Например, сканирование 4 ноября 2026 года запросит 1–3 ноября.
- Если следующая проверка того же источника происходит **ровно через 7 дней**, её окно — 8–10 ноября. **4–7 ноября не охвачены** этими двумя фильтрами: это арифметический четырёхдневный пробел.
- При интервале **3 дня** предыдущие полные трёхдневные окна примыкают без пропуска; при интервале **1 день** они перекрываются. Тест `TestGO293SevenDayScheduleAndThreeDayWindowGaps` проверяет 1/3/7 дней также при переходе декабря в январь. `TestGO293HHWindowAtMoscowMidnight` фиксирует границу 21:00 UTC = 00:00 МСК.
- Это **модель двух полностью завершённых запусков, соответствующих ожидаемым настройкам**, не свидетельство реальных дат/запросов на сервере. Переход на ежедневную проверку снижает будущий календарный риск, но **не восстанавливает** старые пропуски сам по себе.
- Дата в `date_posted`, фактическая доступность HH-вакансии и дата первого импорта — разные события. HH/Actor может вернуть обновлённую старую вакансию **вне запрошенного окна**; код `hh_listing.go` учитывает такие записи отдельным диагностическим счётчиком, но не отбрасывает их только по этому признаку. Поэтому нельзя выводить количество реально потерянных карточек из четырёхдневного пробела.

## 2. Read-only доказательная лестница

1. **Установить границы:** точные даты, московский час, источник/настройки каждой исторической попытки, состояние версии приложения. Не экстраполировать нынешний `intervalDays=1` назад на прежние периоды и не доверять одной записи `next_run_at` как истории.
2. **Подтвердить выполненные scan:** только завершённые HH jobs с надёжной связью `scheduler_jobs` → `apify_runs` → provider run/dataset receipts и доказанными параметрами Actor. Старый сохранённый cursor без надёжной lineage из GO-446 относится к **unknown**, даже если в очереди виден `pending`. Повторный GET или одна оплаченная страница не означают, что весь скан завершился.
3. **Построить таблицу покрытия по каждому источнику:** `scanCompletedAtMSK`, `requestedDateFrom/To`, `effectiveInputVerified`, `finishedCursorVerified`, `state` и `coverageLevel` (`confirmed` / `partial` / `unknown`). Названия работодателей, исходные URL, закрытые ID, реальные cursor/run keys и provider payload **не публиковать в GitHub**.
4. **Сопоставить публикации и импорт** только после подтверждённого покрытия: кандидатские intake/первые успешные операции, `published_at` вакансии, `vacancy_import_operations.action/status`, `vacancy_id`. Считать отдельно **даты публикации**, даты поступления кандидата, первые уникальные `CREATE`, `update`, `unchanged` и повторы. Не считать 61 candidate stage event как 61 новую вакансию.
5. **Проверить альтернативы:** даты вне окна от обновлённых объявлений, отсутствие подходящих публикаций на HH, скрытие/период/роль/избранное в UI, задержка fulltext/AI, partial либо неудачная загрузка, неизменённые дубликаты. Отсутствие записи в нашей БД **не доказывает** её существование в HH.
6. **Подготовить только обезличенный итог:** число источников с `confirmed` покрытием, даты/периоды, число потенциально неохваченных календарных дней, `unknown`/partial отдельно, подтверждённые первые уникальные карточки и **неизвестное** число потенциально потерянных публикаций. Не публиковать строки провайдера, суммы/аккаунты или персональные сведения.

`vacancy_source_parsing.last_success_at` хранит дату **последнего подтверждённого полного** HH-обхода; `last_attempt_at`/partial не эквивалентны `success`. Один текущий `last_success_at` не восстанавливает историю нескольких недель. `GET /api/scheduler/hh-schedule` показывает нынешнее состояние и успешные источники за 24/48 часов, **не** полную ретроспективу.

## 3. Решение о восстановлении — отдельный этап

Если у конкретного периода подтвердился пробел покрытия, **до** любых операций сформировать сухой проект: какие источники, какие exact dates, есть ли доступная историческая выдача, доказуемая идентичность новых операций, стратегия дедупликации и бюджет/платное ограничение. Отдельно определить, как исключить повтор Actor с неизвестным settlement и что делать с истёкшим/неподтверждённым HH cursor. Только после явного разрешения владельца — контролируемый операторский план с rollback и мониторингом. Этот документ ничего не запускает.

## 4. Автоматизированная приёмка

`go test ./internal/parser -run 'TestGO293|TestHHDateWindow' -count=1`

Тесты полностью локальные, используют только синтетические часы, реальные функции расчёта окон и готовые даты. Не обращаются к БД/HH/Apify. Обязательны успешные required CI на точном commit PR; зелёный тест доказывает лишь календарную модель, а **не** число пропущенных вакансий в production.
