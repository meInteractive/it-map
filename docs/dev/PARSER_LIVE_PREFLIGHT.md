# GO-407: подготовка ограниченной проверки настоящего Apify

## Подтверждённые границы

Владелец подтвердил месячные лимиты: Apify — 5 USD, OpenRouter — 10 USD,
OpenAI — 10 USD. Разрешённый источник для проверки — работодатель
`https://hh.ru/employer/780654`. Текущий HH adapter преобразует ссылку на
работодателя в запрос поиска по тому же `employer_id`, до 100 результатов
на странице; при продолжении возможны последующие страницы и дополнительные Actor.

Сквозной mock на отдельной MariaDB проверен в GO-406. 3 ноября 2026
выполнена ограниченная проверка реальных провайдеров: одна вакансия импортирована
в изолированную staging-БД. Все 100 записей первой страницы сохранены как кандидаты; оставшаяся очередь AI не обработана.
При запуске использовать отдельную staging-БД, один явно разрешённый источник,
ручной сигнал, ограниченное число стадий и сохранение run ID и расходов;
автоматическое расписание и рабочие автоматизации не включать.

## Ключи и учёт расходов

В активной MariaDB нового Go-сайта обнаружены непустые зашифрованные записи
OpenAI, OpenRouter и бесплатного профиля Apify. Значения ключей не выводились.
Read-only проверка штатным Go codec выявила ошибку
расшифровки этих записей с текущим секретом процесса. После повторного
сохранения владельцем все три ключа проходят локальную расшифровку и проверку
формата, OpenRouter отмечен `connected`. Проверка токена Apify чтением аккаунта
и лимитов также прошла без запуска Actor. По поручению владельца ключи
переупакованы с отдельным секретом staging внутри сервера и проверены без вывода
значений. Планировщик и Apify staging выключены, дневной и месячный бюджеты
staging равны нулю. 3 ноября владелец сообщил, что месячный расход OpenAI
и OpenRouter равен нулю. Исходный синтетический HH-источник отключён;
указанный владельцем источник employer/780654 после проверки также выключен.

Синтетическая инициализация GO-406 не задала начальную revision планировщика,
из-за чего CAS отказывал при его выключении. В созданной staging-БД только
синтетическая запись с ожидаемым владельцем и отсутствующей revision дополнена
начальной revision 0; создание будущей фикстуры исправлено и защищено CI-тестом.

Месячные суммы относятся к каждому аккаунту провайдера, включая существующий
сайт и другие клиенты. Локальный журнал staging отражает только его операции;
общий месячный лимит планировщика не доказывает соблюдения отдельных лимитов
OpenRouter и OpenAI по всему аккаунту. Apify дополнительно учитывает данные
аккаунта провайдера и собственные резервы. Перед платным запуском необходимо
подтвердить текущий остаток и действующие ограничения непосредственно на каждом
аккаунте; если это невозможно подтвердить, запуск блокируется. Не переносить
реальные пользовательские данные и не использовать фиктивные расходы GO-406
как фактический остаток.

После разрешённого запуска проверить статус Actor, стоимость и ошибки, импорт,
API/SQL readback, повтор и восстановление. Не повторять неизвестный платный
запрос вслепую. Фиксировать только безопасные идентификаторы и результаты,
без ключей, персональных данных и содержимого пользовательских вакансий.

## Результат ограниченной проверки 3 ноября

Указанный источник дал один настоящий Actor `INSE1ZokUAyTj4kVV`,
`SUCCEEDED`; учтённая стоимость Actor — 0.1053954739 USD. Dataset содержит
100 записей, из которых прочитаны первые 10; оставшийся scan_source был
отложен. Один кандидат прошёл Jev, публичное получение подробностей, OpenAI
извлечение, назначение роли, импорт и оценку; девять отклонены. Временная
тестовая роль была расширена до любых профессий, чтобы проверить цепочку,
а не оценивать качество боевой классификации. В staging сохранена вакансия ID 2;
SQL и штатный репозиторий подтвердили поля, HTTP `GET /api/vacancies/2` вернул
200 и непустое описание. Исходный request ID повторён: `reused=true`,
новых задач, вакансий и Actor не появилось. Процесс остановлен.

Учтённые затраты AI-стадий в журнале staging: классификация 0.000256 USD,
извлечение 0.001199 USD, назначение роли 0.000271 USD, relevance 0.000126 USD;
это локальные учётные значения, а не подтверждение расходов всего аккаунта.
Максимум staging на время проверки был 0.30 USD, на каждый Actor — 0.25 USD.
После проверки планировщик и Apify выключены, бюджеты обнулены, источник
выключен. Это меняет revision: отложенный cursor с прежней конфигурацией
нельзя продолжать вслепую. Это ограничение проверено отдельно при восстановлении ниже.

## Восстановление после выключения

После изменения revision выполнен ручной запуск с кодом PR #217: первая
порция продолжения увеличила число кандидатов с 10 до 20, затем оставшиеся
восемь порций довели его до 100. Журнал по-прежнему содержит один настоящий
Actor (и один синтетический из GO-406); новые Actor не запускались. Проверены
run ID восстановления `3b23c1951d593eb1744c71c05a4466f89e6a68ac2d278e83c57971ee850970be`
и итоговой порции `53e4fff8bb20d141bed4d96a229ff55237c5f9e8032e2a0822ecb9b53416a9d3`.
В SQL курсор показывает offset 100 из 100 и `Done=false`: финальное завершение
страницы и переход к следующей не выполнялись, поскольку следующий Actor не
входил в ограниченную проверку. AI-обработка новых 90 кандидатов отложена.
Для чтения страницы приоритет ожидающего scan был временно повышен в staging,
приоритеты ожидающих классификаций снижены; затем планировщик и Apify выключены,
бюджеты обнулены, источник выключен. Проверка на staging использовала операторский процесс; отдельный пользовательский
маршрут и действие очереди подготовлены в PR #218 и требуют CI/слияния.

## Проверка ручного маршрута

На staging вызван `POST /api/scheduler/resume` для сохранённого HH-задания.
Первый ответ — HTTP 200, обработана одна порция; повтор того же requestId
вернул HTTP 200 и `reused=true`. Курсор подтвердил завершение первой страницы
и переход к странице 1 с offset 0. Количество кандидатов — 100, ожидающих
классификаций — 90; денежный журнал не получил новую запись Actor. После
проверки источник и Apify выключены, бюджеты планировщика равны нулю.
