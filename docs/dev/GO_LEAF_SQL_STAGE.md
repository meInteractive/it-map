# GO-366: SQL-стадия конечных ролей

`LeafStageStore` читает только актуальные входы принадлежащей пользователю стадии: кандидат с подходящим текущим root match, валидный полный снимок, успешное структурирование по текущим настройкам, дерево ролей и настройки role prompt/model. Конечные роли берутся только из потомков актуальных совпавших корневых направлений. Список, input/tree/prompt/config hashes воспроизводят source; до отправки и сохранения состояние повторно проверяется.

Результат используется из кэша лишь при совпадении полного input hash и корректном наборе разрешённых ID. Два последних результата с одинаковым временем не выбираются наугад. Новый вызов требует candidate lease, один из двух общих LLM slots и existing Attempt billing. Неизвестный исход удерживает резерв и блокировки, а отсроченный ответ с изменившимся деревом не сохраняется. Результат или безопасное сообщение об ошибке и receipt/job фиксируются в одной транзакции.

Actual `analyzeVacancyLeafRoles` выполняется на synthetic SQLite с mock OpenAI/JEV. Четыре source сценария сравниваются с Go и disposable MariaDB по хешам, решениям, модели, цене и ошибкам; дополнительный required gate проверяет кэш, отсутствие структурирования, бюджет, неизвестный исход, изменение дерева, два занятых слота и очистку незапущенных попыток. Source root ordering также проверяется на разных sort_order. Только положительный CI считается SQL-приёмкой: локальный guard намеренно пропускает БД.

Это внутренняя стадия, без автоматического создания следующего задания или включения worker. Импорт, релевантность, источники, scheduler tick и переход от одной стадии к другой остаются открытыми. Реальная БД, провайдеры и сервер не затрагиваются.
