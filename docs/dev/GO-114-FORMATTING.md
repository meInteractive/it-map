# GO-114 — единое форматирование поддерживаемого React/TypeScript

**Срез: 09.11.2026.** Форматтер: Prettier **3.6.2**, закреплён в `package.json` и `package-lock.json`. Параметры — [`.prettierrc.json`](../../.prettierrc.json). Полная механическая база стиля создана отдельным коммитом [`ce381c0`](https://github.com/meInteractive/it-map/commit/ce381c0c7b9beb17caa655ac77d6f970fcb30362) внутри [PR #298](https://github.com/meInteractive/it-map/pull/298).

## Проверяемая область

Команды и обязательный CI работают **на всей поддерживаемой области**, независимо от git diff и даты создания файла:

- `frontend/**/*.ts`, `frontend/**/*.tsx`;
- `shared/**/*.ts`, `shared/**/*.tsx`, `shared/**/*.mts`, включая `.d.mts`;
- `web/main.tsx`, `vite.web.config.ts`.

Исторические Next/Cloudflare/D1 и JS-эталоны (`server/`, `app/`, `build/`, `db/`), `server/generated/`, vendor и сгенерированные артефакты **не форматируются**. Массовое форматирование за пределами этой области требует самостоятельной задачи и согласования.

## Команды

```bash
npm ci --no-audit --no-fund
npm run format                 # механически отформатировать всю поддерживаемую область
npm run format:check           # проверить всю область, ничего не переписывая
node scripts/test-web-format-guard.mjs
npm run typecheck:web
npm run build:web
```

Проверка в `web` job [`go-ci.yml`](../../.github/workflows/go-ci.yml) расположена после `npm ci`, перед проверкой типов и сборкой Vite. Любой неформатированный поддерживаемый файл приводит к ненулевому статусу. Отдельный синтетический guard `scripts/test-web-format-guard.mjs` временно создаёт неформатированный `frontend/__go114_format_sentinel__.ts`, подтверждает **отказ** Prettier, затем успешное форматирование, успешную повторную проверку и идемпотентность второго прогона. Временный файл удаляется даже при ошибке.

## Механический diff и приёмка

- Prettier применён отдельно от функциональных правок ко всем 81 исходным файлам поддерживаемой области с фактическими изменениями; исходный Go/React-API, SQL/DDL и runtime не менялись.
- При ручном ревью проверить механический характер diff, существующие комментарии, отсутствие перемен семантики и изменения только перечисленных файлов.
- На **последнем** PR SHA проверить `npm ci`, отрицательный guard, полную `format:check`, `typecheck:web`, Vite, реальные браузерные тесты desktop/mobile и все три обязательных GitHub Actions workflow. До полного зелёного CI нельзя объявлять PR готовым к merge.
- Успех CI на синтетической базе **не означает** live smoke, разрешение на production или переход к GO-115 без отдельно согласованной работы.
