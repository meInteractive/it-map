## 1. Назначение и инженерная задача

IT Map объединяет карту и каталог IT-работодателей, CRM поиска работы, вакансии и отклики, задачи и автоматизированный сбор/обработку вакансий. Система использует языковые модели для классификации, извлечения структурированных данных, назначения специализаций и оценки релевантности.

Проект возник как приложение на GPT Sites (React, JavaScript/Cloudflare Worker, D1). Текущая инженерная задача — **перенести продукт на самостоятельно развёртываемый Go-бекенд и MariaDB без потери пользовательских сценариев и данных**. При этом нужно сохранить совместимость API, устойчивость фоновых заданий, ограничения расходов на внешние сервисы и возможность безопасного отката.

Вторая цель проекта — отработать управляемую разработку с Codex: декомпозиция требований, архитектурные решения, небольшие PR, автоматические проверки и приёмка человеком. ИИ ускоряет реализацию, но сам факт генерации кода не считается доказательством работоспособности.

### Принципы

- **Модульный монолит вместо преждевременных микросервисов.** Один Go-процесс, явные предметные модули и ограниченное число инфраструктурных зависимостей.
- **Совместимость прежде переписывания интерфейсов.** Существующий React-клиент и семантика HTTP/JSON используются как контракт миграции.
- **MariaDB как источник истины для новой реализации.** Долговременные состояния, конкурентные операции, задания и учёт расходов фиксируются в БД.
- **Безопасный отказ вместо ложного успеха.** Не перенесённый API и неготовый release gate явно возвращают ошибку.
- **Проверяемые изменения.** Утверждения о готовности опираются на конкретный код, тесты и результаты CI/staging, а не на план работ.

## 2. Системная схема

```text
                  Браузер / PWA
              React + TypeScript + Vite
                         |
                    HTTP / JSON
                         |
                Go (net/http, ServeMux)
                   auth / middleware
                         |
   +---------------------+-----------------------+
   |                     |                       |
Каталог и CRM       Вакансии, отклики        Настройки, backup,
компании, каналы       и задачи              диагностика и API
   |                     |                       |
   +---------------------+-----------------------+
                         |
                   database/sql
                         |
                  MariaDB 10.11+
              данные, leases, receipts,
              задания, настройки и бюджет
                         ^
                         |
             Go-парсер / планировщик
           (явный или разрешённый запуск)
                         |
          +--------------+---------------+
          |                              |
    HH.ru / Apify                   ИИ-провайдеры
    (листинг, текст)              OpenAI / OpenRouter
          |                              |
          +------> обработка вакансий <--+

  Отдельно: работающая исходная версия на GPT Sites
       Cloudflare Worker + D1 + Site Automation
       Не использует Go/MariaDB и не синхронизируется
       с новой реализацией автоматически.
```

Схема отражает реализованный основной маршрут **для HH.ru в Go**, а не обещание эквивалентной поддержки всех исторических источников. Очередь на RabbitMQ и transactional outbox пока запланированы, но не внедрены.

**Почему именно так:** Go использует стандартные `net/http` и `database/sql` без Gin и тяжёлой ORM. Внешние зависимости и интерфейсы вводятся там, где нужно подменять провайдеров, проверять контракт или разграничивать ответственность. Основные архитектурные альтернативы и принятые ограничения описаны в [журнале решений](DECISIONS.md).

### HTTP и фронтенд

Точка входа интерфейса — `web/main.tsx`, основная композиция — `frontend/Application.tsx`, API-клиент и кэш — `frontend/api/client.ts`. SPA собирается командой `npm run build:web` через `vite.web.config.ts`, затем файлы раздаёт сам Go-сервер (`internal/httpapi/static.go`). Постоянно работающий Node.js-сервер **не нужен**.

Клиент обращается к относительным `/api/...`. `cmd/itmap/main.go` собирает зависимости, а `httpapi.Options` передаёт в HTTP-слой реализованные сервисы. В `internal/httpapi/handler.go` видны маршруты каталога, вакансий, откликов, задач, каналов, профиля, настроек ИИ/Apify, планировщика и резервных копий. Защищённые маршруты проверяют сессию. Отсутствующие части legacy API не имитируют успешный ответ: они возвращают `503 backend_not_migrated` (или отказ авторизации, если требуется вход).

Клиент поддерживает навигацию и браузерную историю, несколько типов панелей, сохранение состояния форм и PWA. Регрессионные проверки покрывают также мобильное взаимодействие. При этом отдельные сложные React-компоненты и правила инвалидирования кэша ещё требуют упрощения.

## 4. Обработка вакансий: реальный Go-конвейер

В отличие от ранней архитектурной документации, в `internal/parser` теперь существуют **рабочий `Worker.Cycle`, диспетчер `worker_dispatch.go` и исполнители стадий**. Обработка запускается явно или через отдельно разрешённый серверный механизм; конструктор worker сам по себе не запускает фоновый таймер.

```text
HH-источник
   |
scan_source             список через Apify, набор кандидатов, курсор
   |
classify_title          предварительная классификация
   |
fetch_full_text         полный текст / публичный HH или провайдер
   |
extract_vacancy         структурированное извлечение
   |
assign_roles            назначение специализаций
   |
import_vacancy          атомарная запись вакансии и связей
   |
score_relevance         персональная оценка релевантности
   |
MariaDB -> Go API -> React
```

Не каждый кандидат проходит все стадии: в зависимости от результатов классификации, наличия данных и правил отбора он может быть отклонён, отложен или отправлен на повторную проверку. После импорта вакансия доступна существующему API.

**Устойчивость и стоимость операций:**

- Состояния задания, владельца цикла, попыток и курсоров находятся в MariaDB. Повтор запуска контролируется идентификаторами и проверкой актуальности состояния.
- `Worker.Cycle` ограничивает длительность и число заданий за вызов. `worker_dispatch.go` связывает тип задания с исполнителем.
- Для внешних платных операций используются резервы бюджета, состояния `starting/running/uncertain`, журнал запусков Apify и проверка версий настроек. Неопределённый результат платного POST нельзя автоматически считать бесплатным и слепо повторять.
- Конвейер защищается от устаревших `generation/revision`, повторных импортов и гонок при изменении данных. Проверки включают конкурентные операции и восстановление после сбоев.
- Автоматическое исполнение в обычном Go-сервере по умолчанию выключено; отдельный управляющий путь подключается флагом `ITMAP_PARSER_EXECUTION_ENABLED=1` и требует разрешённой конфигурации.

Подробности инвариантов: [жизненный цикл заданий](../../internal/parser/JOBS.md), [расходы и ограничения](../../internal/parser/BILLING.md) и [миграция парсера](GO_PARSER_MIGRATION.md).

### Историческое подтверждение на 3 ноября 2026 года

1. **Синтетические проверки:** на одноразовых MariaDB в CI и на изолированном staging проверены SQL, HTTP, обработка заданий, повторные запросы, сохранение состояния и сквозной путь с mock-провайдерами.
2. **Ограниченный запуск с настоящими провайдерами:** одна реальная вакансия прошла получение данных, ИИ-стадии, запись в MariaDB и чтение через `GET /api/vacancies/{id}`. Повтор того же запроса не создал дополнительный Actor или вакансию.
3. **Восстановление набора HH:** после остановки и изменения настроек сохранённый dataset был дочитан до 100 кандидатов **без нового запуска платного Actor**. При этом обработка оставшихся 90 кандидатов, финальное закрытие страницы и переход к следующей странице были отложены.

Эта контрольная точка 03.11 доказывает **ограниченную сквозную работоспособность и конкретный сценарий восстановления**; последующие наблюдения 09.11 рассмотрены отдельно в [матрице](GO-119-ARCHITECTURE-EVIDENCE.md). Она не доказывает качество массовой классификации, не полную автоматизацию всех источников и не готовность к непрерывной эксплуатации. Проверки проводились с явным разрешением и ограничением расходов; по завершении исполнение и источники были выключены. Отчёты: [GO-406: staging](PARSER_STAGING_PREFLIGHT.md) и [GO-407: реальный ограниченный запуск](PARSER_LIVE_PREFLIGHT.md).

## 5. Хранилище и миграция данных

**Рабочая исходная версия** продолжает использовать Cloudflare D1/SQLite и Site Automation. Её код находится в `server/`, `build/`, `db/`; он сохраняется как эталон API и поведения, но не является Node-бекендом новой Go-системы. Функции Firecrawl, rabota.ru и Google Calendar из исторической реализации нельзя автоматически считать перенесёнными в Go только потому, что они присутствуют в репозитории.

**Целевая система** использует MariaDB **10.11+**. Проверяемый baseline содержит 72 таблицы и 606 столбцов; дополнительно контролируются ключи, связи, триггеры и совместимость SQL. `internal/storage` настраивает пул подключений и проверяет наличие поддерживаемой схемы. Приложение не выполняет произвольный DDL при каждом старте.

Для первоначальной подготовки схемы предусмотрена отдельная команда `itmap schema-init`, работающая с доверенным определением схемы. Несовместимая MariaDB 10.3.32 намеренно отвергается, а не обходится удалением ограничений целостности. SQL-операции используют параметризованные запросы, транзакции, оптимистические версии/CAS и, в отдельных подтверждённых случаях, ограниченный retry после deadlock.

**Резервные копии не являются только планом.** В `internal/backup` реализованы экспорт, проверка и восстановление формата v39, а также совместимость с историческими форматами через `internal/v39` и соответствующие тесты. Временная MariaDB CI проверяет сценарии восстановления, ошибки, конкурентность и сохранение целостности. Это **не равно** проведённой процедуре восстановления рабочей пользовательской базы.

Автоматической синхронизации D1 и MariaDB нет. Финальная миграция пользовательских данных, заморозка старых записей, допустимые RPO/RTO и процедура возврата после cutover ещё требуют отдельной приёмки.

Документация: [историческая D1](../user/DATABASE.md), [целевая MariaDB](MARIADB.md), [политика совместимости с MariaDB 10.3](MARIADB_103_COMPATIBILITY.md), [форматы резервных копий](../user/BACKUP_FORMAT.md).

## 6. Качество, тестирование и CI/CD

Проверки расположены рядом с Go-пакетами (`*_test.go`), в `scripts/test-*.mjs` и `tests/browser/`. В проекте несколько уровней доказательств:

| Уровень | Что подтверждает | Где запускается |
| --- | --- | --- |
| Go unit и race | Логика, ошибки и конкурентные операции | `go test -race ./...`, GitHub Actions |
| Контракт с исходной системой | Совместимость маршрутов, сериализации и бизнес-правил со старым JavaScript/SQLite | Тесты `legacyinterop` и source-oracle |
| Интеграция MariaDB | Транзакции, ограничения, CAS, восстановление и сквозные SQL/HTTP-сценарии | Временная MariaDB 10.11 в CI, тесты с build tags |
| Браузерные тесты | Реальные React-компоненты и пользовательские действия в Chromium | Playwright: desktop и mobile; изолированные фикстуры и smoke с Go/MariaDB |
| Безопасность публичного кода | Отсутствие запрещённых данных в публичном снимке и доступной истории Git | Проверки `scripts/check-public-repo.py` и CI |
| Серверный staging | Работу конкретной сборки и ограниченных сценариев вне CI | Отдельная БД/процесс, ручная контролируемая приёмка |

Основные workflow: [Go, web и безопасность](../../.github/workflows/go-ci.yml), [MariaDB и браузерная приёмка](../../.github/workflows/mariadb-staging-ci.yml), [проверка отказа на MariaDB 10.3](../../.github/workflows/mariadb-103-ci.yml) и [публикация сборок](../../.github/workflows/publish.yml). Фактический статус конкретной версии следует смотреть в [GitHub Actions](https://github.com/meInteractive/it-map/actions), а не выводить из самого наличия тестов.

Playwright проверяет как изолированные React-сценарии с синтетическим HTTP, так и реальные запросы к Go/MariaDB в CI. Для части интеграционных проверок обязательны ограничения на внешнюю сеть и тестовые данные. Успешный `npm run build:web` **не заменяет** отдельную проверку TypeScript: на указанном коммите команда `npm run typecheck` существует, но не подключена в качестве обязательного шага PR-CI.

Для выпуска существуют сборка релиза по проверенному SHA, отдельный механизм доставки, smoke и откат. Workflow `publish.yml` включается только при разрешающем `ITMAP_DEPLOY_ENABLED`. Наличие release-механизма не является разрешением на переключение рабочего домена или импорт реальных данных.

## 7. Безопасность и граница production

- Go HTTP использует защищённые сессии с подписанными cookie, проверки доступа и ограничение размеров отдельных запросов; выставляются защитные HTTP-заголовки. Перенос механизма авторизации сохраняет совместимость с историческими учётными записями, но не является новой системой управления пользователями.
- Подключение к MariaDB предусмотрено через loopback. Секреты не должны попадать в публичные файлы, логи, результаты тестов и PR.
- Тестовые БД и платные вызовы отделены от старой работающей версии. Сборка или запуск теста не включает автоматически прежние Site Automation и новый worker.
- `GET /health/live` сообщает о работающем процессе. `GET /health/ready` **намеренно возвращает HTTP 503**, в том числе при исправной MariaDB: release gate остаётся закрыт с причиной `business_api_not_migrated`.
- `APP_ENV=production` сейчас явно отвергается конфигурацией. Успешная публикация на staging, тестовый импорт и зелёный CI не отменяют этот запрет.

## 8. Что остаётся незавершённым

**Функциональная совместимость.** Должны быть приняты оставшиеся сценарии исходного продукта, включая интеграции, отсутствующие в Go, и финальный перенос данных. Google Calendar OAuth/синхронизация пока относятся к старой реализации.

**Эксплуатация.** Требуются финальный release gate, проверенный cutover/rollback и сценарии восстановления на согласованном снимке. Полный парсер с реальными источниками, расписанием и обработкой всей очереди не принят как непрерывный production-процесс.

**Следующие архитектурные этапы.** RabbitMQ, transactional outbox и распределённые исполнители предусмотрены следующим спринтом, но **не реализованы**. Их следует вводить только при наличии эксплуатационного обоснования, не ломая сохранённые в MariaDB задания.

**Сопровождаемость.** В контрольной точке 3 ноября 2026 года в планах остаются улучшение читаемости React, обязательная проверка TypeScript/форматирования, упрощение крупных CI-сценариев и ревью. Это технический долг, а не скрытое свойство готового продукта.
