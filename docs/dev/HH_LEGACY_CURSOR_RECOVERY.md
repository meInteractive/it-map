# HH: безопасный предпроверочный протокол восстановления legacy-курсора

**Статус:** инженерный план read-only проверки, не инструкция на самостоятельный запуск восстановления. Контекст — обезличенные агрегаты 10.11.2026. Актуальность подтверждать по текущему `main`, выпущенному Go и новым снимкам. Владелец не разрешал менять production-данные, принудительно запускать платный Actor или мигрировать схему.

## 1. Почему проблема требует отдельного протокола

- После GO-442/443 одно старое задание `scan_source` HH от 04.11.2026 остаётся `pending` с `unverifiedLineage=1`, `unverifiedLegacyFilters=1`; другие 27 из 30 источников имели подтверждённый полный обход за 48 часов на снимке 10.11.2026 19:30 UTC.
- `internal/parser/hh_queue_guard.go`: `hhCursorProof` не принимает старые cursor/filter/lineage, даже если сохранённый Dataset существует. `claimEligible` с `VerifiedHHOnly` не выбирает этот scan в автоматическом цикле.
- `internal/parser/scheduled_sources.go`: `scheduleHH` исключает новый scan для той же компании при существующем `pending/running`. Поэтому ожидание следующего 15-минутного сигнала само по себе не восстанавливает источник.
- `internal/parser/job_actions.go`: общий административный `retry/cancel` **не проверяет** оплаченный Apify ledger, Run ID, Dataset и происхождение курсора. Эти действия могут изменить планирование и не являются проверенной процедурой восстановления.
- `internal/parser/cycle_resume.go`: есть *отдельная* адресная процедура продолжения уже оплаченного HH — для сохранённого Dataset либо существующего Actor. Она использует `ResumePreviousDataset` или `DenyActorStarts`. Она всё равно требует проверки соответствия конкретному job и оплаченной операции; автоматический режим не должен использовать её без оператора.

## 2. Минимальный read-only preflight — выполнение только уполномоченным оператором

1. Подтвердить, что CI и `Publish native main` на merge-коммите GO-443 завершились успешно. Обновить страницу и получить новый **безопасный** `parser_hh_schedule`, проверив наличие всех шести `unverifiedLegacyVersion/Lineage/Moscow/Date/Title/Roles` (отсутствие поля не равно нулю). Определить, какие флаги пересекаются.
2. В действующем поколении MariaDB выбрать **ровно одно** старое `pending` задание HH, сверить связь с соответствующим `vacancy_discovery_runs` по `go399:<job-id>` и с текущим `vacancy_source_parsing` (company, source revision, включённость). Не выгружать их ID, URL или JSON в публичный Git/issue/PR.
3. Только чтением локально проверить поля cursor: `Version`, `LineageVersion`, `MoscowFilter`, `DateFilterApplied`, `TitleQuery`, `ProfessionalRoles`, `Operation`, `PreviousOperation`, `Page`, `Offset`, `Done`, `RunID`, `DatasetID`, `Metadata`, `CandidateIDs`. Сохранять исходный JSON неизменённым; не дополнять старое `LineageVersion` задним числом.
4. Проверить `apify_runs` **по точной identity сохранённой операции и старого Actor input** (см. `apifyruns.HHOperationIdentity`, `listing:go399:<job-id>:<page>`). При наличии `PreviousOperation` или уже пройденных страниц проверить и относящиеся к ним записи. Идентичность `operation_key` чувствительна к параметрам; совпадение компании само по себе недостаточно.
5. Для каждого связанного ledger receipt локально сверить `state`, наличие Run ID, Dataset ID, `charged_usd`, резерв и связь с сохранённым cursor. Отдельно осмотреть соответствующие `scheduler_attempts`, историю импортов кандидатов и возможные partial результаты. Отсутствие найденной строки **не доказывает**, что оплаченного POST не было: identity могла измениться, а неизвестный сетевой исход не исключён.
6. Не запускать Apify GET/POST для preflight. Если требуется связь с реальным Actor или корректировка неопределённого денежного резерва, сначала согласовать отдельный операторский этап с ограничениями и проверкой журналов провайдера. Данные провайдера не копировать в публичный репозиторий.

## 3. Матрица решений после read-only проверки

| Состояние | Что допустимо обсуждать | Что запрещено делать автоматически |
|---|---|---|
| Сохранены Run ID, Dataset ID, Metadata и ledger identity подтверждена | Отдельное однократное продолжение **известного** Dataset с проверенным режимом `DenyActorStarts`/resume, оценкой пригодности lineage и кандидатов | Подменять lineage/вход Actor, повторять POST, считать legacy-кандидатов подтверждёнными |
| Ledger содержит Run ID, но cursor/Dataset ещё не завершён | Контролируемое GET-only reconcile по существующей записи после проверки идентичности и права | Новый POST, отмена ради «очистки очереди» без дальнейшего плана |
| Ledger `starting/uncertain` или отсутствует Run ID | Ручная сверка с провайдером и журналом, отдельно оцениваемый recovery | Повторный старт; списание резерва как нуля |
| Не найден точный ключ операции / cursor неоднозначен | Считать исход неопределённым, уточнить историю страниц, предыдущую operation и attempts | Делать вывод, что Actor не запускался; сбрасывать данные |
| Доказано отсутствие оплаченной операции и безопасная отмена отдельно согласована | Пошаговый операторский `cancel`/перепланирование после backup, проверки dedupe, сроков и мониторинга | Генерировать новый `retry`/targeted Actor без отдельного бюджета и разрешения |

**Особенность scheduleHH:** после `cancelled`/failed dedupe-key прежнего периода планировщик может обновить `next_run_at` на следующий ежедневный срок и оставить `last_result='partial'`, а не немедленно создать новый scan. Не обещать немедленный повтор после отмены. Переход на другие интервалы или исторический backfill (старое окно 7 дней vs текущее 3 дня) требует отдельного решения.

## 4. Критерии безопасного решения

- Один конкретный pending сопоставлен со своими cursor, текущим источником, ledger и попытками; источники доказательств указаны, но не опубликованы.
- Есть однозначная оценка: **GET-only continue**, **manual provider reconciliation**, **operator-approved cancel/reschedule** либо **blocked/unknown**. При недостатке свидетельств допустимый результат — `blocked/unknown`.
- Доказано, что новый платный POST не появится без отдельного явно разрешённого запуска, и что не теряются кандидаты, статус оплаты или неизвестный резерв.
- До любого production write требуется резервная копия, план отмены/отката, явное разрешение владельца, проверка после операции и запись обезличенного результата в handoff. Текущий документ **не является таким разрешением**.

## 5. После восстановления

Сверять по двум последующим безопасным снимкам: `pendingHHScans`, `unverifiedLineage`, `successfulLast24h/48h`, `last_result`, бюджет provider/confirmed vs unknown/read reserves и число опубликованных **уникальных** вакансий. Успешный GET или окончание Actor не равны полному `last_success_at` источника, равно как сканирование не гарантирует новую вакансию.
