## 7. Следующий блок: свидетельство метаданных consumer schema

Подготовлена отдельная проверка `dbschema.CheckConsumerOverlay`: она проверяет
полную неизменённую baseline и точные metadata кандидатной таблицы consumer,
отклоняя неизвестные объекты и изменённые колонки/индексы. Это не миграция,
не проверка singleton или migration marker и не разрешение backup/restore.
Политика backup по-прежнему отклоняет новую таблицу до отдельной версии и тестов.

В изолированном локальном контейнере MariaDB 10.11 без сети загружена только
синтетическая baseline и кандидатная таблица: точная metadata совпала;
неизвестный столбец и отдельная неизвестная таблица отклонены. Добавлен
обязательный сценарий disposable CI. Не считать локальный снимок сертификатом
совместимости всех версий или подтверждением схемы production.

В этот же блок добавлена read-only `GuardSingleton`: под блокировкой generation
проверяются ровно одна строка id=1, согласованная generation, корректные
revision/mode/digest/lease. Отсутствие или повреждение ведёт к отказу, исправления
данных нет. В CI добавлены проверки несовместимых строк и конкурирующего
соединения. Проверка состояния не доказывает migration marker или доверенную
метадату; обе проверки необходимо связывать в будущей защищённой процедуре.

## Candidate preflight схемы consumer

`internal/consumerpreflight.CheckCandidate` диагностически проверяет baseline и
candidate overlay и singleton с generation на одном соединении и в транзакции.
Он использует общий advisory lock с offline schema-init и restore и повторяет
проверки после получения блокировок строк. Результат действует только во время
проверки: migration marker, пригодность backup/restore и разрешение запуска
worker не подтверждаются; произвольный DDL вне протокола не блокируется. В
runtime и production-команды проверка не подключена, изменения данных не делает.
Интеграционные сценарии запускаются только в одноразовой MariaDB GitHub CI.

Следующий диагностический шаг добавляет `CheckBaseline`: точная исходная схема
и generation проверяются под теми же advisory и row locks, что и candidate.
Обе проверки отвергают чужую схему; session с выключенным autocommit, активной
транзакцией либо оставленным advisory lock исключается из пула. Это по-прежнему
снимок, а не проверка marker, миграция, проверка backup или разрешение worker.
В disposable CI добавлены проверки различения схем и очистки сессий; отдельно
локально использовалась изолированная MariaDB с синтетической baseline.

Следующий блок устраняет риск удержания общего advisory lock соединением из
пула при schema-init и restore: обе процедуры отвергают загрязнённую сессию,
ранее захваченную той же сессией блокировку и исключают соединение при
неизвестном ответе GET_LOCK. В disposable CI добавлены сценарии ошибочного
состояния и потери ответа после реального захвата; локально они дополнительно
проверялись на отдельной MariaDB без сети с синтетической базой. Это не
добавляет поддержку consumer в backup/restore и не выполняет её миграцию.

## Транзакционный сброс consumer при restore

`consumercontrol.ResetForRestore` внутри переданной транзакции блокирует
существующие generation и singleton, создаёт новую случайную generation и
переводит consumer в draining с revision 1, без digest и lease. Ошибка требует
полного rollback; неизвестный исход commit требует повторной проверки. Код не
подключён к существующему restore: вызывающему ещё необходимо подтвердить
схему и migration marker, удерживать advisory lock, исключить старые бинарники
и применить данные архива в той же транзакции. CI-сценарий проверяет rollback,
ошибку между записями, блокировку generation и старого владельца. Локально
отдельный синтетический сценарий выполнен в MariaDB без сети.

## Экспериментальный экспорт candidate-схемы

`backup.Repository.ExportConsumerCandidateForEvaluation` под общей advisory
блокировкой и row locks дважды проверяет полную candidate metadata и singleton,
затем выдаёт v39-архив без operational state consumer. Обычный `Export` по-прежнему
отклоняет эту таблицу; новый путь не подключён к API и не проверяет migration
marker. Поэтому результат не является разрешением миграции или подтверждением
restore. Локальная изолированная MariaDB с синтетическими данными проверила
валидность v39, исключение digest, отказ при изменённой схеме и занятой блокировке.
Disposable CI дополнительно сравнивает содержимое с baseline export и проверяет
ошибочные состояния; полный сквозной restore новой схемы остаётся отдельной задачей.

## Экспериментальный restore candidate-схемы

В сборке с отдельным тегом `consumerevaluation` доступен только для оценки
`RestoreConsumerCandidateForEvaluation`: обычная сборка не включает точку входа.
Она проверяет exact metadata и singleton до counter DDL и повторно под locks,
затем восстанавливает v39-данные и сбрасывает consumer в draining в той же
транзакции. Неизвестный исход commit требует отдельной повторной проверки.
Локальный изолированный MariaDB-тест прошёл старый v39 → candidate → v39 →
candidate; CI дополнительно проверяет откат при ошибке после SQL обновления.
Marker, отключение старых бинарников и операторская приёмка пока отсутствуют:
это не разрешение production restore, миграции или запуска worker.
