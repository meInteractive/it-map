## 4. GO-438 — ближайшая самостоятельная миграция «Направления отбора»

**Где:** «Настройки → Парсинг вакансий → Источники и правила → Направления отбора». На 08.11 вместо ролей показано `backend_not_migrated` и кнопка **«Открыть промты обработки»**. Интерфейс — `frontend/features/settings/Classification.tsx`: `ParsingSettings` передаёт блок в `Scheduler.roles`, `ParsingRole` использует `PUT /api/classification/roles/:roleId` и ожидает обновления статуса; вкладка общих «Промты» содержит `ClassificationPrompts` и `PUT /api/classification/prompts/:roleId`. `GET /api/classification/settings` используется **в обоих местах**.

**Эталон:** `docs/user/API.md` → «Классификация по корневым ролям»; `server/repositories/classification-prompts.js` (`readClassificationSettings`, `saveClassificationEnabled`, `saveClassificationPrompt`, `activeClassificationRoles`); `server/repositories/vacancy-roles.js`; `internal/httpapi/handler.go`; фактические `vacancy_roles`, `vacancy_role_classification` MariaDB. Legacy возвращает `maxLength=10000`, `roles[{roleId,name,markdown,revision,updatedAt,enabled,defaultMarkdown,descendants:[{id,path}]}]`. Только корневые роли редактируемы, дети показываются списком. `enabled` и промт — **общие**, не личные; active roots = enabled с непустым Markdown.

**Существенная деталь:** legacy GET `readClassificationSettings` при необходимости создаёт стандартные промты по immutable stable-key и обновляет **только прежний неизменённый стандарт**. Не копировать наивно side effects старого D1 GET в Go: выяснить текущее существование записей и действующую стратегию idempotent seed/миграции; не перезаписывать ручные промты, в том числе **намеренно пустые**. Параметр `revision` защищает от гонок и потери правок. Не понижать требования к Unicode или к авторизации.

**Минимальные этапы:** (A) инвентаризация Go/schema и legacy контрактов, read-only admin GET; (B) проверенный PUT `enabled` + CAS; (C) PUT промта + CAS/лимит + согласованная реакция UI; (D) synthetic unit/HTTP/Go MariaDB 10.11 + негативные проверки + CI. Если API связи с существующим Go классификатором не готово, задокументировать границу: **настройки можно сделать отдельно от запуска модели**.

**Acceptance:**
- Администратор видит все корневые роли, имя, `enabled`, наличие промта, дочерние пути; при отсутствии ролей — нормальное пустое состояние, не `backend_not_migrated`.
- Включение/выключение и редактирование промта сохраняются, старый `revision` даёт `409`, отсутствие/дочерняя роль защищены. Повторное чтение сохраняет настройки. Ни один обычный GET не изменяет пользовательские промты.
- `401` без сессии, `403` не-администратору/чужому Origin, `405` неподдерживаемому методу, строгая JSON/Unicode-валидация; не утекать SQL error, сырые ключи или чужие данные.
- Не переносить одновременно `POST /api/classification/test` и не вызывать платные модели. Приёмка браузера отдельно, после обязательных CI.

См. полную формулировку **GO-438** в `tasks/SPRINT-01.md`.

## 5. GO-434 → GO-433: расходы и стоимость результата

### GO-434. Аудит, сделать первым

**Старт:** [Issue #273](https://github.com/meInteractive/it-map/issues/273), `tasks/SPRINT-01.md` → GO-434. `apify_runs` и операции Actor, `scheduler_attempts/runs/jobs`, AI/LLM ledger OpenRouter/JEV/OpenAI, `firecrawl_usage_events`, `vacancy_classification_attempts`, `vacancy_raw_snapshots`, `vacancy_extractions`, `vacancy_role_results`, `vacancy_import_operations`. **Названия ориентировочные, перед SQL проверить реальную схему**. Идентичность «оплаченное событие» не равна «попытка HTTP», «строка Dataset», «кандидат», «основная вакансия», «успешный job».

**Важные кейсы:**
1. Один подтверждённо оплаченный Apify Actor и несколько receipts/кандидатов — расход один, не умножать на кандидатов.
2. Два источника/публикации одной вакансии — одна основная карточка.
3. Повторные JEV/LLM после timeout/unknown ACK — разделить оплаченный повтор, повтор чтения и непризнанный резерв; не объявлять `unknown` нулём.
4. Пустой scan, отрицательная классификация и failure с подтверждённым списанием тоже входят в стоимость обработки.
5. Firecrawl может возвращать **кредиты**, денежная цена зависит от плана и периода; не склеивать числа USD и credits.
6. Поздний импорт старой когорты, незавершённые операции, неполный lineage: вывести `unallocated`/неизвестно и сохранить сверку с исходными журналами.

**Deliverables:** матрица `provider → paid operation ID → ledger → stage → candidate/vacancy`, различия confirmed/reserved/unknown, схема безопасных SELECT-only агрегаций, синтетические tests на MariaDB, документ в `docs/dev/` с известными пределами наблюдаемости. **Никаких реальных финансовых цифр в публичном Git**. Отчёт не считается аудитом живых счетов без отдельной read-only сверки.

### GO-433. KPI после GO-434 и GO-436

**Знаменатель:** уникальные **впервые созданные** основные вакансии, атрибутируемые выбранной **когорте** запусков, не `daily.published` и не `scheduler_runs.succeeded`. ## 8. Задачи, которым сначала нужен проектный документ, а не код

### GO-435 — персональная рекомендательная система

`tasks/SPRINT-02.md` уже содержит подробные пожелания пользователя. Цель: одна вакансия имеет отдельную релевантность **для каждого кандидата**, базовый сигнал резюме + положительные карьерные пожелания + негативные исключения + история **не более 10 заголовков вакансий с откликами** и **10 заголовков скрытых вакансий** данного кандидата. Старт — не collaborative filtering между пользователями. Не утекать данными между кандидатами. Исследовать действующие `company_vacancy_user_state`, `vacancy_relevance_profile_state`, `score_relevance`, API и `GO-120` (Markdown поле пожеланий и существующий промпт). Холодный старт/нет навыков/противоречивые сигналы/жёсткие запреты/снятые скрытия/несколько резюме — отдельные случаи. Администратор регулирует веса, версия весов/резюме/пожеланий/истории/промпта влияет на cache invalidation; не принимать месячный TTL без сравнения с дешёвым SQL и изменениями действий.

**Codex вправе подготовить RFC**, 2–3 формулы, synthetic golden cases и схему cache/score с оценкой стоимости. **Реализация и DB migrations запрещены до явного утверждения формулы, UX, разделения «хочу/не хочу», правил жёстких исключений, 10+10 событий, диапазонов и режима пересчёта.** GO-120 не дублировать. Промпт нельзя автоматически переписывать.

### GO-431 — supervised Go Worker

Перед проектированием проверить полноту GO-430 (есть PR #252 и профили `launch/reconcile/pipeline`). Потребность: отделить редкие потенциально платные запуски новых HH Actor от частого безопасного `GET/reconcile Dataset` и от исполнения стадий кандидатов. Цель — непрерывный/короткий bounded-poll worker с `context`, graceful SIGTERM, backoff, bounded concurrency, MariaDB leases/CAS/generation/owner fencing, сохранением `unknown ACK`, без дублирующего платного POST. RabbitMQ не нужен в 1.1. Старый hourly timer и новый worker одновременно на одной рабочей очереди запускать нельзя.

**Codex вправе сделать RFC/изоляцию будущих mock-тестов**, эксплуатационный план запуска/rollback, таблицу race/crash/lease-loss и latency budget. **Нельзя** переподключать рабочие systemd timers, выкатывать worker, менять rate limits/budgets или начинать платные Actor без отдельного допуска на cutover. Зависимость от подтверждения GO-430 обязательна.

## 9. Правила выполнения, отчётов и приёмки

- Перед **каждым** PR сверить актуальный `main`, существующие open PR и тестовые данные; независимые задачи не смешивать. Время пользователя тратить только на решения, которые нельзя обоснованно принять автоматически (права/доступ, бюджет, UX-формула, live cutover).
- Код и CI: документировать точный head SHA, PR, проверенные команды, все обязательные CI по **точному SHA**, failing тест до исправления, после — regression. Для Go — `go test ./...`, точечные tagged Go/MariaDB acceptance **только в disposable среде**; для web — унаследованные tests, `npm run build:web`, `node --check public/service-worker.js`, `npm run typecheck` после GO-113. Не скрывать ошибки через `--unhandled-rejections=warn` или редактирование тестовых ожиданий без диагноза.
- Новые задачи и отчёты по спринтам вести в `tasks/` и `tasks/sprint-01-subtasks/`; **не отмечать незавершённые чекбоксы выполненными**. Для скоупа около 10 пунктов принят один PR с отчётом (PR, SHA, ID, CI, ограничения) в файле пачки; отдельные независимые GO-задачи — отдельные небольшие PR. Merge делает пользователь.
- Никаких реальных ключей, Bearer/Cookie, SSH адресов, серверных IP, дампов, внутренних URL, резюме и персональных вакансий в публичный Git, PR, fixtures или handoff. Внешние Apify/Firecrawl/JEV/OpenAI вызовы могут тратить деньги; на стадии тестов только mock. Production SQL/DDL, изменение очереди, live timers, обновление данных и привязки — **только по отдельному явному разрешению владельца**.
- Готовность к **приёмке** = CI + проверяемые артефакты/контракты + необходимые разрешённые staging/browser наблюдения. Если не хватает доступа, честно написать «автоматическая часть готова; live не подтверждён», не пытаться обходить ограничения.
