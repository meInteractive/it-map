## Новые проверки этой порции

`TestMariaDBAIStageSIGKILLRecoveryDisposable`:
- Родитель создаёт синтетическую задачу в disposable MariaDB.
- Отдельный дочерний процесс начинает настоящий AI-stage через
  `AIStageExecutor` и `Attempt.Run`, но provider mock не вызывает HTTP.
- Дочерний процесс сообщает только фиксированный маркер после
  устойчивого резерва, затем родитель делает реальный `SIGKILL` без cleanup.
- Проверяется retained reserve, `cost_usd=NULL`, running job/attempt,
  recovery после истечения lease и нулевое число вторых POST.
- Ни реальные провайдеры, ни production schema/data не используются.

`TestMariaDBAIGenerationRotationBlocksPaidReplayDisposable`:
- Mock возвращает потерянное подтверждение после возможной отправки,
  оставляя unknown-paid attempt.
- Run/job восстанавливаются, затем **только в одноразовой CI БД**
  меняется generation singleton с обязательным восстановлением.
- Новый job с другим ID не должен обходить исторический AI fence:
  `ErrHistoricalAIUnresolved`, количество POST не увеличивается,
  старый резерв и `cost_usd=NULL` сохраняются.

Обе новые проверки включены как обязательные parent tests в
`mariadb-staging-ci.yml`. Общие CI, security и отсутствие `SKIP`
должны проверяться на **точном SHA PR** перед merge.

## Границы доказательств

Проверка SIGKILL происходит во время synthetic POST, а не после
успешного ответа/финальной фиксации; этот случай остаётся частью
оставшейся fault-injection матрицы. Изолированная MariaDB проверяет
реальное поведение SQL owner/recovery, но не подтверждает состояние
production. Не изменять production-БД, не очищать резервы, не повторять
платные запросы и не запускать старый HTTP consumer параллельно worker.

Следующее после успешного CI — при необходимости отдельные проверки
SIGTERM/grace shutdown после ответа и меж-job idempotency с одинаковым
входом, а также read-only сверка диагностик в реальном окружении только
с разрешения владельца и без раскрытия приватных данных.
