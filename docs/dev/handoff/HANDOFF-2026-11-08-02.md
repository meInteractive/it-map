### Что при этом НЕ готово и почему

- **Платные OpenAI письма ещё не разрешены в Go**: нужен отдельный durable ledger для ручных вызовов с budget/reserve/settle/unknown ACK, корректным учётом возможной оплаты и защитой от повторов при сетевом сбое; нельзя просто убрать `ErrPaidBilling` или передать `nil` billing. Это следующая отдельная часть GO-018/GO-017, а не ошибка текущего бесплатного контура.
- Нет доказанной **live browser + live provider** приёмки; тесты только synthetic/mock. После ручного merge и разрешённого staging проверить сценарии: пустое письмо автоматически создаётся; готовое не регенерируется; «Создать» меняет только личный текст; две вкладки одного пользователя; два разных пользователя; отсутствие промта/резюме/описания; недоступная модель; сброс сессии/refresh; error/heartbeat/done; сохранение без утечки в общую вакансию. **Не запускать платную модель для smoke.**
- Legacy сохраняет богатые семантики retries/leases/cost и 15-минутного ожидания; Go сейчас ограничивает ожидание занятого lease двумя минутами. Это **разница поведения, требующая отдельной проверки/решения**, а не доказанная полная parity. Не менять таймауты без оценки серверных ресурсов и UI.
- Новая реализация не даёт автоматического разрешения на production и не означает, что вся GO-018 (включая оценку релевантности) завершена.

## 5. Что делать **сразу после писем**: статистика GO-436

**Исходный симптом:** на графике за **07.11.2026** показано «Опубликовано: 61», пользователь сомневается в числе реальных новых вакансий. **Смысл метрики уже установлен** из `internal/parser/funnel.go` и подтверждён синтетическим тестом; **причина конкретной производственной цифры 61 НЕ подтверждена**.

- `daily.published` — число *кандидатов вакансий* с **первой** успешной `vacancy_import_operations` (`create`/`update`/`unchanged`) в выбранные московские сутки, а не количество впервые созданных уникальных `company_vacancies`.
- Повторная операция того же кандидата не даёт +1, но множество кандидатов может связываться с одной основной вакансией. `cohort.created/linked` группируется по времени первоначального получения кандидата, поэтому с дневной метрикой напрямую не совпадает. `scheduler_runs.succeeded` тоже не равен новым карточкам.
- Синтетический тест с 61 первым импортом, 2 основными вакансиями, распределением 1/20/40 создано/обновлено/без изменения **не является записью из production**. Не цитировать эти доли как факт.
- Безопасный следующий шаг: с **явного согласия пользователя** получить admin-only read-only результат `GET /api/scheduler/funnel?sourceId=all&parser=all` либо присланный им **отредактированный/обезличенный JSON** кнопки диагностики; сравнить `checkedAt`, фильтры, `daily[2026-11-07]`, `totals`, `cohort`; затем повторно GET, чтобы исключить устаревший UI cache.
- При отдельном разрешённом read-only SQL сопоставить события первого успешного импорта с **различными** основными `main_vacancy_id`, первым `create` и фактическим созданием карточки. Проверить timestamp formats перед SQL: для московского дня 07.11 UTC-границы `2026-11-06T21:00:00Z` (вкл.) → `2026-11-07T21:00:00Z` (искл.) верны **только при нормализованных UTC timestamps**, не для смешанных форматов. В [GO-436-FUNNEL-RECONCILIATION.md](../GO-436-FUNNEL-RECONCILIATION.md) есть точный план и пример SELECT.
- Затем согласовать **названия показателей** и/или раздельные ряды графика: *первые успешные импорты кандидатов*, *новые уникальные вакансии*, *обновления*. Не менять график/данные без подтверждения семантики и real snapshot. Возможно, потребуется маленький PR только на терминологию/визуализацию после фактов.
- Для дальнейшей статистики 30 дней не восстанавливать отсутствующие historical samples нулями; учитывать московские календарные сутки, неполный текущий день, `observedDays`, дубли измерений и отсутствие данных/сбоев отдельно. Прежние работы GO-107/108 и S11-DIAG уже предоставляют наблюдаемость, но live не принят.

## 8. Правила PR/CI, безопасность и что в Git **не** записано

- Одна самостоятельная проверяемая часть на PR, ветка от актуального `main` либо **stacked** от предыдущего PR; никакого auto-merge/прямого push в `main`. После merge stacked PR retarget на актуальный `main`, повторная проверка diff/CI.
- Для Go: `go test ./...`, `go vet ./...`, `go test -race ./...`, соответствующие tagged MariaDB tests в **disposable** CI. Для web: `npm run build:web`, унаследованные тесты; при изменениях `public/service-worker.js` также `node --check`. Не применять `--unhandled-rejections=warn` и не ослаблять тесты без диагноза.
- Для `docs/user/` соблюдать `docs/user/manifest.json`, changelog, `server/generated/documentation.json` и документационный CI; не редактировать generated JSON вручную без верификации штатного генератора.
- **Не публиковать в Git** приватные operational details, резюме/карьерные предпочтения конкретных лиц, имена/данные из рабочих карточек вакансий, закрытые URL, серверные логины, ключи и адреса, реальные provider account balance, cookies, raw JSON/SQL с персональными строками. Истинные значения runtime и разрешения на действия обсуждаются **только в пользовательском чате**.
- Handoff с временной меткой — информационный снимок. Если он расходится с новейшим кодом/CI, проверенный `main` и GitHub имеют приоритет.
