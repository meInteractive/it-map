## 3. Реализовано в #518–519: BATCH-05/B, DELETE вакансии

Риск: существующий `DELETE /api/vacancies/{id}` для linked-вакансии — **двухэтапный**. Первый вызов архивирует; **следующий** окончательно удаляет саму вакансию и отвязывает отклики/задачи. Если первый SQL COMMIT состоялся, а HTTP-ответ оказался `503` или потерян, слепой пользовательский повтор мог выполнить необратимый второй этап.

**#518 — исправление React и browser evidence:**
- `frontend/features/vacancies/Vacancies.tsx`: после неопределённого результата DELETE до повтора сверяется свежий `GET /api/vacancies/{id}` с `cache:'no-store'`. При `404` повтор не делается; при изменившемся `archived` UI инвалидирует список, блокирует повтор и требует нового подтверждения; при ошибке проверочного GET повтор также блокируется.
- `tests/browser/vacancy-drawer.spec.ts`: synthetic/mock HTTP (desktop/mobile) моделирует потерю ACK **после архивирования** и **после hard-delete**. Ранее существовавший тест ошибки до COMMIT сохранён.
- `docs/dev/API_CALLSITES.json`, `docs/dev/API_COVERAGE.md` актуализированы; [матрица 30 критериев](../BATCH-05-ACCEPTANCE-MATRIX-2026-11-20.md) добавлена.

**#519 — независимые SQL/HTTP evidence на disposable MariaDB:**
- `internal/storage/vacancy_delete_http_test.go`, `TestMariaDBVacancyDeleteHTTPDisposable`: реальный Go handler **сначала выполняет SQL COMMIT**, затем тестовая HTTP-обёртка подменяет только ответ на `503`; отдельно archive и hard-delete. Проверяется следующий GET вакансии (`archived:true` или `404`) **без нового DELETE**, сохранность SQL/CRM и изоляция прав.
- Реальные `GET /api/applications/{id}` с синтетическими сессиями двух пользователей подтверждают, что после hard-delete отклики доступны владельцам, `vacancyId=null`, статус/комментарий/история сохранены, чужие отклики по ID недоступны.
- Тест входит в обязательный `go test -race -tags mariadb,vacancydeletes ./internal/storage -run '^TestMariaDBVacancyDelete(HTTP)?Disposable$'` внутри `.github/workflows/mariadb-staging-ci.yml`; CI на head #519 зелёный.

**Граница доказательств:** #518 тестирует React + полностью синтетическую сеть; #519 тестирует Go HTTP + настоящую **одноразовую** MariaDB, но не запускает тот же React-клиент над этим сервером в одном интеграционном сценарии. Это **дополняющие**, а не единый end-to-end React→Go→MariaDB тесты. Не выдавать имитацию потери ответа из HTTP-тестовой обёртки за реальный сетевой сбой production.

## 6. Архитектура и действующие запреты

- **Go API** обслуживает React, CRM, вакансии, задачи и интеграции; **Go Worker** — отдельный непрерывный Go-процесс с логическими профилями `launch`, `reconcile`, `pipeline`. Они используют MariaDB. Существуют также ограниченные recovery-инструменты.
- Слияние в `main`, успешный API publish или `worker-artifact.yml` **не доказывают обновления установленного `itmap-worker`**. Не запускать второго consumer или дублирующий платный job. Рабочие SHA, состояние systemd/сервера, health/rollback проверять отдельно и только допустимым read-only способом.
- Никаких прямых правок `main/master`, auto-merge, production API/Worker deploy/restart, изменения live MariaDB, DDL, backfill, переключения старых сервисов, платных OpenAI/OpenRouter/Apify/Firecrawl запросов, запуска HH-сканирования или изменения бюджетов без отдельного разрешения владельца.
- Использовать только синтетические фикстуры/одноразовую MariaDB и branch+PR. Ни секретов, ни приватного контекста в публичном документе. Новый рабочий чат должен вести собственный следующий датированный handoff.
