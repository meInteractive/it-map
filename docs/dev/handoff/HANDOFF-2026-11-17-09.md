## Работа текущего диалога

Установлен конкретный пробел в `reserveAttemptLocked`:
`ErrMoneyUncertain` по прежним попыткам работал для того же
`job_id` и отдельно для `score_relevance` по вакансии. Новый
job ID при том же кандидате/типе AI-этапа мог пройти предыдущий guard,
если старый attempt ещё не имеет определённого завершения и относится
к текущему поколению.

Добавлена **консервативная read-only проверка** по
`scheduler_jobs.candidate_id + scheduler_attempts.type` перед
платной резервацией/POST, без нового DDL, внешних вызовов,
доступа к серверу, реальных DB rows или изменения бюджета.
Существующие проверки same-job, historical и relevance сохраняются.
Проверка имеет fail-closed результат `ErrMoneyUncertain`.
Точный контракт, границы меж-кандидатской дедупликации:
[AI_CROSS_JOB_PAID_GUARD](../AI_CROSS_JOB_PAID_GUARD.md).

`TestMariaDBAICandidateCrossJobUnknownPaidDisposable` использует
только disposable MariaDB, synthetic callback и валидные run/job/attempt
ledger. Сценарии: zero-reserve lost ACK, ACK с known cost но без stage
Save, unknown reserve, `failed` и `completed` без стоимости,
четыре AI types; разрешённые случаи другой кандидат, другой AI
этап, полноценное completed/known cost, never-selected provider.
До POST и после denial проверяется неизменность прежнего ledger.
Новый тест добавлен в **обязательный scheduler billing gate** с
проверкой pass не только родителя, но и критических subtests.

## Честные ограничения

- Контракт **не** гарантирует exactly-once для разных candidate_id
  одного URL или одинакового текста. Нужен durable input fingerprint,
  прежде чем разрешить универсальную дедупликацию.
- Для job без candidate_id невозможно применить меж-job guard,
  для orphan attempts без `scheduler_jobs` атрибуция кандидата
  утрачена; fallback historical AI guard работает по своим правилам.
- `completed` с известной стоимостью не блокируется этим guard:
  повторный job может быть обоснован реальной сменой входа, а
  `Prepare/Revalidate` остаются обязательными.
- Последний CI и PR надо проверить **на точном head SHA** после
  завершения текущей ветки; нельзя объявлять проход по успеху
  только сборки или другим PR. GitHub PR не мержить самостоятельно.
- Live worker, API, production-БД и реальный paid budget не затрагивали.
