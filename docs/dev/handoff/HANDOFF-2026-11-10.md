## 2. Неприкосновенные решения владельца

1. **Разделение задач от 09.11:** в обычном чате выполнять автономную работу, не требующую изменений рабочей схемы/данных: React/Go, read-only API, ошибки статистики, синтетические тесты, документация и CI. **Любые DDL, новые таблицы, миграции, проверку фактической производственной схемы и план rollback поручать Codex Cloud и отдельно согласовывать с владельцем.** Само поручение Codex не даёт допуска к production.
2. **Никаких** автоматического merge, прямых коммитов в `main`, production cutover, самовольного деплоя, DDL, мутаций рабочих данных, paid Apify/Firecrawl/OpenRouter/OpenAI, backfill, изменений budgets, timers/worker или запуска второго consumer. Только отдельные небольшие ветки `codex/GO-NNN-…` и PR с ручным слиянием владельцем. Тесты — синтетические и disposable MariaDB в CI.
3. Сохранять внешние API-контракты и строгую политику проверок. Не ослаблять `go-ci`, `mariadb-staging-ci`, `mariadb-103-ci`, `tsc`, `format:check`, Playwright и тестовые ожидания ради зелёного статуса. Если не проверено — писать «не проверено».
4. Комментарии нового кода — по-русски, без попутной перезаписи исторических JS. Для React: Prettier 3.6.2, `npm run format:check`, `npm run typecheck:web`, `npm run build:web`, Playwright desktop/mobile. `public/service-worker.js` дополнительно проверять `node --check` при изменении.
5. Реальные данные и серверные детали **только в приватном чате**. В handoff / PR / issue — минимальные обезличенные итоги; не выкладывать сырой JSON диагностики, SQL-выгрузки и финансовые счета.

## 4а. Данные HH/Apify от 10.11.2026: read-only диагностика, новый приоритет

**Разрешение владельца:** 10.11.2026 пользователь подтвердил, что обезличенные сведения из представленного снимка диагностики не являются секретными и их можно включить в публичный handoff. Полный JSON, отдельные имена компаний, ID заданий и провайдерских запусков, исходные ответы API, доступы и серверные детали здесь не публикуем. Снимки — наблюдение, а не live-доступ или доказательство полной production-сверки.

**Общая диагностическая выгрузка (10.11, 12:12 МСК, фильтры воронки `sourceId=all, parser=all`):**
- Планировщик активен; сигнал в 12:00 МСК; последний успешный цикл по данным обзорного summary в 11:45 МСК. В очереди 6 pending; цикл 12:00 увидел 6 ready, обработал 0 (без ошибок); некоторые прошлые попытки HH имеют `deferred`. Факты не доказывают, что очередь остановилась окончательно: не известны свежие попытки после снимка.
- Воронка первых успешных `create` **уникальных вакансий**, не число свежих публикаций на HH: **09.11: received=5, accepted=3, published candidates=2, newVacancies=1**; **10.11 на 12:12: received=26, accepted=19, published candidates=16, newVacancies=16**. По наблюдению владельца каталог показывает соответственно 0 и 2. Разница требует сверки: каталог по умолчанию фильтрует **дату публикации вакансии**, воронка использует **дату первого create**, плюс возможны фильтры типа сущности/ролей/избранного и UI cache. 16 созданий считаются по всем источникам, не утверждать, что все 16 принадлежат HH.
- Apify: был `failed` запуск и позже `apify_partial_run`; один `running` receipt без свежего обновления в момент выгрузки. Включён провайдерский лимит, но свободный бюджет сохраняется. Требуется проверить уже существующие receipts/cursors (read-only), **не** повторять Actor без разрешения.
- Накопленных P2=82, P1=0; среди P2 есть недавние HH `fetch_full_text` и `import_vacancy` `stage_failed`. Большинство остальных ошибок относится к старым заданиям и другим источникам; 82 не равно новым ошибкам сегодня.

**Самостоятельный снимок виджета «Когда HH проверят снова?» (10.11, 12:33 МСК):**
- Правила: интервал **1 день**, окно поиска **3 полных дня**, **только избранные компании**.
- Настроено 30 HH-источников, отключено 0, исключено по фильтру избранного 0. Из них **10 потенциально просрочены**, **14 ждут срока** (ближайший 10.11, 20:30 МСК), **6 уже имеют HH-задание**, 0 выполняются. 10+14+6=30; все находятся в выбранной области диагностики.
- После смены интервала 10 сроков пересчитаны по последней успешной проверке. У **1 источника** дата успеха отсутствует/некорректна и применён сохранённый срок; дополнительно проверить. `finalEligibilityVerified=false`: виджет не различает реально допущенные и заблокированные worker задачи.
- Проверка кода `internal/parser/scheduled_sources.go`: admission держит до **5 незаблокированных HH pending scan** и не создаёт второй активный scan для той же компании. Поэтому **6 общих pending** в UI не доказывают исчерпания именно этого лимита; `readVerifiedHHLineage` может исключать часть. Код `internal/parser/worker.go` разделяет `launch/reconcile/pipeline` с лимитами и deferred. Корневая причина задержки **не доказана**.
- Проверка кода `internal/parser/funnel.go` и `shared/publication-period.ts`: `newVacancies` считает первый уникальный `create` по времени `processed_at` в московском дне, каталог выбирает прежде всего `publishedAt` для периода. Фильтр «Неделя» может скрывать загруженные сегодня объявления с более старой датой публикации; требуется независимое read-only сравнение, а не предположение о потерянных карточках.

**Новое архитектурное ограничение, выявлено при разборе кода 10.11:** в `internal/parser/job_selection.go` глобальный `lastListingStart` подавляет **новый HH Actor в течение часа** после последнего старта (за исключением `reconcile` существующего запуска); в `worker.go` в одном balanced-цикле допускается лишь один новый launch. Поэтому в идеальном случае не более **24 новых HH Actor за 24 часа**, тогда как у владельца 30 ежедневных источников. При допущении хотя бы одного отдельного Actor на источник полный ежедневный обход математически не помещается в сутки. Это **ёмкостное ограничение**, а не доказательство конкретных потерь вакансий; нельзя увеличивать rate/бюджеты без согласования. Создан [issue #303](https://github.com/meInteractive/it-map/issues/303) с критериями оценки throughput, цены и безопасности.

**Разделение 15-минутного тика и часовой политики новых Actor (проверено после замечания владельца 10.11):** `internal/parser/cycle_control.go:113` создаёт 15-минутные ключи `quarter:<UnixMilli/900000>`; новый `balanced` тик может обслужить очередь, но `internal/parser/job_selection.go:208` оставляет отдельный cooldown новых HH Actor `3600000` миллисекунд (1 час), а `worker.go:230` — максимум один `launch` на тик. Это **намеренное ограничение GO-430**, явно описанное в `deploy/scheduler/README.md`, но оно противоречит ежедневному сканированию 30 независимых компаний при одном Actor на компанию. В Git-шаблоне `deploy/scheduler/itmap-scheduler-main.timer` всё ещё `OnCalendar=hourly`; **фактически установленный** systemd timer по Git не определить, нужна отдельная read-only проверка. `job_selection.go` также использует `/3600000` для бонуса приоритета старого задания, это **не** таймер и не надо менять механической заменой. Детальный аудит и требования к согласованию ускорения в [issue #303](https://github.com/meInteractive/it-map/issues/303). До явного одобрения владельцем менять интервал платных запусков с 1 часа на 15 минут нельзя; это может ускорить расход ограниченного Apify-бюджета.

**Текущая реализация read-only разбивки очереди:** [PR #302](https://github.com/meInteractive/it-map/pull/302) в статусе draft. В существующий административный HH-schedule GET добавляет агрегаты pending по категориям: не наступил срок / cursor неподтверждён / есть признаки осиротевшего провайдерского запуска / пригоден для GET/reconcile / глобальный launch cooldown / потенциально готов к новому launch / прочее. Применяет текущие правила `claimEligible`, но не создаёт lease, не делает POST, не сообщает индивидуальные job, URL или payload. `finalEligibilityVerified` остаётся `false` ввиду неизвестной фактической квоты/бюджета и лимитов цикла. Статусы CI проверять по **последнему SHA PR**, не переносить от прежних коммитов.

**Дальнейшие самостоятельные действия (высокий приоритет, до крупных рефакторингов GO-115):**

4. После одобрения read-only данных при необходимости сверить агрегаты actual production GET/receipts; если окажется нужен доступ или дополнительный свежий снимок, запрашивать строго необходимое. **Сейчас действий от владельца не требуется**.
5. Не запускать платные HH/Apify scan, batch backfill, повторные Actor, изменять расписание, проделывать DDL или править рабочие данные без отдельного разрешения владельца. **Двухконтурная передача по решению владельца:** handoff хранит только приведённую безопасную агрегированную фактуру и план. Частные операционные детали, если появятся после завершения задачи, резюмируются исключительно в пользовательском чате и не перепечатываются в Git.

## 6. Как вести этот handoff дальше

При **каждом значимом архитектурном/продуктовом решении**, старте и завершении PR или обнаружении блокировки добавлять датированную запись в **этот файл** и включать её в очередной коммит/PR. Минимальный набор полей: «дата МСК → кто/что согласовал → мотивация → какие файлы/контракты затронуты → PR/SHA → фактические тесты/CI → что не проверено → что делать следующим». В новом чате читать самый свежий handoff и сначала проверять актуальный код. **Записи делаются в ходе следующего активного шага разработки, не фоновым процессом без запуска.**
