# IT-MAP — рабочий handoff и журнал решений от 09.11.2026 (МСК)

> **Статус:** активный документ текущей сессии, заведён **до начала следующей задачи разработки**.  
> **Назначение:** передавать между чатами проверенный технический контекст, пользовательские решения, PR/CI и очередь работ, не заставляя пользователя копировать весь диалог. По завершении сессии документ становится историческим снимком; для следующей передачи создаётся новый датированный файл, а не переписывается старый.  
> **Публичность:** GitHub-safe документ. Доступ к production, платным провайдерам, миграциям и реальным данным **не предоставляется** самим фактом его существования.

## 1. Как входить в проект и поддерживать этот файл

1. Сначала прочитать [AGENTS.md](../../../AGENTS.md), [PLANS.md](../../../PLANS.md), [задачи](../../../tasks/README.md), [спринт 1.1](../../../tasks/SPRINT-01.md), [парсер/Apify](../../../tasks/SPRINT-01-PARSER-APIFY.md), [спринт 1.2](../../../tasks/SPRINT-02.md), [архитектуру](../ARCHITECTURE.md), [MariaDB](../MARIADB.md), [прошлый handoff 08.11 (21:32)](HANDOFF-2026-11-08-02.md) и [подробную очередь 08.11](HANDOFF-2026-11-08.md).
2. Затем сверить **актуальные** `main`, открытые PR, состояние обязательных CI, код Go/React и схему, доступную в коде. Handoff фиксирует решения и прошлые проверки, **не заменяет GitHub/код, runtime и реальную БД**.
3. **Новые важные решения добавлять в этот активный файл** по мере работы: дата (МСК), что решили и почему, область действия, исключения/ограничения, PR/SHA, результат CI, что ещё не проверено, следующее действие. Не превращать предположения в доказанные факты.
4. При подготовке каждого следующего функционального PR обновлять этот handoff **в том же PR, когда это практично**, либо отдельным маленьким документационным PR от актуального `main`, если есть риск конфликтов. После merge фиксировать фактический статус, не считать открытый PR смерженным. **Merge выполняет пользователь.**
5. Не писать в документ реальные ключи, серверные адреса, резюме, персональные данные, финансовые счета/выгрузки, приватный JSON/SQL и закрытую диагностику. Операционные детали остаются в приватном пользовательском чате.

## 2. Главное решение пользователя от 09.11: разделение ответственности

Пользователь прямо решил: **изменения схемы БД оставить Codex Cloud**, поскольку там безопаснее выполнять миграции и проще проверять фактическое состояние БД. Для работы в обычном чате выбирать задачи, **не требующие изменения рабочей БД**.

| Работа в этом чате / через GitHub | Передать Codex Cloud |
| --- | --- |
| Go/React UI, корректность статистики и фильтров, безопасные read-only API по существующей схеме, диагностические представления, документация и synthetic/mock-тесты | Новые таблицы, DDL и миграции схемы, проверка фактической production-схемы, подготовка/проверка rollback и восстановления |
| Анализ кода и существующих журналов, SELECT-only методики **без самостоятельного обращения к production**, одноразовая MariaDB в CI | Сверка исторических расходов с реальными рабочими данными и провайдерами при отдельном доступе и разрешении |
| Небольшие независимые PR, тесты, отчёт о CI и передача пользователю для ручного merge | Постоянные связи `provider operation → scan/candidate/stage/vacancy` и связанная аддитивная миграция для полноценной когортной стоимости |

**Ограничение не является разрешением для Codex** самостоятельно менять production или получать доступ к секретам. Нужны отдельное решение владельца, план резервного копирования/rollback и подходящая среда проверки.

Дополнительные постоянные правила:

- Никаких прямых изменений `main` или auto-merge. Один самостоятельный PR на логически завершённую часть. Не смешивать неконтролируемый рефакторинг с исправлением поведения.
- Не изменять рабочие записи, поведение живого парсера/очередей, лимиты, таймеры/worker, развёрнутый D1/Go runtime, бюджеты и расписания без явного разрешения. Правки исходного Go-кода для read-only статистики допустимы в отдельном PR. Не выполнять реальные платные вызовы Apify/Firecrawl/JEV/OpenAI в рамках синтетических тестов.
- Проверять **все три обязательных workflow** на **последнем HEAD SHA**, а не только один зелёный job или старую версию. CI на disposable MariaDB не равен live smoke. Не скрывать падения через `--unhandled-rejections=warn` и не исправлять тесты под результат без разбора причины.
- Не отмечать незавершённые чекбоксы задач выполненными. Для каждой задачи хранить PR, SHA, CI, ограничения и фактически проверенные сценарии. После сообщения пользователя «смержил» переходить к следующей самостоятельной задаче без повторения согласованных вопросов.

### Новые диагностические выводы по issue #290 (09.11.2026)

По безопасному пользовательскому JSON: scheduler включён, автоматические сигналы приходят каждые 15 минут, но последние циклы имеют `ready=1, processed=0, errors=0, remaining=1` и не создают новых событий; новый приём вакансий 09.11 равен нулю. При этом воронка уже учитывает **60 новых уникальных карточек 07.11** и **5 карточек 08.11**. Поэтому пользовательская формулировка «ничего после 06.11» верна не для дат **импорта**; исходные даты публикации HH и каталог отдельно не сверены.

Кодовый вывод: `cycle_progress.go` вычисляет `ready` по всем просроченным pending, но автоматический `worker.go` выбирает только HH и этапы `launch/reconcile/pipeline`, затем проверяет `VerifiedHHOnly`. Значит `ready=1 / processed=0` **не доказывает**, что одно HH-задание блокировано; оно может быть неисполняемым в этом цикле. `scheduled_sources.go` создаёт новые HH-задачи только с наступившим `next_run_at` и в рамках выбранных company/favorites, `intervalDays` и `sourceIds`. Подтвердить конкретный фактор по реальной БД без отдельного разрешения нельзя. Периодический тик не означает обязательного ежедневного платного сканирования.

Следующая проверка: безопасный `status=pending` срез очереди (тип/источник/время/причина без публикации ID), пользовательские настройки источников; при необходимости отдельный Codex read-only аудит `next_run_at` и действующей конфигурации. Не запускать повторы платных операций, не изменять таймеры и DB. [Issue #290](https://github.com/meInteractive/it-map/issues/290) дополнена выводами. **Причина пока не установлена.**
