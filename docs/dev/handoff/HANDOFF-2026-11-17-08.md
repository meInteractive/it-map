## Что сделано

Добавлены три read-only агрегата к `GET /activityz`:
`importCreateOperations`, `importUpdateOperations`,
`importUnchangedOperations`.

Числа отражают только синтетически проверяемый по SQL контракт:
- `scheduler_jobs` текущего generation, `type='import_vacancy'`,
  `status='completed'`, `completed_at` в 24-часовом окне;
- `vacancy_import_operations.id=scheduler_jobs.id`,
  `status='success'`, `candidate_id` совпадает с job,
  `vacancy_id IS NOT NULL`, action из закрытого набора;
- не требуют внешних POST и не пишут в БД.

Даже если `importCreateOperations=2`, это **не** обязательно
`newVacancies=2` — два разных кандидата могут иметь один
`vacancy_id`. GO-436 и `internal/parser/funnel.go` считают первые
успешные CREATE глобально по уникальному `vacancy_id`, а не все
подтверждения импорта. Воронка использует московские календарные
даты; activity — rolling 24h по часам MariaDB.

Проверки:
- новый disposable MariaDB тест
  `TestMariaDBWorkerActivityImportActionsDisposable`:
  create/create на одну карточку, update, unchanged,
  failed receipt/job, старое окно, другое поколение,
  пустой receipt, null FK; read-only snapshot, отсутствие
  влияния чужого поколения;
- исходный `TestMariaDBWorkerActivityDisposable` включён в
  mandatory worker diagnostic MariaDB CI вместе с новым тестом
  и существующими queue/recovery;
- unit `TestReadyAndEmptyQueueDoNotClaimNewVacancies`: все
  профили `Idle`, `/readyz` 200, `/queuez` пуста, но
  `/activityz` не утверждает наличие опубликованных вакансий.
- описаны условия и ограничения наблюдений в
  [WORKER-ACTIVITY-DIAGNOSTICS.md](../../../deploy/WORKER-ACTIVITY-DIAGNOSTICS.md).

## Важно для последующих PR

Не выдавать счётчики activity за аудит уникальных вакансий,
не включать старый consumer, не менять реальные БД или
finance ledger. `/activityz` показывает только текущий generation
и окно по времени завершения job: старые/пропавшие job не
позволяют восстановить полную статистику. `/readyz` лишь
сообщает о свежем результате профилей. Для реальной сверки
нужны обезличенные read-only снимки и отдельное решение владельца.

Следующее: после полного CI этого PR — тестировать GO-431
меж-job idempotency для разных кандидатов/одного входа,
не допуская повторного платного POST при неопределённых попытках;
рассмотреть только read-only evidence и synthetic тесты.
