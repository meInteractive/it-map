# GO-433 — изолированный SQL-проект расширения схемы

**9 ноября 2026. Статус: проект миграции, протестированный только в одноразовой MariaDB. НЕ готов к применению на staging/production.**

Файл: [`db/migrations/proposals/go433_cost_lineage_v1.sql`](../../../db/migrations/proposals/go433_cost_lineage_v1.sql). Он **не** загружается в `schema-init`, не входит в `db/testdata/empty-schema.sql` и не исполняется сервером. В нём нет `ALTER`/изменения исходных таблиц, INSERT существующих данных, триггеров или чтения аккаунтов. Контракты происхождения и расчёта описаны в [GO-433-PROVIDER-COHORT-LINEAGE-DESIGN.md](./GO-433-PROVIDER-COHORT-LINEAGE-DESIGN.md).

## Почему пока не запускаем эту миграцию

`internal/dbschema/baseline_v1.json` задаёт строгий baseline **72 таблицы, 606 столбцов, 50 внешних ключей, 22 триггера**. `dbschema.CheckFull` и `ValidateBaseline` отвергают *любые* неизвестные таблицы. `dbschema.Initialize` работает только с этой фиксированной схемой, а старые backup/restore v39 и smoke-проверки ожидают её. Простое применение пяти новых таблиц на рабочем стенде сделало бы схему **несовместимой со штатным сервером**. Подменять baseline и ослаблять проверку без отдельной схемной миграции нельзя.

В рамках текущего PR решаем только DDL-структуру и инварианты; тест **намеренно подтверждает**, что baseline несовместим до удаления расширения и снова валиден после очистки. Это блокировка будущего unsafe rollout, а не ошибка теста.

## Таблицы

| Таблица | Назначение и защита |
|---|---|
| `cost_scan_cohorts` | Неизменяемый `cohort_id`, версия источника, `generation`, `scan_job_id`. UNIQUE(`generation,scan_job_id`) запрещает вторую когорту одного job; при другом job разрешён повтор того же Actor |
| `cost_provider_operations` | PK отдельной финансовой операции, UNIQUE(`source_ledger,source_receipt_id`) и UNIQUE(`provider_kind,billing_scope,provider_operation_id`). Неизвестный ACK хранит `provider_operation_id=NULL`; аккаунт при этом может быть известен |
| `cost_operation_settlements` | Версионированные локальные/провайдерские наблюдения; отдельные `cost_usd`, `reserved_usd`, `credits` как `DECIMAL(20,8)`. NULL расхода не превращается в ноль. `provider_verified=1` разрешён только для `status=settled`, `source=provider` с не-NULL ценой |
| `cost_operation_cohort_links` | Many-to-many. UNIQUE по (`operation_id,cohort_id,relation`) и FK на существующие в расширении операции и когорты. Один оплаченный Actor в нескольких когортах остаётся shared/unallocated |
| `cost_discovery_events` | Связь конкретного элемента Dataset с когортой, операцией и кандидатом; UNIQUE по (`cohort_id,operation_id,dataset_item_key`). FK требует ранее записанный link `observed_from`. Для rejected допускается NULL `candidate_id` |

Все таблицы имеют `InnoDB`, `utf8mb4_nopad_bin`, уникальные идентификаторы и ограничения. В логах финансового конвейера не сохраняются тексты вакансий, резюме, API-ключи, полные URL и исходные тела ответа. Идентификаторы `dataset_item_key` должны выпускаться сервером как стабильный неперсональный digest; это ещё не подключено.

**Ограничения проекта:** UNIQUE с `NULL` в MariaDB не предотвращает несколько разных *неидентифицированных* provider операций: именно существующий fenced reserve должен обеспечивать идемпотентность до появления внешнего ID. В SQL пока нет FK к старым `scheduler_jobs`, `vacancy_candidates`, `company_vacancies`: эти таблицы участвуют в восстановлении v39, и политику каскадов/поколений необходимо согласовать до внедрения. Ссылка `captured` не является подтверждением тарифа или счета.

## Изолированный CI

`TestMariaDBSchedulerCostLineageSchemaDisposable` исполняется в `scheduler-job-acceptance` **после всех его обычных проверок**. `openDisposableMariaDB` требует loopback, точное имя `itmap_ci`, CI writer identity и совпадение случайного generation текущего workflow. Перед DDL тест проверяет `dbschema.CheckFull` и отсутствие всех пяти таблиц, затем проверяет:

- создание ровно пяти таблиц и четырёх внутренних FK;
- разные billing scopes с одинаковым Actor run ID, отказ от дубликата Actor и повторного local receipt;
- сохранение состояния unknown ACK и истории резерва отдельно от подтверждённой суммы, точность `DECIMAL`, известный ноль;
- отказ от невалидных `provider_verified` и отрицательных сумм;
- два links одного Actor к разным когортам, запрет дублирования link и ссылок на несуществующую когорту;
- идемпотентность повторного Dataset item, запрет discovery без link, транзакционный ROLLBACK события;
- отклонение расширенной схемы старым trusted baseline и полное восстановление этого baseline после удаления пяти таблиц в обратном порядке.

Не используется production, реальные счета, внешние запросы, миграции существующей БД или платные API. Тест не создаёт триггеров, пользовательских аккаунтов и таблиц в других схемах.

## Что необходимо до внедрения

1. Отдельный **schema-policy v2 и upgrade preflight**: полная метаданная политика всех пяти новых таблиц, миграция *только* из exact v1 под тем же named ownership lock, запрет DDL при неизвестном/частично повреждённом состоянии, восстановление после прерывания, отсутствие фонового DDL.
2. Согласовать поведение **backup/restore v39** при новом финансовом ledger: исключение из публичного выгружаемого бэкапа или строго версионированный приватный бэкап с восстановлением только совместимого generation. При полной смене поколения нельзя сохранять устаревшие внешние связи как подтверждённые.
3. Раздельные права: offline schema upgrader DDL, runtime только SELECT/ограниченный DML. Проверить, что старые серверы не запускаются поверх v2 и наоборот.
4. После утверждения миграции: trusted, fenced, атомарный capture при Apify/Dataset/AI/Firecrawl. Любая ошибка записи provenance должна откатить курсор/кандидата; неизвестный ACK не разрешает второй POST.
5. Затем реализовать read-only когортный API и UI с `verified/local/unknown/shared` и проводить реальную сверку только при явном разрешении.

**Merge текущего PR не является разрешением запускать SQL вручную.** Пока сохраняется частичный календарный показатель из GO-433 и отдельная диагностика покрытия связей. Полная когортная себестоимость не реализована.
