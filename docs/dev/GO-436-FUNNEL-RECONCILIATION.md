# GO-436: сверка «Опубликовано» и реально новых вакансий

> **Исправление GO-436 (09.11.2026, PR в проверке):** в Go API воронки добавлено независимое поле `daily[].newVacancies`, `totals.newVacancies`, `averages.newVacancies` и `undatedNewVacancies`. Это первые успешные `create` по **уникальному существующему `vacancy_id`**, выбранные из всей истории *до* фильтрации источника и парсера. Повторный `create` другой кандидатуры/источника не создаёт новую карточку ещё раз. Старый `daily[].published` **сохранён для совместимости**, но в интерфейсе переименован в «Импортировано кандидатов», включая `create/update/unchanged`. По умолчанию график показывает «Получено» и **«Новые уникальные вакансии»**; детализация содержит обе категории. Нижняя воронка по-прежнему считает кандидатов и не выдается за уникальные карточки. Устаревшие ответы фильтров не показываются во время смены источника. Исправление проверяется на синтетической MariaDB, **реальные 61 за 07.11 по-прежнему не сверены**. Никакой записи в рабочую БД, DDL или платных вызовов нет.

**Состояние на 08.11.2026:** смысл показателя подтверждён исходным Go-кодом; 61 на скриншоте пользователя и фактическое распределение записей production **не подтверждены чтением API/SQL**. Этот документ готовит безопасное расследование. Не использовать синтетические числа как наблюдения из рабочей БД.

## Что сейчас считает график

В `internal/parser/funnel.go` поле `published_at` вычисляется для каждого `vacancy_candidates.id` как `MIN(vacancy_import_operations.processed_at)` среди операций с `status='success'` и `action IN ('create','update','unchanged')`. Если первая успешная операция попала в московские сутки, дневное `daily.published` увеличивается на **одного кандидата**, а не на одну уникальную запись `company_vacancies`. Старые кандидаты могут впервые пройти импорт сегодня; несколько кандидатов могут ссылаться на одну основную карточку. Повторные успешные операции одного кандидата не увеличивают дневное значение.

Нижняя `cohort.created`/ `cohort.linked` группирует **кандидатов, впервые полученных** за выбранные 30 дней, с результатом на момент чтения. Она не является разбивкой `daily.published` за определённую дату. `scheduler_runs.succeeded` и количество завершённых `scheduler_jobs` также не эквивалентны новым карточкам.

## Безопасная последовательность проверки реальных данных

1. После явного разрешения администратора снять **только внутренний GET** `/api/scheduler/funnel?sourceId=all&parser=all` с проверкой прав и ответов. Зафиксировать `checkedAt`, `timezone`, `filters`, `daily` для `2026-11-07`, `totals`, `cohort`. Повторить GET для исключения устаревшего React cache. Общая JSON-кнопка содержит safe snapshot; при спорной цифре сравнивать с исходным read-only API.
2. На отдельно разрешённом **read-only** соединении к рабочей БД проверить форматы `vacancy_import_operations.processed_at` и другие фильтры. Не выполнять SQL ниже, пока неизвестно, что время **нормализовано в UTC RFC3339 с `Z`**; наличие `+hh:mm`, локальных дат или нераспознаваемых значений требует отдельной точной нормализации, эквивалентной `funnelDate`.
3. Выполнить агрегирующий SELECT только по разрешённым данным, отдельно сравнив входящие кандидаты, разные `main_vacancy_id`, и первые успешные `create/update/unchanged`. Не экспортировать `title_raw`, URL, тексты, `changes_json` и `message`. Проверять все поколения: funnel не фильтрует исторические импортные операции по текущему `generation`.
4. Для первых `create` проверить наличие/время создания основной строки `company_vacancies` и связи `vacancy_publication_keys/sources` или другие действующие ключи дедупликации. `action='create'` — свидетельство действия импортёра, **не абсолютное доказательство** вновь созданной уникальной карточки без сверки.
5. Если расхождение объясняется `update/unchanged`, отдельно согласовать корректное название/несколько рядов графика. Если нашлась повторная реальная вставка, готовить отдельный узкий failing test и PR, **без редактирования рабочих данных**.

### Контрольная граница суток

7 ноября 2026 года по `Europe/Moscow` соответствует полуинтервалу UTC:

- от `2026-11-06T21:00:00Z` **включительно**;
- до `2026-11-07T21:00:00Z` **не включительно**.

Если в `processed_at` хранятся другие часовые зоны или смешанные строковые форматы, простое сравнение с этими границами **неверно**. Исходный Go-код разбирает время и затем переводит его в фиксированное `UTC+03:00`; SQL должен воспроизводить именно этот смысл.

### SELECT для нормализованного UTC RFC3339

**Только пример для согласованного чтения и только при проверенном формате времени.** Параметры: `sourceId='all'`, `parser='all'`, UTC-границы выше. Агрегат не возвращает строки, названия или URL. Из всех исторических успешных операций кандидата сначала выбирается первая; иначе повторы одного кандидата искажают результат.

~~~sql
WITH first_ok AS (
  SELECT o.candidate_id, o.vacancy_id, o.action, o.processed_at,
    ROW_NUMBER() OVER (
      PARTITION BY o.candidate_id
      ORDER BY o.processed_at, BINARY o.id
    ) AS rank_in_candidate
  FROM vacancy_import_operations o
  WHERE o.status = 'success'
    AND o.action IN ('create','update','unchanged')
    AND o.processed_at IS NOT NULL
)
SELECT
  COUNT(*) AS first_success_events,
  COUNT(DISTINCT f.candidate_id) AS unique_candidates,
  COUNT(DISTINCT f.vacancy_id) AS distinct_receipt_vacancy_ids,
  COUNT(DISTINCT c.main_vacancy_id) AS distinct_main_vacancy_ids,
  COALESCE(SUM(f.action='create'),0) AS create_receipts,
  COALESCE(SUM(f.action='update'),0) AS update_receipts,
  COALESCE(SUM(f.action='unchanged'),0) AS unchanged_receipts,
  COUNT(DISTINCT CASE WHEN f.action='create' THEN f.vacancy_id END)
    AS distinct_create_receipt_vacancy_ids
FROM first_ok f
JOIN vacancy_candidates c ON c.id = f.candidate_id
LEFT JOIN parser_candidate_intakes i ON i.candidate_token = c.creation_token
WHERE f.rank_in_candidate = 1
  AND f.processed_at >= ?
  AND f.processed_at < ?
  AND (i.parser IN ('apify','firecrawl','http','unknown')
    OR (i.parser IS NULL AND c.acquisition_method IN ('site','firecrawl')));
~~~

**Сверка с фильтрами UI:** добавить строго эквивалентные `funnelCandidateSQL` фильтры на `sourceId` и `parser`, если пользователь смотрел не «Все источники / Все парсеры». Не фильтровать события только по `processed_at` *до* выбора первого успеха: тогда повторная публикация старого кандидата ошибочно попадёт в день. Если у кандидата несколько успехов с одинаковым ранним timestamp, отдельным SELECT проверить конфликтующие действия; выбор `ORDER BY ... id` — детерминированная техническая развязка, а не дополнительное доказательство `create`.
