# GO-447 — согласованный релиз API и Worker

[Задача GO-447](../../tasks/GO-447-WORKER-DEPLOY-RESTART.md) · [Issue #472](https://github.com/meInteractive/it-map/issues/472)

## Что позволяет действующий протокол

`publish.yml` собирает API и SPA для точного SHA, регистрирует sequence и
передаёт архив по ограниченному SSH-каналу. Receiver проверяет manifest и ELF,
записывает точку отката и запускает отдельный systemd job. Этот job переключает
только API. Воркер поставляется через отдельный workflow сборки артефактов.

`RunProfilesWithGrace` прекращает планирование при отмене и ограничивает
ожидание текущего шага. При истечении grace контекст шага отменяется. Выход
процесса после SIGTERM поэтому не подтверждает расчёт с провайдером.
`/queuez` и `/activityz` показывают снимки. Между снимком и SIGTERM может
начаться новый шаг. Для автоматизации требуется подтверждение от самого
цикла исполнения после закрытия допуска.

## Контракт остановки

1. Receiver передаёт запрос на паузу через локальный Unix-сокет с доступом
   только для воркера и root. Запрос привязан к экземпляру процесса и
   идентификатору релиза. Повтор того же запроса возвращает его текущий статус.
   Источник истины о запущенном экземпляре — systemd MainPID и его исполняемый
   файл.
2. Цикл закрывает допуск новых профилей и claims, пропускает уже начатый шаг
   до штатного завершения и подтверждает паузу только после выхода из шага.
   Начатым считается и шаг, которому уже разрешено войти в критическую
   секцию, даже если внешний запрос ещё не отправлен. У запроса на паузу свой
   срок ожидания. Его истечение не отменяет контекст выполняемого шага.
3. Подтверждение содержит итог активного шага и признаки занятого lease или
   незавершённой попытки. Потерянный ответ провайдера, ошибка записи расчёта,
   потеря процесса или невыясненное владение дают `deferred`. Receiver
   отменяет запрос на паузу для живого прежнего экземпляра и оставляет оба
   релиза на месте. Существующие неопределённые попытки учитываются по
   правилам GO-431. Для первого включения оператор сверяет такие попытки
   отдельно.
4. После подтверждения пауза удерживается до завершения экземпляра. Если
   экземпляр сменился, подтверждение недействительно. На время транзакции
   требуется постоянный локальный запрет обработки, который переживает
   самоперезапуск systemd. Новый экземпляр стартует в режиме ожидания,
   поднимает диагностику и проверяет generation и схему. Обычный режим
   обработки открывается после фиксации релиза. Состояние ожидания должно
   явно отличаться от прикладной readiness.

## Доставка и восстановление

- В режиме совместного релиза пакет содержит `itmap`, `itmap-worker` и SPA.
  Два бинарника собираются с `-buildvcs=true` из чистого checkout того же SHA,
  с тегом `mariadb` и одной архитектурой. Упаковщик проверяет build info до
  архивации. Receiver проверяет точную схему manifest, хеши, ELF и
  идентичность кандидата до изменения указателей.
- Совместный пакет допускается только для main и только при включённом
  root-controlled флаге на receiver. Workflow выбирает формат явно.
  При несовпадении формата и политики receiver отклоняет релиз. До
  согласованного включения сохраняется действующий путь публикации API.
- Под общим lock receiver сохраняет прежние цели API и Worker, digest,
  sequence, состояние запрета обработки и фазу транзакции. Journal
  записывается до каждого необратимого перехода. Затем receiver удерживает
  паузу, останавливает воркер, проверяет отсутствие его процесса, переключает
  оба указателя и запускает службы. Новый воркер остаётся в ожидании.
- Перед фиксацией receiver сверяет оба процесса с ожидаемыми файлами и
  digest, выполняет действующие API smoke-проверки и проверку готовности
  воркера к снятию паузы. После фиксации снимает запрет для проверенного
  экземпляра и подтверждает рабочую readiness. Повтор завершённого запроса
  возвращает результат без дополнительных рестартов.
- Ошибка до фиксации возвращает обе прежние цели. Receiver проверяет версии
  и доступность обоих прежних процессов перед снятием запрета. Ошибка при
  проверке после фиксации требует повторного подтверждения паузы перед
  откатом. Если восстановление или подтверждение остановки невозможно,
  результат `rollback_failed` блокирует последующие публикации до
  операторской сверки. Схема и данные MariaDB остаются вне транзакции.
- После прерывания receiver сверяет journal, указатели, MainPID и запрет
  обработки. До фиксации он восстанавливает прежний релиз. После фиксации
  он завершает последнюю проверку или публикует блокирующий статус.
  Исходящий статус `success` появляется только после подтверждения обоих
  процессов.

## Первый запуск и приёмка

У установленной версии может отсутствовать контракт паузы. Первый переход
на совместимую версию требует отдельного контролируемого окна и проверки
возможности восстановления. Включение автоматического режима происходит
после установки совместимого воркера, receiver и проверки конфигурации
служб. Отказ по активной работе отображается как `deferred` в publish job.

Для реализации нужны проверки Python-протокола на валидный релиз и повтор,
устаревший sequence, неверный SHA/ELF/digest, прерывание на каждой фазе
journal, потерю ACK, ошибку readiness и ошибку отката. Тесты Go проверяют
гонку между паузой и claim, потерю экземпляра, удержание паузы и штатное
завершение активного шага. Тесты disposable MariaDB подтверждают
сохранение lease и ledger при потерянном ответе и отсутствие повторного
платного POST после перезапуска. Внешние вызовы в этих тестах синтетические.
