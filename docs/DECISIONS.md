# Журнал архитектурных решений it-map

Решения сохраняют договорённости, но **не** дают разрешения на изменение данных/production. «Принято» = концептуально утверждено, не обязательно реализовано; «предложено» = требуется согласование. Дата указана только если известна из истории проекта.

| ID | Дата | Решение | Обоснование | Последствия / ограничения | Статус |
|---|---|---|---|---|---|
| ADR-001 | 2026-10-23 | Миграция GPT Sites → Go по спринтам 1.1–1.4 | Снять лимиты Sites и улучшить эксплуатацию | Старый сайт работает до отдельного cutover | принято |
| ADR-002 | 2026-10-23 | Один монорепозиторий для Go и React; `gpt-site` как исходный эталон, новая разработка в `master` | Codex может сопоставлять API и код | Запрет прямой записи и автослияния в `master` | принято |
| ADR-003 | 2026-10-23 | MariaDB локально на сервере Go; исходная D1-схема с минимумом изменений | Сохранить данные и связи | Новая БД отдельно от живой D1; нужен финальный синхронизированный снимок | принято |
| ADR-004 | 2026-10-23 | В 1.1 сохранить React и по возможности существующий HTTP API | Быстрее перейти без регрессий интерфейса | Контрактные проверки обязательны | принято |
| ADR-005 | 2026-10-23 | В 1.1 Go-модульный монолит, `database/sql` и драйвер MariaDB без тяжёлой ORM | Минимум лишней архитектуры | SQL переносить и тестировать вручную | принято |
| ADR-006 | 2026-10-23 | В 1.1 автономный Go-планировщик/очередь на MariaDB, без RabbitMQ | Функциональный перенос раньше изменения механизма очередей | Сохранение leases, retry, generation и бюджетов | принято |
| ADR-007 | 2026-10-23 | RabbitMQ в 1.3, MariaDB остаётся источником истины, transactional outbox | Не терять задания при сбоях | Нужны replay/idempotency/DLQ/rollback | принято |
| ADR-008 | 2026-10-23 | 1.2 — correctness и улучшения, 1.4 — чистка/документация/качество | Разделить скорость переноса и engineering hardening | Изменения API в 1.2 допускаются по согласованию | принято |
| ADR-009 | 2026-10-23 | Публичный Git без дампов, бэкапов, реальных секретов и частных данных | Защита пользователей и платных провайдеров | `.gitignore` не удаляет данные из истории; аудит обязателен | принято |
| ADR-010 | 2026-10-23 | Staging изолирован от production; раздельные БД/секреты; production только после release-gate | Тестовые записи не должны попасть в рабочие данные | Домен `master` не означает право на автоматический cutover | принято |
| ADR-011 | 2026-10-23 | Новая клиентская Vite-сборка для React вместо зависимости от Vinext в Go | React преимущественно клиентский | Реальная сборка/PWA должны быть проверены | принято |
| ADR-012 | 2026-10-23 | Стартовый Go HTTP реализован на `net/http`, не на Gin | Текущий код и тесты уже используют ServeMux | Смена фреймворка — отдельное решение; исходная рекомендация Gin не реализована | принято (для текущего кода) |
| ADR-013 | 2026-10-24 | `docs/DATABASE.md` сохраняется без изменений, целевую MariaDB документируем отдельно в `docs/MARIADB.md` | Не терять исторический справочник D1 | Не смешивать разную семантику SQL | принято |
| ADR-014 | — | Способ финального инкрементального переноса/заморозки D1, RPO/RTO и откат новых Go-записей | Два хранилища в ходе разработки расходятся | Требуется отдельная согласованная процедура до production | предложено |
| ADR-015 | — | Инструмент для Go/MariaDB миграций и процесс применений | Необходимо версионировать DDL | Пока не внедрять произвольный фреймворк | предложено |
| ADR-016 | — | Стратегия секретов и совместимость старого AES-GCM, staging-провайдеры | Платные API и зашифрованные настройки | Нельзя переносить секреты через публичный репозиторий | предложено |
| ADR-017 | — | Политика GitHub branch protection, выбор ветки тестового домена, правила ручного деплоя | Несколько feature-веток претендуют на один стенд | Настроить только после отдельного утверждения и учёта инфраструктуры | предложено |
| ADR-018 | 2026-10-25 | Ubuntu 24.04 LTS; автоматический деплой из GitHub Actions: main на основной домен, последняя обновлённая non-main ветка на dev-домен | Утверждено пользователем для инструкции собственного сервера | Выбор по push, раздельные контуры и обязательный CI; подключение сервера/секретов/защиты и приёмник ещё не реализованы. Не разрешает production/cutover | принято (схема; оставшиеся правила ADR-017 открыты) |

**Процедура изменения:** новая запись ADR с мотивацией и последствиями; при отмене сохранять старую строку со статусом «отменено» и ссылкой на замену. Существенные решения не менять только потому, что Codex нашёл более удобный способ.
