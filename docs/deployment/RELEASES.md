# Две ветки и автоматический деплой из GitHub Actions

Утверждённая схема: `main` обслуживает основной домен; **одна последняя обновлённая ветка кроме main** обслуживает dev-домен. Репозиторий прежний, ОС сервера — Ubuntu 24.04 LTS. Домены в публичных примерах заменены на app.example.org/app-dev.example.org. Ветка спринта и отдельная task-ветка выбираются одинаково; PR base не определяет домен.

GO-056/057 реализуют native receiver/workflow/packer/SSH client. Точная настройка — [RECEIVER.md](RECEIVER.md) и [ACTIONS.md](ACTIONS.md). Реальный сервер/ключи/Environments ещё не подключены, production не включён. Ниже сохранён контракт, по которому реализована автоматика; его инфраструктурные/внешние acceptance gates требуют настройки оператора.

## 1. Правило выбора

- Main-контур получает только точный SHA ветки main после успешных проверок этого SHA.
- Dev-контур получает точный SHA последнего **push обновления ветки** кроме main. Время автора/коммиттера, `git branch --sort=-committerdate` и время окончания CI для этого непригодны. Rebase/cherry-pick может оставить старую дату коммита, а старый медленный CI закончится позже нового.
- Контроллер регистрирует push **до** ожидания тестов и сохраняет выбранные ref/SHA/порядковый номер запроса. Повторный запуск CI того же события не делает ветку «последней» снова. Другой старый успешный run не должен перезаписать новый выбор.
- Если у последнего кандидата красный CI, сервер недоступен или ветка не содержит Go-проект/обязательный workflow, сохранить предыдущий работающий dev-релиз и показать отказ. Не подставлять следующую по возрасту ветку молча.
- Исторические gpt-site/master не являются Go-релизами. Их нельзя автоматически запускать как старый Worker. Если правила выбора затронули такую ветку, кандидат блокируется проверкой пригодности; рабочий dev-релиз сохраняется. При желании исключить архивные ветки целиком это нужно явно закрепить в политике, а не угадывать по имени.
- Удаление/переименование выбранной ветки — отдельное событие: отменить кандидата, сохранить работающий релиз, потребовать новый push/явный выбор. Force-push — новый запрос со своим SHA и CI. Не деплоить refs/pull/* и forks с серверными секретами.

Git не хранит время обновления каждой ветки. GitHub events API имеет ограниченную историю, а branch API не даёт универсальный pushed_at для ref. Поэтому нужен устойчивый журнал push-запросов в защищённом каталоге сервера или другом durable store. До включения автоматики начальный кандидат фиксируется оператором по известному push; «восстановить последнюю ветку» сортировкой коммитов нельзя.

## 2. Настройка GitHub и сервера

1. Сначала подготовить [SERVER.md](SERVER.md), раздельные main/dev БД/env/службы, SSH, DNS/TLS. Main пока также ограниченный staging, APP_ENV=production остаётся запрещён. Не переводить живые пользовательские данные по факту включения workflow.
2. Создать GitHub Environments `itmap-main` и `itmap-dev`. Для main разрешить только ветку main. Для dev определить доверенных авторов/ветки; автоматический запуск кода произвольного автора с доступом к серверу недопустим. Environment должен выдавать секреты только job публикации/регистрации, не build/test job. Не использовать `pull_request_target` для выполнения кода PR с ключом сервера.
3. Настроить отдельные deploy-пользователи/SSH-ключи main/dev. Ключ dev не должен давать возможность перезапускать main, читать его env или менять systemd/nginx/контроллер. У SSH-ключа отключить agent/X11/port forwarding и PTY; по возможности использовать forced command приёмника. Для sudo разрешить только необходимые операции одной службы, без произвольного shell/root-команд. Не передавать Go-процессу SSH-ключи и Docker socket.
4. В соответствующий Environment добавить **секрет** `DEPLOY_SSH_KEY`. Несекретные настройки: `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_USER`; если адрес тоже приватный, хранить как secret. `DEPLOY_KNOWN_HOSTS` — проверенная запись ключа хоста; получить fingerprint у администратора по независимому каналу. Не доверять первому ssh-keyscan во время деплоя и не ставить StrictHostKeyChecking=no. Эти имена относятся к workflow публикации, **не к Go/.env.example**.
5. DB_PASSWORD, SESSION_SECRET и пользовательские пароли оставить в `/etc/itmap/{main,dev}.env`. Для деплоя бинарника Actions их не нужны. Не пересоздавать env при каждом релизе, не включать в artifact или Docker layers. Для private GHCR нужен отдельный pull-доступ сервера; при передаче tar по SSH registry не обязателен.
6. Включить branch protection/rulesets, обязательные проверки и защиту изменений workflow/приёмника. Политика reviewers и main-публикации согласуется владельцем. Автоматический деплой после проверок не означает автоматический merge PR.
7. Убедиться, что обязательный CI действительно запускается на push нужных веток. Обычные PR/основные push-триггеры сохранены; включённый publish.yml вызывает **оба** набора через workflow_call на push подготовленной Go-ветки, даже без PR. Нельзя заменять отсутствие проверок «зелёной» публикацией.

GitHub Actions workflow на push берётся из соответствующей ветки. Наличие файла только в main не включает его в старой ветке! Перед включением схемы перенесите контроллер во все разрешённые рабочие ветки и определите поведение непригодных/архивных веток. Если нужен охват вообще всех ref, включая ветки без workflow, требуется доверенный приём repository push webhook/контроллер; такой сервис отдельно реализуется и проверяется. Не обещайте всеобщую регистрацию веток одним YAML, отсутствующим в них.

## 3. Структура workflow и условия публикации

Реализованная последовательность jobs (native):

| Job | Что делает | Доступ к серверу |
| --- | --- | --- |
| register | фиксирует slot/ref/SHA и порядок push в durable journal до длительных тестов | только ограниченная регистрация |
| checks | source/history, Go vet/race/mod verify/tidy diff/tagged build, React build | нет |
| mariadb | существующий disposable schema/storage → seed → business → авторизованный API/browser gate | нет; только синтетические CI-секреты |
| package | собирает бинарник+SPA из проверенного точного SHA либо Docker image; создаёт digest/manifest | нет |
| deploy | проверяет кандидата/CI, передаёт immutable artifact и запрашивает переключение одной службы | ключ только своего Environment |
| report | записывает ref/SHA/digest, исход CI/deploy/rollback, URL и время | без печати env/cookies |

Все jobs используют один SHA и зафиксированные lockfile. Публикация зависит от **обоих** обязательных наборов, не только Go build. Проверять head_sha и заключение success, а не находить «какой-то зелёный» запуск ветки. Skipped/cancelled/timed_out/отсутствующий gate блокируют публикацию. Fork/внешний PR не получает deploy secrets. Сторонние Actions и container builders зафиксировать на проверенные версии/digest по принятой политике.

Исторический упрощённый фрагмент ниже — не исполняемый workflow. Актуальный publish.yml намеренно не использует отмену общих jobs: сериализация и stale-guard находятся на сервере; delete routing вычисляется из payload.

```yaml
on:
  push:
    branches: ['**']
  delete: {}
permissions:
  contents: read
  actions: read
# concurrency уменьшает число работ, но не заменяет серверную проверку кандидата.
concurrency:
  group: itmap-${{ github.ref_name == 'main' && 'main' || 'dev' }}
  cancel-in-progress: true
```

Delete-событие нужно разбирать по payload ref/ref_type: github.ref_name в нём может указывать default branch; приведённую общую concurrency для delete необходимо заменить вычисленным slot либо обрабатывать удаление отдельным workflow. Не давать delete-событию случайно отменять main-публикацию. Для main желательно не прерывать уже начатое серверное переключение; отмена runner не завершает удалённый процесс безопасно. Основная защита — серверный приёмник и журнал состояния, а не флаг cancel-in-progress.

Если все push обрабатывает один неизменный workflow, его `run_number` можно использовать как последовательность **созданных этим контроллером запросов**, с отдельным пространством имён/version. Это не Git commit timestamp. При переименовании/пересоздании workflow, потере журнала или первичной регистрации нужен явный reset/инициализация оператором; не сравнивать номера разных workflow как универсальные GitHub push-времена. Повторный run сохраняет тот же выбор, новый run_attempt лишь обновляет результат того же запроса.

## 4. Что обязан делать серверный приёмник

Контракт реализован GO-056/057 и тестируется на синтетических каталогах/процессах; перед включением подтвердить его на вашем сервере:

1. При регистрации проверить репозиторий, разрешённого отправителя, slot, ref и полный SHA; записать request ID/порядок/ref/SHA атомарно. Старый запоздалый запрос не должен затереть новый. Никакие ref/имена из event не интерполировать в shell, путь или systemctl-команду; slot только main/dev.
2. При получении артефакта проверить размер, SHA-256, точный SHA и соответствие текущему кандидату; запретить path traversal, symlink/hardlink и неожиданные файлы tar. Разрешённая структура native-релиза: `itmap`, `web/**` и фиксированный metadata manifest. Сам код приёмника лежит отдельно, root-owned, и не обновляется из dev artifact.
3. Под **серверной** блокировкой одного контура ещё раз сверить кандидата; старый run после нового успешного релиза обязан получить отказ. Запомнить previous release; развернуть новый каталог, атомарно сменить current, перезапустить только нужную службу. Runtime-пользователь не может изменять релизы/env/приёмник. Для Docker сохранять image digest и параметры запуска отдельно от образа.
4. Дождаться liveness=200, текущего readiness=503 с business_api_not_migrated и read-only smoke; проверить TLS/вход по согласованному сценарию без вывода пароля/cookie. До снятия release gate не подменять проверку ожиданием readiness=200.
5. При неуспехе вернуть предыдущую ссылку/образ и перезапустить, проверить откат, зафиксировать failure даже при успешном восстановлении. При первой установке без previous остановить неуспешный процесс и оставить диагностический результат. Не трогать БД, DNS и соседний контур.
6. Сохранить successful/failed/superseded, ref/SHA/digest/CI IDs и previous/current. Даже если SSH оборвался, серверная операция должна дойти до определённого состояния; следующий job читает результат вместо слепого повтора. Блокировка охватывает переключение, проверки и rollback.

Одного `ssh 'git pull && go build && systemctl restart'` недостаточно: branch может обновиться между командами, web и binary разойтись, а старый job перезаписать новый. Нельзя компенсировать это continue-on-error, пропусками CI или отключением авторизации.

## 5. Откат и контрольная точка

Хранить несколько предыдущих артефактов, SHA-256 и ref/SHA журнала; secrets хранятся отдельно. Native: вернуть предыдущий current и перезапустить службу. Docker: запустить предыдущий digest с тем же конфигом. Это откат **кода**, не записей БД. При несовместимой миграции требуется отдельный проверенный план восстановления; автоматически импортировать старый дамп нельзя.

Для каждого запуска отчёт должен включать slot, ref, SHA, digest, два CI run ID, исход server smoke и при необходимости rollback. GitHub Deployment/Environment может показывать историю домена, но журнал сервера остаётся нужен для разрешения гонок. Не удалять релиз при активной службе и не выполнять автоматическую очистку БД/volume. После merge родительского stacked PR актуализировать базу оставшихся PR: слияние в уже закрытую родительскую ветку не доставляет код в main.

## 6. Приёмка автоматики до её включения

Проверить на изолированном сервере: новый push B опережает медленный A; A не перезаписывает B; красный B сохраняет работающий dev без скрытого выбора A; rerun A не становится новым кандидатом; force-push/удаление/непригодная ветка; отмена Actions/обрыв SSH/перезапуск сервера; ошибка старта с успешным и неуспешным rollback; main и dev не меняют соседнюю БД/службу. Убедиться, что ключ dev не может обратиться к main. Изолированные unit/protocol/native CI проверки входят в GO-056/057; реальный SSH/systemd/сервер, reboot/отмена сетевого соединения и TLS ещё требуют отдельной инфраструктурной приёмки.
