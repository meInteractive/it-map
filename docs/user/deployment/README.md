# Запуск и развёртывание it-map

Инструкция для текущего **ограниченного Go-приложения**, а не подтверждение завершения миграции. Код хранится в [meInteractive/it-map](https://github.com/meInteractive/it-map). Go обслуживает API и собранный React; Node.js нужен при сборке, отдельный Node-сервер при работе Go не нужен.

1. [Локальный запуск и переменные окружения](LOCAL.md).
2. [Свой сервер без Docker: MariaDB, systemd, HTTPS](SERVER.md) — основной вариант; [отличия Ubuntu 20.04 LTS](UBUNTU-20.md).
3. [Вариант с Docker](DOCKER.md) — Linux, тот же Go-код и локальная MariaDB.
4. [Две ветки, выбор dev-релиза, обновление и откат](RELEASES.md).
5. [Установка приёмника](RECEIVER.md) и [включение GitHub Actions](ACTIONS.md).

Публичные примеры используют `app.example.org` и `app-dev.example.org`; замените их своими доменами. Реальные адреса и секреты в Git не нужны. Kubernetes не используется.

## Что работает и чего ждать

В проверенной ветке доступны вход/выход/сессии, React SPA, чтение компаний, карточек, вакансий, откликов и задач. В GitHub CI выполняются реальные синтетические Go → MariaDB → API и desktop/mobile проверки трёх аккаунтов. Часть операций записи реализована, но полный перенос и приёмка всех сценариев ещё не завершены. Парсер, backup/restore, внешние интеграции и Google OAuth/sync в Go не готовы целиком. Старый GPT Sites/D1 продолжает работать независимо.

Без БД можно запустить интерфейс и авторизацию; бизнес-маршруты возвращают 503, а не выдуманные данные. С MariaDB требуется заранее подготовленная совместимая схема. Приложение **не создаёт и не мигрирует БД при старте**. `APP_ENV=production` намеренно запрещён кодом. Оба домена пока могут быть только ограниченными тестовыми контурами с `APP_ENV=staging`; имя main не отменяет этот запрет. Открытие рабочего сервиса требует отдельной приёмки и решения по cutover.

## Зависимости и версии

| Компонент | Минимум для этой инструкции | Рекомендуется / подтверждено |
| --- | --- | --- |
| ОС сервера | Linux с systemd; контейнерный вариант требует Linux host networking | Ubuntu 24.04 LTS; Ubuntu 20.04 LTS — условный вариант по [UBUNTU-20.md](UBUNTU-20.md) |
| Go при сборке | 1.23 согласно go.mod; проверена 1.23.12 | 1.27.3, принята для проекта и проверена в облачной среде; поддерживаемый security patch |
| Node.js при сборке | 24 (`package.json: engines`) | актуальный patch ветки 24; локально проверена 24.19.0 |
| npm при сборке | 11 для поддерживаемого здесь окружения | 11.9.0; `npm ci`, lockfile не пересоздавать |
| MariaDB | 10.3.32; схема использует MariaDB collation/JSON/триггеры | Проверки совместимости на точной 10.3.32 и ветке 10.11; результаты — [GO-334](../../dev/MARIADB_103_COMPATIBILITY.md). Для новой установки предпочтительна поддерживаемая ветка. MySQL не считается заменой |
| Nginx | 1.18 для использованных директив; ранее syntax проверен на 1.24 | поддерживаемый пакет ОС с security updates; TLS 1.2/1.3 |
| systemd | 247+ для ProtectProc; 245 с адаптацией unit | Ubuntu 24.04 — штатный 255; для Focal см. [UBUNTU-20.md](UBUNTU-20.md) |
| Git | на runtime не нужен при доставке готового артефакта | Git 2.43 проверен; checkout/build выполняет CI |
| curl, CA certificates, OpenSSL | поддерживаемые пакеты ОС | HTTPS-проверки, генерация секретов; TLS verification не отключать |
| Python | код приёмника 3.10+; выбирать поддерживаемую ветку | 3.12 с security patch, штатный в 24.04; на Focal отдельная установка |
| Docker (необязательно) | Engine 24+ с BuildKit для Dockerfile | поддерживаемый Engine; локальный демон 28.4.0. Compose не требуется |
| Chromium / Playwright (только e2e) | версия Chromium, установленная закреплённым Playwright | `npm ci`, затем `npx playwright install --with-deps --only-shell chromium`; Playwright 1.64.1 |

Для минимальной runtime-машины достаточно бинарника Go, `web/` из Vite-сборки, CA bundle, MariaDB и reverse proxy; Go/Node/npm/Git можно оставить на сборочной машине. RabbitMQ, Redis, D1, Wrangler и Kubernetes текущему Go-запуску не нужны. `npm run build`, `npm start` и `npm run dev` относятся к старому Worker; здесь используется **`npm run build:web`**.

Практическая отправная точка: 2 vCPU, 4 GiB RAM для двух небольших runtime-процессов и MariaDB; для сборки React/Go на том же сервере лучше 4 vCPU/8 GiB или отдельный builder. Это рекомендация, не результат нагрузочного теста. Размер диска определяется БД, журналами и политикой резервного копирования; место под резервные копии должно быть вне каталога релизов.

## Что ещё нужно определить перед реальным запуском

- ОС и архитектуру сервера, доступ администратора, кто управляет DNS/TLS/firewall и резервными копиями.
- Отдельные main/dev БД и пользователей ОС; по выбору пользователя одна SQL-учётная запись/пароль для обеих БД, отдельные SESSION_SECRET/пароли входа и источник **согласованной** схемы/тестовых данных. Не использовать один рабочий DB_NAME для двух веток.
- Выбран автоматический запуск деплоя из GitHub Actions. Реализованы native workflow/packer/SSH client и receiver GO-056/057; реальный сервер и его Environments ещё не подключены.
- Для автоматики: устойчивый журнал push-событий, права доверенных авторов dev-кода, блокировка параллельных деплоев и проверка обязательного CI на точном SHA. Детали в RELEASES.md.
- Приёмка текущих ограничений, RPO/RTO и разрешение на работу с реальными данными. Эти документы не снимают существующие release gates.

## Проверка этой инструкции (25.10.2026)

Сверены все 14 runtime-переменных Go: пропусков в `.env.example` нет. Проверены локальные Markdown-ссылки. Dockerfile действительно собран с Go 1.27.3/Node 24 по lockfile; итоговый nonroot/read-only контейнер без БД отдал SPA и health, сохранил закрытый readiness, выполнил синтетические 401 → login 303 → session 200 без вывода cookie. Контейнер остановлен после проверки. Nginx 1.24 подтвердил syntax обоих шаблонов с временным тестовым сертификатом, без сетевой публикации; systemd-analyze проверил unit со временно подставленными существующими путями.

Не проверены: установка Ubuntu на реальном сервере, DNS/ACME/внешний HTTPS, запуск двух live DB-контуров, перезагрузка сервера, реальный OpenSSH/systemd приёмник и rollback на вашем сервере (код автоматики и synthetic CI описаны в ACTIONS.md). Это отдельные acceptance gates, а не следствие успешной сборки документации/образа.

HTTPS/proxy и expiry/relogin: [сценарий приёмки auth](AUTH-ACCEPTANCE.md). Локальный TLS harness не закрывает проверку настоящего staging-домена.
