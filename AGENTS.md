# it-map: правила для Codex Cloud

**Назначение.** it-map — карта московских IT-работодателей, вакансий и откликов с CRM и конвейером поиска вакансий. Этот репозиторий — **переходная версия**, не подтверждённая как production-ready.

## Где что находится

- `cmd/itmap/main.go` — вход Go-приложения; `internal/` — Go-пакеты; `go.mod` — модуль `itmap`, Go 1.23.
- `internal/httpapi/` — HTTP через стандартный `net/http` (`ServeMux`), **не Gin**; `internal/storage/` — `database/sql`, MariaDB-драйвер за build tag `mariadb`.
- `frontend/`, `web/`, `vite.web.config.ts` — React/TypeScript и Vite. `server/`, `build/`, `db/schema.ts` — старый JavaScript/D1-код для сравнения контрактов, а не Go-production.
- Прочитать `PLANS.md`, `docs/dev/ARCHITECTURE.md`, `docs/user/DATABASE.md` (историческая D1), `docs/dev/MARIADB.md` (целевая БД), `docs/dev/DECISIONS.md`, `tasks/README.md`; API: `docs/dev/LEGACY_API_BASELINE.md` и `docs/user/API.md`.

## Неприкосновенные ограничения

1. GPT Sites, его D1 и Site Automation **продолжают работать**, пока пользователь отдельно не утвердил cutover. Не запускать с этого репозитория старые автоматизации, фоновые задания против production или платные провайдеры без разрешения.
2. Новый Go-бекенд разрабатывать отдельно. Не ломать работающие API/парсеры; в спринте 1.1 сохранять метод, URL, права, JSON, коды статусов, версии записей и поведение React.
3. MariaDB на том же сервере — целевая БД. Основа — исходная структура D1 с минимально необходимыми изменениями; **не изменять/удалять реальные данные и не выполнять DDL без отдельного согласования**. D1 и MariaDB не синхронизируются автоматически.
4. Никаких реальных `.env`, секретов, токенов, SQL-дампов, резервных копий, персональных данных, зашифрованных ключей или скриншотов приватных данных в Git, PR, логах и тестовых фикстурах. Использовать только синтетические тестовые данные; `.env.example` без значений.
5. **Запрещены автоматический production-деплой, прямые изменения `main` и `master`, автоматическое слияние PR**, переключение домена, импорт/синхронизация реальных БД и необратимые операции. Для них всегда требуется отдельное явное утверждение.

## Правила инженерной работы

- Новые комментарии в коде писать на русском языке. Существующие английские комментарии не переводить попутно: их перевод запланирован отдельной низкоприоритетной задачей GO-111 во втором спринте. Идентификаторы и технические директивы сохранять.
- Работать в отдельной ветке `codex/GO-NNN-short-title`, **только по конкретной задаче или утверждённому диапазону** из `tasks/`. До изменений прочитать относящиеся к задаче исходники, зависимости и контракт старого API. Последовательно выполнять задачи утверждённого плана с учётом зависимостей; не расширять архитектуру за его пределы.
- Go: использовать существующие `cmd/` и `internal/`, `context.Context`, параметризованные запросы, ограниченные транзакции и минимальные интерфейсы у потребителей. Сохранять `net/http` до отдельного архитектурного решения. Ошибки возвращать с контекстом, но без DSN, секретов и персональных данных; не скрывать ошибку успешным HTTP-ответом.
- DB: новые миграции — отдельные версионированные, рецензируемые файлы; не менять исходный D1-справочник `docs/user/DATABASE.md`. Сначала тест на изолированной MariaDB и восстановимость. Учитывать FK, триггеры, revision/CAS, идемпотентность платных вызовов.
- API: сначала тест контракта (включая ошибки/авторизацию), затем реализация. Любое несовместимое изменение требует согласования и обновления фронтенда/документации.
- Проверки согласно затронутому коду: `gofmt`, `go vet ./...`, `go test -race ./...`, `go build ./cmd/itmap`, `npm run build:web`, `python3 scripts/check-public-repo.py`; для MariaDB: `go test -tags mariadb ./...` и staging-интеграция **только при доступном драйвере и безопасной тестовой БД**. Если проверка недоступна/падает, явно указать её статус, не считать выполненной.

## Задачи, Git и отчёт

1. Проверить зависимости задачи и критерии в `tasks/SPRINT-*.md`; если задача крупная — предложить разделение **до реализации** с новыми неизменяемыми ID.
2. Сделать одну самостоятельно проверяемую порцию изменений. Запустить проверки; ошибки исправить или честно сообщить блокировку. После успешных проверок, коммита и создания PR сразу переходить к следующей доступной задаче утверждённого плана без ожидания merge/приёмки. При небезопасном исправлении или архитектурном вопросе зафиксировать блокировку и не брать зависящие от неё задачи.
3. Для каждой задачи создать отдельную ветку от проверенной вершины предыдущей и отдельный **stacked PR** в предыдущую ветку; первый PR стека направлять в `main`. Не ветвиться заново от устаревшего `main`. Не выполнять автоматический merge и не удалять действующий код без отдельного разрешения; не закрывать задачу на основании только сгенерированного кода. `[x]` ставить лишь при выполненных критериях и зафиксированном результате (коммит/PR); частичную реализацию описывать без отметки завершения.
4. В отчёте по задаче указать: `GO-NNN`, ветку/коммит/PR, что изменено, список файлов, тесты (`успех`/`ошибка`/`не запускались`), сопоставление со старым API, риски и ограничения, нужна ли ручная приёмка, следующую разрешённую задачу. Для реальных данных, продуктивной инфраструктуры и архитектурных решений требуется отдельное разрешение. Если GitHub API/прокси недоступны, сохранить локальные коммиты и отчёт; не заявлять о создании PR без подтверждения. Не останавливаться ради промежуточной приёмки. Заголовки, описания и комментарии новых PR — на русском.

Этот файл задаёт правила, но не заменяет техзадания в `tasks/` и не разрешает автоматических действий с production.
