# it-map: правила для Codex Cloud

**Назначение.** it-map — карта московских IT-работодателей, вакансий и откликов с CRM и конвейером поиска вакансий. Этот репозиторий — **переходная версия**, не подтверждённая как production-ready.

## Где что находится

- `cmd/itmap/main.go` — вход Go-приложения; `internal/` — Go-пакеты; `go.mod` — модуль `itmap`, Go 1.23.
- `internal/httpapi/` — HTTP через стандартный `net/http` (`ServeMux`), **не Gin**; `internal/storage/` — `database/sql`, MariaDB-драйвер за build tag `mariadb`.
- `frontend/`, `web/`, `vite.web.config.ts` — React/TypeScript и Vite. `server/`, `build/`, `db/schema.ts` — старый JavaScript/D1-код для сравнения контрактов, а не Go-production.
- Прочитать `PLANS.md`, `docs/dev/ARCHITECTURE.md`, `docs/user/DATABASE.md` (историческая D1), `docs/dev/MARIADB.md` (целевая БД), `docs/dev/DECISIONS.md`, `tasks/README.md`; API: `docs/dev/LEGACY_API_BASELINE.md` и `docs/user/API.md`.
- **Отдельные технические подзадачи спринта:** [`tasks/sprint-01-subtasks/`](tasks/sprint-01-subtasks/README.md), стабильные IDs/PR/CI. **Текущее состояние 09.11:** GO-434 аудит и диагностика повторов ([#283](https://github.com/meInteractive/it-map/pull/283), [#291](https://github.com/meInteractive/it-map/pull/291)), GO-433 частичная стоимость ([#284](https://github.com/meInteractive/it-map/pull/284)–[#286](https://github.com/meInteractive/it-map/pull/286), [#289](https://github.com/meInteractive/it-map/pull/289)), GO-436 уникальные вакансии ([#287](https://github.com/meInteractive/it-map/pull/287)) и read-only HH-диагностика ([#292](https://github.com/meInteractive/it-map/pull/292)) уже в `main`. **Ближайшая независимая очередь: GO-119 документация → GO-117 Playwright** с учётом release gate спринта 1.1. Исторические задачи S11-DIAG остаются в прежних документах, но не задают порядок новых PR. [Справочник диагностики](docs/dev/PARSER_DIAGNOSTICS_PLAYBOOK.md) содержит исторические методы и пометки, которые могут устаревать.
- **Передачи дел между чатами/Codex:** читать [каталог `docs/dev/handoff/`](docs/dev/handoff/README.md), начиная с наиболее нового `HANDOFF-YYYY-MM-DD.md`, затем сверять со свежими `main`, PR/CI и задачами. Вся история handoff хранится только там; старые снимки не переписывать. **Новый handoff** создавать именно `docs/dev/handoff/HANDOFF-YYYY-MM-DD.md` (если за день несколько — суффикс `-02`, `-03`); сохранять подробный технический контекст, но **не** приватные серверные адреса/ключи/доступы, счета, дампы или персональные данные. **Двухконтурная передача (решение владельца 10.11.2026):** публичный handoff/PR/issue содержит только безопасные инженерные итоги, архитектуру, подтверждённые метрики, SHA, CI и шаги. После каждой законченной задачи отдельно резюмировать в пользовательском чате закрытые операционные факты (без сырых токенов, ключей, паролей, персональных записей и дампов). Закрытые данные из чата не переносить в Git. Согласованные владельцем обезличенные диагностические агрегаты разрешается публиковать в handoff. Новый handoff-файл надо начинать при каждом новом диалоге. Далее в него надо добавлять важные изменения и выводы, сделанные в ходе текущего диалога. Это нужно для продолжения разработки в новом чате при переполнении окна контекста в текущем диалоге.
- **Сверка архитектуры перед Codex:** [GO-119 — матрица реализованного, CI и ограничений](docs/dev/GO-119-ARCHITECTURE-EVIDENCE.md), [текущий статус миграции](docs/dev/GO_MIGRATION_PROGRESS.md) и [последний handoff](docs/dev/handoff/HANDOFF-2026-11-10-02.md). HH/Apify Go-парсер реализован, но это не приёмка всех источников, платных операций и непрерывного Go Worker. [Issue #290](https://github.com/meInteractive/it-map/issues/290) закрыта после операторского подтверждения возобновления HH; исторические пробелы — [#293](https://github.com/meInteractive/it-map/issues/293). **Не** запускать GO-431, production-миграции, сканирования, backfill или изменение рабочих бюджетов без отдельного разрешения владельца.
- При запросе «Настройка сервера» открыть `.agents/skills/itmap-server-setup/SKILL.md`; он описывает доступ Codex через Tailscale и подготовку ограниченного релизного пользователя.

## Неприкосновенные ограничения

1. GPT Sites, его D1 и Site Automation **продолжают работать**, пока пользователь отдельно не утвердил cutover. Не запускать с этого репозитория старые автоматизации, фоновые задания против production или платные провайдеры без разрешения.
2. Новый Go-бекенд разрабатывать отдельно. Не ломать работающие API/парсеры; в спринте 1.1 сохранять метод, URL, права, JSON, коды статусов, версии записей и поведение React.
3. MariaDB на том же сервере — целевая БД. Основа — исходная структура D1 с минимально необходимыми изменениями; **не изменять/удалять реальные данные и не выполнять DDL без отдельного согласования**. D1 и MariaDB не синхронизируются автоматически.
4. Никаких реальных `.env`, секретов, токенов, SQL-дампов, резервных копий, персональных данных, зашифрованных ключей или скриншотов приватных данных в Git, PR, логах и тестовых фикстурах. Использовать только синтетические тестовые данные; `.env.example` без значений.
5. **Запрещены автоматический production-деплой, прямые изменения `main` и `master`, автоматическое слияние PR**, переключение домена, импорт/синхронизация реальных БД и необратимые операции. Для них всегда требуется отдельное явное утверждение.

## Правила инженерной работы

- Новые комментарии в коде писать на русском языке. Существующие английские комментарии не переводить попутно: их перевод запланирован отдельной низкоприоритетной задачей GO-111 во втором спринте. Идентификаторы и технические директивы сохранять.
- Работать в отдельной ветке `codex/GO-NNN-short-title`, **только по конкретной задаче или утверждённому диапазону** из `tasks/`. До изменений прочитать относящиеся к задаче исходники, зависимости и контракт старого API. Последовательно выполнять задачи утверждённого плана с учётом зависимостей; не расширять архитектуру за его пределы.
- Go: использовать существующие `cmd/` и `internal/`, `context.Context`, параметризованные запросы, ограниченные транзакции и минимальные интерфейсы у потребителей. Сохранять `net/http` до отдельного архитектурного решения. Ошибки возвращать с контекстом, но без DSN, секретов и персональных данных; не скрывать ошибку успешным HTTP-ответом.
- DB: новые миграции — отдельные версионированные, рецензируемые файлы; не менять исходный D1-справочник `docs/user/DATABASE.md`. Сначала тест на изолированной MariaDB и восстановимость. Учитывать FK, триггеры, revision/CAS, идемпотентность платных вызовов.
- API: сначала тест контракта (включая ошибки/авторизацию), затем реализация. Любое несовместимое изменение требует согласования и обновления фронтенда/документации.
- Проверки согласно затронутому коду: `gofmt`, `go vet ./...`, `go test -race ./...`, `go build ./cmd/itmap`, `npm run build:web`, `python3 scripts/check-public-repo.py`; для MariaDB: `go test -tags mariadb ./...` и staging-интеграция **только при доступном драйвере и безопасной тестовой БД**. Если проверка недоступна/падает, явно указать её статус, не считать выполненной.
- Каждый новый или изменённый тест запускать непосредственно штатной командой (`node scripts/test-*.mjs`, `npx playwright test ...` и т. п.) и проверять код завершения. Режимы, скрывающие необработанные ошибки или превращающие падение в предупреждение, не подтверждают прохождение теста. Если отдельный тест не входит в CI, указать это в PR и выполнить его вручную до приёмки.
- Для поддерживаемого React/Vite TypeScript использовать закреплённый Prettier 3.6.2: `npm run format` форматирует **всю** область `frontend/`, `shared/`, `web/main.tsx`, `vite.web.config.ts`, а `npm run format:check` проверяет её целиком и обязательно запускается в PR-CI. Legacy `server/`, `app/`, generated и миграционные эталоны не переформатировать. Подробности: [GO-114](docs/dev/GO-114-FORMATTING.md).
- При изменении JavaScript-файлов, которые сборщик не разбирает (например, `public/service-worker.js`), дополнительно выполнять `node --check` для каждого такого файла. Для изменений React выполнять `npm run build:web`; для затронутых браузерных сценариев запускать соответствующие Playwright-тесты на синтетических данных в desktop и mobile либо подтверждать их прохождение в CI на том же коммите.

## Задачи, Git и отчёт

1. Проверить зависимости задачи и критерии в `tasks/SPRINT-*.md`; если задача крупная — предложить разделение **до реализации** с новыми неизменяемыми ID.
2. Сделать одну самостоятельно проверяемую порцию изменений. Для каждого ID сопоставить критерий с наблюдаемым поведением и результатом конкретного теста; наличие похожего кода или успешная сборка сами по себе не закрывают сценарий. Запустить проверки; ошибки исправить или честно сообщить блокировку. На приёмку передавать PR с пройденными обязательными проверками; если проверка объективно недоступна, явно описать блокировку, оставить соответствующие ID незавершёнными и не заявлять, что PR принят. После успешных проверок, коммита и создания PR сразу переходить к следующей доступной задаче утверждённого плана без ожидания merge/приёмки. При небезопасном исправлении или архитектурном вопросе зафиксировать блокировку и не брать зависящие от неё задачи.
3. Для каждой задачи создать отдельную ветку от проверенной вершины предыдущей и отдельный **stacked PR** в предыдущую ветку; первый PR стека направлять в `main`. Не ветвиться заново от устаревшего `main`. Перед передачей stacked PR проверить, что его базовая ветка актуальна; если она продвинулась, обновить зависимую ветку, разрешить конфликты и повторить проверки. Проверять CI и возможность слияния именно на последнем SHA каждой ветки, не переносить статус со старого коммита. Не выполнять автоматический merge и не удалять действующий код без отдельного разрешения; не закрывать задачу на основании только сгенерированного кода. `[x]` ставить лишь при выполненных критериях и зафиксированном результате (коммит/PR); частичную реализацию описывать без отметки завершения.
4. В отчёте по задаче указать: `GO-NNN`, ветку/последний SHA/PR, что изменено, список файлов, доказательства по каждому ID, фактически выполненные тесты (`успех`/`ошибка`/`не запускались`), CI на последнем SHA, сопоставление со старым API, риски и ограничения, нужна ли ручная приёмка, следующую разрешённую задачу. Для реальных данных, продуктивной инфраструктуры и архитектурных решений требуется отдельное разрешение. Если GitHub API/прокси недоступны, сохранить локальные коммиты и отчёт; не заявлять о создании PR без подтверждения. Не останавливаться ради промежуточной приёмки. Заголовки, описания и комментарии новых PR — на русском.

Этот файл задаёт правила, но не заменяет техзадания в `tasks/` и не разрешает автоматических действий с production.
