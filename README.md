# IT Map

**CRM для поиска работы, карта IT-работодателей и автоматизированный мониторинг вакансий. А ещё практический проект по превращению AI-прототипов в самостоятельные приложения на Go.**

IT Map начинался как инструмент для системного поиска управленческих позиций в IT. Постепенно он вырос в приложение с собственной базой работодателей, CRM, агрегатором вакансий, интеграциями с внешними источниками и конвейером обработки данных с помощью языковых моделей.

Первая версия создана на GPT Sites. Сейчас я переношу её на Go и MariaDB, сохраняя существующий React-интерфейс. Параллельно выстраиваю процесс разработки, в котором ИИ помогает быстрее реализовывать задачи, а архитектура, требования, проверка качества и управление изменениями остаются под контролем человека.

## Что умеет IT Map

Основные возможности исходного приложения:

- **Карта работодателей и CRM.** Каталог IT-компаний, фильтры, рейтинги, избранное, история взаимодействия и отклики на вакансии.
- **Мониторинг вакансий.** Сбор вакансий с сайтов компаний и внешних платформ, включая интеграции с hh.ru, rabota.ru и Telegram.
- **Обработка вакансий с ИИ.** Предварительная классификация, извлечение структурированных данных, определение релевантности и устранение дубликатов.
- **Управление поиском работы.** Задачи, статусы откликов, история изменений, интеграция с Google Calendar.
- **Автоматизация.** Планирование фоновых заданий, очереди обработки, повторные попытки, контроль ограничений внешних сервисов.
- **Диагностика.** Мониторинг ошибок, работы парсеров, результатов обработки и расходов на ИИ-модели.

Проект используется как функциональный прототип, на котором можно проверять не только пользовательские сценарии, но и подходы к организации разработки.

## Зачем я развиваю этот проект

Меня интересует практическое применение ИИ не только для написания кода, но и для ускорения всего процесса разработки.

GPT Sites позволяет быстро перейти от идеи к работающему приложению и проверить продуктовые гипотезы. Но по мере развития продукта возникают обычные инженерные задачи: сопровождение, тестирование, управление данными, интеграции, безопасность, предсказуемые релизы и независимость от платформы прототипирования.

На примере IT Map я отрабатываю процесс перехода от быстрого AI-прототипа к приложению с контролируемой архитектурой и инфраструктурой.

**Цель проекта — сделать этот переход максимально воспроизводимым:** определить, какую часть работы можно делегировать ИИ, где необходим инженерный контроль и какие автоматические проверки позволяют безопасно ускорять разработку.

В перспективе такой подход можно использовать для быстрого создания внутренних корпоративных инструментов, проверки гипотез и последующего развития успешных прототипов без необходимости заново проектировать продукт с нуля.

## Архитектура

Проект проходит поэтапную миграцию. Действующая версия и новая реализация пока существуют независимо.

| Компонент | Исходная версия | Целевая реализация |
|---|---|---|
| Фронтенд | React / TypeScript | React / TypeScript / Vite |
| Бекенд | JavaScript / Cloudflare Worker | Go, модульный монолит |
| База данных | Cloudflare D1 / SQLite | MariaDB |
| HTTP API | Исходный API GPT Sites | Go `net/http`, совместимые контракты |
| Фоновая обработка | Site Automation и JS-планировщик | Собственный Go-планировщик |
| Интеграции | Firecrawl, Apify, LLM API | Поэтапный перенос на Go |
| Развёртывание | Управляемая платформа | Собственный Linux-сервер, CI/CD |

Для Go выбран модульный монолит. На данном этапе это позволяет сохранить понятные границы ответственности без преждевременного усложнения инфраструктуры.

HTTP-слой построен на стандартном `net/http`, работа с БД — на `database/sql`. Бизнес-логика разделяется на модули авторизации, каталога, вакансий, откликов, задач и других предметных областей.

На последующих этапах предусмотрено развитие фоновой обработки с использованием RabbitMQ и transactional outbox. Состояние заданий и бизнес-данные при этом остаются в MariaDB.

Подробнее: [архитектура](docs/ARCHITECTURE.md), [целевая БД](docs/MARIADB.md), [архитектурные решения](docs/DECISIONS.md).

## Как организована разработка с ИИ

Я использую GPT Sites для прототипирования, а Codex — для реализации отдельных задач, рефакторинга и подготовки изменений в Go-коде.

При этом задача состоит не в том, чтобы получать как можно больше сгенерированного кода. Важнее построить процесс, результат которого можно проверить, сопровождать и развивать.

В проекте используются следующие принципы:

1. **Архитектура до реализации.** Сначала определяются границы модулей, требования к API, данным и совместимости, затем формируются задачи.
2. **Малые проверяемые изменения.** Большие этапы делятся на самостоятельные задачи с зависимостями и критериями приёмки.
3. **Контроль исходного поведения.** JavaScript-версия сохраняется как эталон. При переносе проверяются не только успешные операции, но и ошибки, права доступа, обработка данных и пограничные сценарии.
4. **Автоматизированные проверки.** Для изменений используются модульные, контрактные, интеграционные и браузерные тесты. Проверки запускаются через GitHub Actions.
5. **Управляемая работа с Git.** Отдельные ветки, коммиты и Pull Request для проверяемых частей работы. Codex может последовательно выполнять задачи, но слияние и критические изменения требуют отдельной приёмки.
6. **Изоляция окружений.** Тестовые данные и базы отделены от рабочего приложения. Миграция и развёртывание не должны нарушать работу исходной системы.

Таким образом, ИИ выступает инструментом ускорения разработки, а не заменой инженерного процесса.

Правила для AI-инструментов описаны в [AGENTS.md](AGENTS.md), план работ — в [PLANS.md](PLANS.md), задачи и критерии приёмки — в [tasks/](tasks/).

## На чём сосредоточена техническая работа

Важная часть проекта — сохранение корректности приложения при смене технологического стека.

**Совместимость API и бизнес-логики**

Перенос JavaScript → Go выполняется с проверкой контрактов на эквивалентных тестовых данных. Это особенно важно для операций с откликами, задачами, статусами и пользовательскими состояниями.

**Миграция данных**

Исходная схема D1 переносится в MariaDB с минимально необходимыми изменениями. Отдельно проверяются различия SQL-диалектов, ограничения целостности, транзакции и конкурентные операции.

**Надёжность операций**

В тестах проверяются идемпотентность, повторные запросы, конкурентная запись, управление версиями записей, откат транзакций и восстановление после сбоев.

**Фоновые задания**

Для парсера проектируется обработка с сохраняемым состоянием, блокировками заданий, повторными попытками и контролем расходов на внешние API. Это необходимо, чтобы перезапуск процесса не приводил к потере работы или неконтролируемым повторным обращениям к провайдерам.

**Сборка и выпуск изменений**

Настроены автоматические проверки Go, React, контрактов исходной системы и безопасности публичных исходников. Подготовлены сценарии публикации и отката релизов для собственного сервера. Проверки на синтетическом окружении отделены от приёмки на реальной инфраструктуре.

## Текущее состояние

Проект находится в активной разработке.

- **GPT Sites:** исходная версия продолжает работать независимо от миграции.
- **Go + React:** реализован каркас самостоятельного приложения и часть бизнес-функциональности. Выполняются автоматизированные проверки с тестовой MariaDB и браузерные сценарии.
- **Парсер и интеграции:** перенос в Go продолжается. Полный конвейер пока остаётся в исходной JavaScript-реализации.
- **Развёртывание:** подготовлена инфраструктура сборки, публикации и отката, но полноценная приёмка на целевом сервере ещё не завершена.

Новая реализация пока не заявляется как production-ready. Переход будет завершён после проверки функциональной совместимости, миграции данных, фоновых процессов, безопасности и восстановления после сбоев.

Основные этапы: функциональный перенос, повышение надёжности и безопасности, развитие очередей, финальная инженерная доводка.

Актуальный план и состояние задач: [PLANS.md](PLANS.md), [tasks/README.md](tasks/README.md).

## Открытый код и безопасность

Публичный репозиторий содержит очищенные исходники и синтетические тестовые данные. Реальные резюме, контакты, SQL-дампы, резервные копии и ключи внешних сервисов в него не включаются.

Проверка публичных исходников и доступной истории Git входит в процесс CI. Операции с рабочими данными и развёртывание на продуктивную инфраструктуру отделены от обычных задач разработки.
