# Денежная диагностика worker

`/recoveryz` также показывает число AI-попыток текущего поколения с резервом
и без записанной стоимости: отдельно выполняющихся и остальных. Эти счётчики
не являются подтверждёнными списаниями и не доказывают отсутствие расходов по
другим провайдерам или вне журнала.

## GO-431: неизвестный AI-исход при нулевом резерве

Помимо прежних счётчиков, `GET /recoveryz` показывает три
**дополнительных read-only агрегата**:

- `currentAIZeroReserveProviderUnknown` — попытки текущего поколения
  с `reserved_usd=0`, `cost_usd IS NULL`, типом одного из
  `classify_title`, `extract_vacancy`, `assign_roles`,
  `score_relevance`, а провайдером `openai` или `openrouter`.
- `schedulerHistoricalZeroReserveProviderUnknown` — такие же попытки
  **старого поколения**, определённого по `scheduler_runs`;
  выбранный провайдер может быть любым непустым, поскольку историческая
  запись может содержать старый код провайдера.
- `schedulerOrphanZeroReserveProviderUnknown` — такие же попытки без
  существующего `scheduler_runs`, то есть нельзя определить даже
  поколение по run. Если также отсутствует `scheduler_jobs`, неизвестен
  кандидат и нельзя сопоставить попытку с новой работой.

Первые два исторических счётчика — **подмножества** существующих
`schedulerHistoricalUnknown` и `schedulerOrphanUnknown`; складывать
их между собой как независимые события нельзя. Существующие агрегаты
денежных резервов не меняют смысл. Нулевая величина любого счётчика
**не доказывает**, что не было платного POST: может отсутствовать запись,
провайдер, run или durable доказательство.

### Эксплуатационное решение

`reserved_usd=0` вместе с выбранным провайдером и
`cost_usd IS NULL` — **не подтверждённая бесплатная попытка**.
Запрос мог быть отправлен до прерывания и потери ответа. Нельзя:
обнулять `cost_usd`, удалять строку, восстанавливать неизвестное списание
по предположению, снимать блокировку same-job или разрешать replay.

**Новая диагностика не меняет admission в runtime.**
Для попытки с сохранившимся `scheduler_jobs.candidate_id` действует
меж-job guard GO-431; для orphan без job-строки у него нет безопасного
ключа привязки. Глобальный запрет всех AI-заданий на основании такой
одной строки остановил бы и независимые вакансии, поэтому не включён.
Из этого следует остаточный риск повторного обращения к провайдеру
при совпадающем, но неатрибутируемом входе. Для полноценного устранения
нужны отдельный durable input fingerprint, провайдерский operation ID
и операторский reconciliation protocol, сначала в synthetic CI и
отдельном проекте миграции с backup/restore.

Для диагностики использовать только обезличенные агрегаты и read-only
проверки. Ни `/recoveryz`, ни зелёный synthetic CI не являются
разрешением на массовый перезапуск AI или платный backfill.
