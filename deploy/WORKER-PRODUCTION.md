# Подготовка постоянного worker

`itmap-worker.service.example` — шаблон для отдельного пользователя и каталога
worker. Он не устанавливается автоматически, не содержит enable-флагов или
секретов и не выполняет переключение. Бинарник и unit должны быть проверены
на точном release SHA и архитектуре сервера до установки.

Для production-профиля команда требует `APP_ENV=production`, независимый
`ITMAP_WORKER_PRODUCTION_ENABLED=1`, `ITMAP_WORKER_ENABLED=1`,
`ITMAP_PARSER_EXECUTION_ENABLED=1` и `ITMAP_WORKER_HEALTH_ENABLED=1`. Настройки
БД (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`) и
`SESSION_SECRET` поступают через защищённый EnvironmentFile; в Git сохранять
только имена переменных. БД должна быть локальной, пользователь БД не root.
Параметры и секреты должны соответствовать экземпляру приложения. Провайдеры
и сохранённые бюджетные ограничения используются существующим runtime.

Включение флагов не доказывает готовность к работе и может запустить платные
операции. До запуска необходимо проверить резервную копию, совместимость схемы,
поколение и неопределённые расходы, остановить старый scheduler и дождаться
завершения его обработки. У профиля нет распределённой блокировки старого
HTTP consumer: два исполнителя могут чередоваться. Для разных экземпляров
worker health-порт также не является распределённой блокировкой. План перехода
и отката описан в `tasks/GO-431-PRIORITY-TRANSITION.md`; единичный успешный
старт на тестовой БД не заменяет реальную приёмку.

После остановки старого consumer и установки проверенного release оператор
включает и запускает службу только в рамках согласованного переключения;
проверяет `/healthz`, `/readyz`, очередь, неопределённые резервы, ошибки и
состояние расходов. Остановка должна прекратить новые claims до возврата к
старой схеме; откат программы сам по себе не откатывает изменения БД.

Локальный `GET /hh-schedulez` показывает агрегат расписания HH и причины
ожидания scan: в том числе интервал Actor и старые неподтверждённые параметры.
Это снимок без claim и сетевых запросов к провайдерам; кандидат на запуск не
означает разрешения бюджета или фактического запуска Actor. Как и остальные
диагностические endpoints, он доступен только на loopback и ограничен общей
конкуренцией запросов.


## Локальное управление паузой для GO-447

После отдельного согласования конфигурации можно включить
`ITMAP_WORKER_RELEASE_CONTROL_ENABLED=1`. Unit создаёт приватный
`RuntimeDirectory`. Из этого каталога доступен Unix-сокет с режимом 0600.
Поддерживаются `GET /instance` и `POST /pause`, `POST /resume`.
Для POST передаются токен релиза и полученный идентификатор экземпляра.

Перед паузой оператор создаёт root-owned файл `release-hold` в корне
релизов воркера. Его содержимое — токен релиза. Права должны разрешать
чтение службе и исключать запись пользователем воркера. Если такой файл
есть при старте, допуск к обработке закрывается до запуска профилей.
После снятия файла требуется явный запрос resume для живого экземпляра.

Ответ `held` означает, что профиль остановился и новых claims нет.
Клиент receiver повторно сверяет MainPID, экземпляр и токен, а также
требует нулевых активных заданий и отсутствия блокирующих операций до
переключения. Для старых AI-попыток текущего поколения допускается
совпадение количества и digest по локальному сокету до и после паузы.
В выборку входят только записи с завершением минимум 30 минут назад,
привязанные к заданию без lease и завершённому run. Добавление, удаление
или изменение записи откладывает релиз. Статусы и резервы не изменяются. Ошибка чтения диагностики также блокирует подтверждение.
При ошибке клиент сохраняет hold, чтобы вызывающая транзакция явно
выбрала безопасное снятие паузы или восстановление. Совместный путь publish требует отдельного включения на GitHub и сервере. При `draining` он ожидает повторной проверки, а при `unsafe`
откладывает релиз. `/readyz` сообщает `release_paused` до снятия паузы.

## Первый совместный релиз

1. Оператор проверяет резервную копию, совместимость схемы и generation,
   единственный consumer и отсутствие активной или неподтверждённой работы.
2. Оператор устанавливает совместимый worker и receiver, затем проверяет
   `/instance` через локальный сокет, запущенный SHA и возможность отката.
3. Для согласованного включения на сервере требуется обычный root-owned файл
   `/var/lib/itmap-deploy/main/joint-release-enabled` без прав записи для
   группы и остальных. В GitHub Actions отдельно требуется
   `ITMAP_JOINT_RELEASE_ENABLED=true`. Несовпадение настроек останавливает
   публикацию. До включения сохраняется режим публикации API.
4. В первом проверенном publish сверяются PID и исполняемые файлы API и
   воркера, SHA активного релиза, `/readyz` и стандартный API smoke.
   При `deferred` проверяются счётчики очереди и журнала. При
   `rollback_failed` новые публикации блокируются до операторской сверки
   hold, journal, current и фактических процессов.

## Профиль сайтов компаний

`ITMAP_WORKER_FIRECRAWL_ENABLED=1` добавляет профиль `companySite` в штатный
цикл. По умолчанию профиль выключен. В production для него также требуется
`ITMAP_WORKER_RELEASE_CONTROL_ENABLED=1`. Перед включением проверьте, что старый
парсер больше не потребляет эту очередь, а у Go-воркера есть доступ к журналу
кредитов Firecrawl и действующему ключу, сохранённому в настройках.

Профиль учитывает выбранный источник `companySite`, включённый Firecrawl,
настройку автоматического сканирования источника и область избранного. В этой
версии доступны обычные одностраничные сайты без специального адаптера. Счётчики
цикла `companySite` доступны в диагностике воркера после первого тика. Во время
активного окна резерва Firecrawl совместная публикация откладывается.

В production continuous worker использует подтверждённый жёсткий лимит Apify
Free, когда консервативный резерв на чтение результатов перекрывает остаток.
Для этого баланс должен быть свежим, лимит провайдера должен укладываться в
пакет Free, все операции периода должны быть завершены и сверены. Платный
профиль этот допуск не получает. `ITMAP_APIFY_TRUST_FREE_HARD_LIMIT=0` оставляет
для воркера только консервативный расчёт.
