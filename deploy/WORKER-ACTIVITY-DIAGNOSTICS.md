# Активность worker и очереди

Локальный `GET /activityz` показывает агрегаты за последние 24 часа по часам
БД и текущему поколению: созданные Actor, успешные Actor с записанной
стоимостью, активные операции или операции без стоимости, завершённые scan,
созданные, завершённые и неуспешные задания pipeline. Конечная точка только
читает БД, не раскрывает суммы и идентификаторы и использует общее ограничение
одновременных диагностических запросов.

Это сохранённые события всех исполнителей текущего поколения, а не доказанная
атрибуция конкретному процессу, полноты архива или завершённого импорта новой
вакансии. Время Actor относится к созданию операции, а статус — к моменту
снимка; для завершённых заданий используется время завершения. При смене
поколения или ошибке БД снимок недоступен.

## GO-431: отделять выполнение импорта от публикаций

Новые **дополнительные** поля `GET /activityz` за последние 24 часа
по времени MariaDB и *текущему поколению*:

- `importCreateOperations` — число завершённых import-job с подтверждённым
  `vacancy_import_operations.status='success', action='create'`.
- `importUpdateOperations` — подтверждённые `action='update'`.
- `importUnchangedOperations` — подтверждённые `action='unchanged'`.

Для каждого требуется связь `scheduler_jobs.id = vacancy_import_operations.id`,
тип `import_vacancy`, статус job `completed`, совпадение `candidate_id`
в job и receipt, непустой `vacancy_id`; окно берётся по
`scheduler_jobs.completed_at`. Числа не учитывают потерявшие job,
другие поколения, старые операции и удалённые связи: это **наблюдаемые
успешные операции**, а не полный исторический аудит. Каждое
`create` — операция, **не обязательно новая уникальная карточка**:
несколько кандидатов/импортов могут ссылаться на один `vacancy_id`.
`update` и `unchanged` не добавляют уникальные вакансии.

Для подсчёта реально **новых уникальных карточек** использовать
`newVacancies` из отдельной воронки `internal/parser/funnel.go`
и принятый контракт GO-436: первый успешный `CREATE` на один
`vacancy_id`, без повторного учёта поздних кандидатов.
При сравнении окон учитывать, что воронка группирует события по
московской календарной дате, а `/activityz` — скользящее 24-часовое
окно по часам БД; это разные знаменатели и область данных.

### Интерпретация ответов без платных действий

| Наблюдение | Что известно | Чего это НЕ доказывает |
|---|---|---|
| `/readyz` = 200, `ready=true` | Все три профиля недавно отчитались без failure | Были новые вакансии, опубликованы карточки, нет проблем у провайдера |
| `/queuez`: `due=0, running=0` | Сейчас нет соответствующих ожидающих/выполняющихся jobs текущего поколения | Не было ошибок, импортов или новых исходных вакансий |
| `/activityz`: `scanCompleted>0`, `import*Operations=0` | Были завершённые scan, но нет подтверждённых импортов в выбранном окне | Провайдер вернул подходящие вакансии или фильтры разрешили импорт |
| `pipelineCompleted>0`, `import*Operations=0` | Завершились какие-то стадии конвейера | Было успешно сохранение карточки |
| `importCreateOperations>0` | В этом окне были успешные операции с действием create | Столько же уникальных новых вакансий |
| `importUnchangedOperations>0` | Подтверждён повторный/неизменённый импорт | Карточка появилась впервые |
| `/recoveryz`: есть неясные резервы | Сохранилась денежная неопределённость | Провайдер списал или не списал средства |
| `/activityz` возвращает HTTP 503 | Снимок не получен / занят общий read-only gate | Нулевой результат или ноль вакансий |

Одинаковые кандидаты после нескольких scan, `match`/`reject`,
пустые результаты, дубли, старые `failed`, повторные `unchanged`,
смена generation и частично полученные данные требуют отдельного
разбора. Не изменять БД и не запускать Actor/AI POST ради диагностики.
`/healthz`, `/profilez`, `/hh-schedulez` также имеют собственные
ограниченные контракты, ни один не является доказательством новых публикаций.
