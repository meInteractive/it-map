# Изолированный staging для постоянного worker

`itmap-worker-staging.service.example` — пример для отдельного тестового
контура, а не установленная служба и не способ переключить production. Сборка
worker должна включать драйвер MariaDB: `go build -tags mariadb -o itmap-worker
./cmd/itmap-worker`. Путь бинарника и каталог в примере выделены для worker;
учётная запись службы и файл настроек создаются отдельно оператором.

Команда принимает только `APP_ENV=staging`, локальную тестовую MariaDB с
именем `itmap_worker_staging` и пользователем `itmap_worker_app`, а также явные
флаги `ITMAP_WORKER_ENABLED=1`, `ITMAP_PARSER_EXECUTION_ENABLED=1` и
`ITMAP_WORKER_STAGING_REAL_PROVIDERS=1`. Файл настроек содержит секреты и должен
быть доступен только назначенному пользователю и администратору. Не помещайте
значения в Git или журналы. Использовать только изолированные тестовые данные и
провайдеры, соответствующие разрешённому эксперименту; сам флаг не является
разрешением на платные операции.

`Restart=on-failure` позволяет supervisor перезапустить процесс, когда тот
обнаружил смену generation; новая копия повторно читает состояние БД.
`TimeoutStopSec=90s` оставляет время для ограниченного завершения активного
шага и cleanup. Это не доказывает сохранность всех результатов при SIGKILL или
корректность внешнего провайдера. При остановке служба не должна автоматически
возвращать старый scheduler.

Перед любой реальной установкой отдельно проверить изоляцию базы, секреты,
версии, предохранители расходов, отсутствие конкурирующего consumer, результаты
CI и план восстановления. Настройка systemd, запуск worker, операции с рабочей
БД и платные вызовы требуют отдельного разрешения. Шаблон не включён в релизный
pipeline и сам ничего не устанавливает.

## Проверяемый артефакт worker

Workflow `Worker build artifact` собирает отдельные Linux amd64 и arm64 бинарники с
MariaDB-драйвером и публикует каждый вместе с отдельной операторской командой
`itmap-recovery`, `commit.txt`, сведениями сборки обоих бинарников и
`SHA256SUMS` как временный артефакт GitHub Actions. Он проверяет, что встроенная
в бинарник версия совпадает с проверенным commit и рабочее дерево чистое.
Проверяйте `GOARCH` в `build-info.txt` и выбирайте артефакт по архитектуре
целевой машины: arm64 для `aarch64`, amd64 для `x86_64`. Для pull request
это тестовый merge commit GitHub, а не обязательно вершина
ветки; для поставки следует брать артефакт успешного запуска на нужном `main`.
Контрольная сумма позволяет проверить целостность скачивания и сама по себе не
удостоверяет происхождение файла. Workflow не устанавливает и не запускает
worker, не обращается к серверу или платным провайдерам и не заменяет CI,
операционную приёмку и отдельное разрешение на запуск.
