# it-map — генеральный план миграции на Go

**Состояние на 26.10.2026:** спринт 1.1, Go/React собираются и ограниченно запускаются; synthetic MariaDB/API/browser CI успешен. Полная миграция и production-приёмка не завершены. Актуальные источники — код проверенного стека, tasks/STACK.md и CI; v12–v21 — исторические отчёты. Конкретные задачи и приёмка: [tasks/README.md](tasks/README.md).

## Цель и инварианты

Заменить сервер GPT Sites/Cloudflare Worker на автономный Go-бекенд с MariaDB на том же сервере, сохранив React-фронтенд, данные, пользовательские сценарии, API и функциональность работающего парсера. Итог после 1.4 — сопровождаемый модульный Go-монолит инженерного качества. В 1.1 приоритет работающему переносу, не идеальной архитектуре.

**Старый сервис остаётся действующим** весь период разработки. Пока Go развивается, GPT Sites использует собственные D1 и Site Automation, а тестовый Go использует отдельную MariaDB. Два независимых потока записи не становятся автоматически общей базой. Дату окончательного снимка и процесс синхронизации необходимо утвердить отдельно.

## Спринты и зависимости

### 1.1 — функциональный перенос, безопасный запуск

Последовательность: безопасность исходников и реестр API → Go/конфигурация/MariaDB/Vite/staging → авторизация, компании/CRM, вакансии и отклики → задачи/Google Calendar, настройки, backup v39 и Excel/JSON → ИИ/генерация → Firecrawl/Apify/JEV и импорт → автономные Go-очередь/планировщик/диагностика → регрессия и контролируемый cutover. Все 28 исходных задач сохранены в `tasks/SPRINT-01.md` (GO-001…GO-028); небольшие проверяемые части выделяются отдельно без потери исходных задач.

**Готовность:** действующие React-сценарии и критичные API совпадают с эталоном; Go собирается с MariaDB-драйвером; тестовая база проходит проверку схемы, целостности, транзакций; backup v39 делает проверенный round-trip; парсер проходит полностью от источника до сохранения/релевантности, соблюдая бюджет, повторы, блокировки и восстановление после перезапуска; автоматизация не запускает два парсера; staging прошёл end-to-end и регрессию. Не выдавать `go test ./...` за подтверждение всего релиза.

### 1.2 — исправление грубых инженерных недостатков

Зависит от принятого 1.1: качество конкурентных операций, транзакций, индексов, типов API/ошибок, security/CSRF/таймаутов; воспроизводимые тесты и эксплуатационная наблюдаемость. Небольшие улучшения: 30-дневная воронка парсера с фильтрами источника/провайдера, графики P1/P2, контроль повторов, оптимизация источников при подтверждённых дефектах. Изменения API и фронтенда допустимы после согласования. Готовность: нет известных критичных дефектов, релевантные тесты/race/CI и эксплуатационные проверки проходят.

### 1.3 — RabbitMQ

После стабилизации и проверенной устойчивой MariaDB-очереди: закрытый RabbitMQ; `transactional outbox` в MariaDB; durable доставка только идентификаторов заданий; consumer + lease + ACK после фиксации состояния, retry/DLQ и защита платных вызовов от повторов. Переключение стадий поэтапно с возможностью вернуться к MariaDB-диспетчеру. Готовность: тесты отключения брокера, повторной доставки, падений и восстановления без потери заданий и двойных списаний.

### 1.4 — доводка до уровня Team Lead

После 1.3: убрать подтверждённо неиспользуемый переходный код (без удаления `gpt-site`), выровнять зависимости пакетов, ошибки и конфигурацию; комментарии для инвариантов и публичных API, GoDoc, тестирование, профилирование, документация API и runbook; воспроизводимый выпуск и восстановление. Готовность: новый инженер без доступа к реальным данным способен локально запустить/проверить проект и выполнить безопасный релиз по инструкции.

## Проверка совместимости

1. Использовать `docs/LEGACY_API_BASELINE.md`, `docs/LEGACY_API_PATHS.json`, `docs/API.md` и реальные вызовы `frontend/api/client.ts` для матрицы: метод, URL, роли, запрос, JSON, коды, побочные эффекты.
2. Для каждого метода покрыть success/failure, user isolation, conflict/duplicate/retry, даты и `null`; сравнивать JS/Go на **синтетических** эквивалентных фикстурах, не на production данных в CI.
3. На изолированной MariaDB с импортированным приватным снимком выполнить DB-интеграционные тесты, проверку `SHOW CREATE TABLE`, FK/триггеров, round-trip и ручные браузерные сценарии. Не публиковать результаты с личными данными.
4. Проверить полную цепочку: источники → классификация JEV → полный текст → структурирование → конечные роли → дедуп/импорт → релевантность; бюджеты и ошибки.
5. Проверить Chrome/мобильную верстку, авторизацию, PWA, восстановление после остановки процесса, импорт/экспорт и Google OAuth.

## Cutover: отдельное утверждение и окно обслуживания

1. Согласовать RPO/RTO, способ получения свежего прямого согласованного D1-снимка, безопасный доступ к расшифровке настроек и план обратного переноса новых Go-записей.
2. Развернуть изолированный Go staging. Нельзя выдавать старый снимок 23.10 за актуальную production-БД.
3. После отдельного утверждения: заморозить запись в GPT Sites, остановить Site Automation и дождаться завершения работ; сделать новый полный прямой D1-снимок; импортировать в **пустую** MariaDB; применить разрешённые миграции; проверить контрольные суммы, количество строк, FK, поколения, очереди, расходы и авторизацию.
4. Отдельно разрешить смену домена. Запустить Go без второго активного парсера; только после проверок открыть запись и фоновую обработку. Следить за ошибками, очередями и расходами.

**Откат:** до появления Go-записей возможен возврат маршрутизации на старый сервис; после новых записей переключение обратно на старую D1 без переноса дельты приведёт к потере данных. Основной сценарий — откат Go-релиза к совместимому предыдущему бинарнику при сохранении MariaDB. Переключение обратно на GPT Sites только по отдельно проверенной процедуре синхронизации.

## Открытые решения

Gin vs остающийся в коде `net/http`; формат и инструмент новых Go-миграций; точная стратегия финальной синхронизации D1→MariaDB; режим и бюджет staging-парсера; RPO/RTO; процедура перешифрования/восстановления интеграционных секретов; оставшаяся политика доверенных веток/защиты и реализация контроллера деплоя. **Не принимать эти решения самовольно.** Схема двух доменов утверждена пользователем 25.10.2026: main и последняя обновлённая non-main ветка, автоматический GitHub Actions, Ubuntu 24.04 LTS (ADR-018). ### Как продолжать работу

Выбрать следующий доступный критический результат → прочитать legacy контракт и зависимости → отдельная ветка от предыдущей проверенной вершины → тест контракта/реализация → Go vet/race/build и релевантные SQL/CI gates → коммит → отдельный stacked PR → обновить статусы/контрольную точку → сразу следующая доступная задача, без ожидания review/merge. Автоматический merge запрещён. Если родитель уже объединён, актуализировать базу открытых потомков перед их merge, не отправлять изменения в закрытую ветку как будто они попали в main. При приёмке всего стека проверять ancestry и содержимое default branch, а не только MERGED каждого PR; после merge родителя сразу перенаправлять открытого потомка на main.
